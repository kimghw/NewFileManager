# 브라우저 — 큰 문서에서 요소를 감추고·붙이고·옮기는 비용 (Chromium)

실측 2026-11-10. NewFileManager 화면에 연구개발계획서(74쪽 · 표 181개 · 문단 약 7,500 — 작업 19c31da0aa13)를 연 상태, Chromium(Playwright 헤드리스).
잰 것 = **쓰기 한 번 뒤 `getBoundingClientRect()` 한 번**이 걸리는 시간(쓰기가 더럽힌 스타일·배치를 그 읽기가 한꺼번에 계산한다).
재는 스크립트 꼴: `performance.now()` 로 감싼 `td.getBoundingClientRect()` — 쓰기 → 읽기를 번갈아 4~60번.

## 1. 주어가 `body` 인 `:has()` 규칙이 있으면 `hidden` 속성·요소 붙이기/떼기가 문서 전체 스타일을 다시 계산한다

| 쓰기(한 번) | `:has()` 규칙 있음 | `:has()` 규칙을 지운 뒤 |
| --- | --- | --- |
| body 자식의 `el.hidden = true/false` | 115~119 ms | 0~0.1 ms |
| body 에 요소 붙이기 / 떼기 | 115~150 ms | 0 ms |
| 쪽(.sheet) 안에 요소 붙이기 / 떼기 | 116~118 ms | 0.1~0.2 ms |
| 알림(#toast)의 `hidden` 바꾸기 | 115~118 ms | 0~0.1 ms |
| `el.style.display = "none" / ""` | 0~0.1 ms | — |
| `el.style.visibility`, 클래스 넣고 빼기, `data-*` 속성, `style.transform` | 0 ms | — |

- 그때 스타일시트에 있던 `:has()` 규칙 10개: landing.css `body:has(#empty:not([hidden])) …` 8개(시작 화면일 때의 상단 바 모양), heading-panels.css `…:has(.analysis-state.running)` 1개,
  style.css `.mc-work-option:has(input:checked)` 1개. 화면 안에서 `CSSStyleSheet.deleteRule` 로 `:has(` 가 든 규칙만 지우고 같은 측정을 되풀이하면 위 오른쪽 열이 된다.
- **원인은 주어가 `body` 인 규칙**이다(확인): landing.css 의 `body:has(#empty:not([hidden]))` 만 `body.no-doc`(클래스)로 바꾸고 나머지 `:has()` 둘(주어가 좁은 `.mc-work-option:has(input:checked)` ·
  `#headsOverview .result-meta:has(…)`)은 둔 채 다시 재면 위 오른쪽 열과 같다 — `hidden` 속성 120 → 0.1 ms · 붙이기·떼기 121 → 0 ms · 공용 메뉴 열기 125 → 0 ms · 알림 123~137 → 0.2 ms.
- 풀이: 주어가 `body` 인 `:has(… [hidden])` 은 body 아래 어느 요소의 `hidden` 속성·삽입·삭제도 결과를 바꿀 수 있어, 그런 변경마다 브라우저가 body 와 그 뒤 선택자에 걸린 자손(= 문서 전체)의 스타일을
  다시 맞춘다(왜 그런지는 브라우저 안을 보지 않은 추정이고, 위 수치는 실측). 문서가 작으면(53문단) 눈에 안 띄고, 큰 문서에서만 번마다 100ms 를 넘는다.
- 그 규칙이 있을 때도 **`hidden` 속성이 아니라 `style.display`** 로 감추면 걸리지 않았다(속성 선택자 `[hidden]` 과 무관한 변경이라).

대처:
- **주어가 넓은(`body`·화면 틀) `:has()` 를 쓰지 않는다** — 상태는 JS 가 클래스로 단다. NewFileManager 는 2026-11-10 에 `body:has(#empty:not([hidden]))` → `body.no-doc` 로 바꿨다
  (spec_hwpx_웹편집 ② §10 · ③ — 시작 화면 상단 바의 계산된 스타일·그림은 바꾸기 전과 같음).
- 그런 규칙을 못 없앨 때: 자주 켜고 끄는 것(마우스를 따라 나타나는 손잡이 · 미리보기 표시)은 `hidden` 속성 대신 `style.display` 나 클래스로 감추고, 요소는 문서를 열기 전에 한 번만 붙여 두고 다시 쓴다.
- 어느 경우든 요소를 여러 개 붙일 때는 붙이기를 다 한 뒤에 읽는다(읽기 한 번에 다시 계산 한 번 — 번갈아 하면 요소 수만큼).
- 큰 문서에서만 느린 화면 동작을 만나면 `el.hidden` 한 번 + 자리 읽기 한 번의 시간부터 잰다(100ms 대면 이것).

## 2. 문서를 따라다니는 작은 요소 — 쪽 안 절대 위치보다 body 고정 위치 + transform

표 60개의 왼쪽 위 모서리로 16px 단추를 차례로 옮기며(옮기기 → 다음 표 자리 읽기) 잰 합계:

| 방법 | 60번 합계 | 한 번 |
| --- | --- | --- |
| 쪽(.sheet) 안 `position: absolute` — 표가 있는 쪽으로 옮겨 붙이고 `left/top` | 1,691 ms | 28 ms |
| 한 쪽 안에서 `left/top` 만 바꿈 | 243 ms | 4 ms |
| `body` 자식 `position: fixed` — `left/top` | 120 ms | 2 ms |
| `body` 자식 `position: fixed` — `transform: translate(x, y)` | 0 ms | 0 ms |
| 스크롤 상자 안 `position: absolute` — `left/top` | 120 ms | 2 ms |
| (읽기만 — 처음 60번 / 다시 60번) | 119 ms / 0 ms | — |

- `transform` 은 배치를 다시 시키지 않는다. 고정 위치라 문서가 스크롤되면 따라 옮겨야 한다(`scroll` → `requestAnimationFrame` 에서 자리 한 번 읽고 `transform` 쓰기 — 읽을 때 더럽혀진 것이 없어 0ms 대).
- 화면 좌표라 CSS `zoom` 으로 키운 쪽 안의 크기 보정(`zoom: 1/z` — [CSS_zoom_중첩.md](CSS_zoom_중첩.md))이 필요 없다. 대신 보기 밖(도구 줄·옆 열 위)으로 나가면 직접 감춰야 한다.
- 처음 읽기 60번의 119ms 는 아직 자리를 잰 적 없는 쪽 밖 표를 처음 재는 값이고, 같은 것을 다시 읽으면 0ms 다.

쓰는 곳: 표 모서리 손잡이(`app/static/table_menu.js` `tmnBtn`·`tmnPlace` — spec_헤딩_추출 ② §16).

## 3. `body` 에 클래스를 달고 떼기 · 물려받는 속성 · 문서를 통째로 뗐다 붙이기

실측 2026-11-11. 같은 화면에 더 큰 문서(쪽 상자 100개 · 문단 12,706개 · `#doc` 아래 요소 41,780개)를 연 상태. 잰 것 = 쓰기 한 번 뒤 `getComputedStyle(문단).fontWeight` 한 번.

| 쓰기(한 번) | 걸린 시간 |
| --- | --- |
| `document.body.classList.add("busy-edit")` — 규칙 `body.busy-edit .doc .para {…}` · `body.busy-edit .doc {…}` 가 있을 때 | 203~233 ms |
| 그 클래스 떼기 | 341~353 ms |
| `#doc` 의 `style.cursor`(물려받는 속성) 바꾸기 — 켜기 / 끄기 | 53~62 ms / 57~65 ms |
| `#doc` 의 `style.pointerEvents` 바꾸기 — 켜기 / 끄기 | 57~62 ms / 59~62 ms |
| `#doc` 의 `style.caretColor`(물려받는 속성) 바꾸기 — 켜기 / 끄기 | 200~246 ms / 386~392 ms |
| `#doc` 에 클래스 달기 — 규칙 `.doc.busy-edit { cursor: progress; caret-color: transparent }` — 켜기 / 끄기 | 177~820 ms / 176~386 ms |
| 문단 하나의 `style.caretColor` 바꾸기 · 문단 하나에 클래스 달기 | 0~0.3 ms |
| 규칙에 안 걸리는 속성(`aria-busy`)을 스크롤 상자에 달고 떼기 | 0~0.1 ms |
| (아무것도 안 쓰고 읽기만) | 0~0.1 ms |

- **`body` 클래스에 걸린 자손 선택자 규칙**(`body.X .doc .para`)이 있으면 그 클래스를 달고 뗄 때마다 그 선택자에 걸릴 수 있는 자손 전부(문단 12,706개)의 스타일을 다시 맞춘다 — 켜고 끄는 한 쌍에 0.55초.
  1절의 `body:has()` 와 같은 꼴의 함정이다(「주어가 넓은 상태 표시」). 규칙이 하나도 안 걸리는 속성을 다는 것은 0ms.
- **물려받는 속성**을 그릇 하나에 바꿔도 그 아래 요소 전부(41,780개)가 다시 계산된다 — 속성마다 값이 크게 다르다: `cursor`·`pointer-events` 는 한 번에 0.06초,
  **`caret-color` 는 켜기 0.2~0.25초 + 끄기 0.39초**(`body` 클래스 규칙과 같은 크기). 클래스로 달든 `style` 로 달든 같다 — 선택자가 아니라 「물려받는 값이 바뀜」 이 비용이다.
  (왜 `caret-color` 만 비싼지는 브라우저 안을 보지 않았다 — 위 수치는 실측.) 글 커서 감춤처럼 **한 요소에만 필요한 것은 그 요소에만** 단다(0초).
- **문서 전체를 비우고(`doc.textContent = ""`) 같은 노드를 다시 붙이면** 다음 자리 읽기(`offsetHeight`) 한 번이 문서 전체의 스타일·배치를 다시 계산한다 — 여기서 0.41~0.52초(JS 자체는 0.05초).
  노드 몇 개만 그 자리에서 바꿔 끼우면(`first.before(...새 요소)` → 옛 요소 `remove()`) 그 쪽 상자만 다시 배치된다.

대처:
- 잠깐 켜는 상태 표시(바쁨·끌기 중)는 **`body` 가 아니라 그 표시가 실제로 닿는 가장 좁은 요소**에 달고, 금방 끝나는 동작이면 아예 달지 않는다(늦게 다는 타이머).
  처음에는 `#doc.busy-edit { cursor; caret-color }` 를 0.4초 뒤에 달았는데, 서버 응답이 0.4초를 넘는 편집마다 0.5~0.7초가 더 들었다(위 표 — 표시가 일보다 비쌌다).
- 큰 문서에서 「조금 고쳤는데 전체를 다시 그리는」 길(`textContent = ""` 뒤 다시 붙이기)은 고친 노드만 바꿔 끼우는 길을 따로 둔다.

쓰는 곳: 편집 응답을 기다리는 표시(app.js `busyMark` — 글 커서 감춤은 커서가 든 문단 하나에 `.para.busy-caret`, 진행 커서는 `#doc.busy-edit`(cursor 만)를 0.8초 뒤에) ·
구조 편집 뒤 그 자리에서 바꿔 끼우기(app.js `applyTops` → `flowSwap`) — spec_hwpx_웹편집 ② §11.

## 4. 배율(`zoom`)을 큰 문서에서 바꾸기 — 상자마다 나눠서 · 밀리는 형제는 `contain: paint` (2026-11-12 실측)

Chromium 140(Playwright 헤드리스), 협약용 연구개발계획서(쪽 상자 204개 · 문단 16,842 · `#doc` 아래 요소 54,841 · 표 239). 재는 법: CDP `Performance.getMetrics` 전후 차이 +
`browser.start_tracing(page, categories=["devtools.timeline", "blink", "toplevel"])` 로 받은 추적에서 주 스레드(= `Layout` 시간이 가장 큰 스레드)의 `ph: "X"` 사건을 이름별로 더함
(`UpdateLayoutTree` 의 `args.elementCount` = 다시 계산한 요소 수, `Layout` 의 `args.beginData.frame` = 어느 문서(iframe 포함)인지, `EventDispatch` 의 `args.data.type`).

- **그릇 하나의 `zoom` 을 바꾸면 그 아래 전부를 한 번에** 다시 계산·배치한다 — 위 문서에서 한 번에 스타일 0.4~1.4초 + 배치 0.5~1.2초(작게 → 크게가 더 든다). 쪼갤 수 없는 한 덩이라 그동안 화면이 멈춘다.
- **같은 값의 `zoom` 을 그릇이 아니라 자식 상자마다** 두면 그린 결과가 같다 — 쪽 210개 · 문단 602 · 칸 612 · 여백 표시 199 · 쪽 번호 102의 자리·크기 차이 0px, 스크롤 크기도 같음
  (그릇 자신의 길이 — flex `gap`·`padding` — 만 배율을 곱해 따로 준다. 자식의 `width: 100%` 는 전처럼 그릇 폭). `offsetWidth` 는 제 `zoom` 과 무관하게 배율 전 px 이라 `getBoundingClientRect().width / offsetWidth` 로 그 상자의 배율이 나온다.
  그러면 **상자 하나의 값만 바꾸고 자리를 읽을 때 그 상자만** 다시 계산·배치된다: 보기에 걸친 3~5쪽 13~21ms, 나머지는 4쪽씩 가운데값 11~22ms(가장 무거운 묶음 50~490ms).
- 하지만 **상자 하나의 크기가 바뀌면 그 아래 형제가 모두 밀리고**, 브라우저는 다음 프레임에 밀린 상자들의 속을 다 훑는다(PrePaint — 자리(paint offset)가 바뀐 요소마다): 위 문서에서 프레임마다
  PrePaint 35ms + Paint 18ms 안팎(추적을 켠 값), 71프레임에 PrePaint 만 2.4~2.8초 — 조금씩 나눠 바꾸면 전체 일이 오히려 는다.
  **밀리는 상자에 `contain: paint`** 를 주면 상자마다 자리 변환 노드가 생겨 속을 안 훑는다: 프레임의 주 스레드 몫 64 → 30ms, PrePaint 는 목록에서 사라짐.
- `contain: paint` 는 상자 밖에 그리는 것을 자르지만 **`overflow-clip-margin` 이 `contain: paint` 에도 듣는다**(실측: 60px 을 주면 30px 밖은 보이고 200px 밖은 잘림 · 0px 이면 둘 다 잘림). 길이는 그 상자의 `zoom` 을 따른다.
  부작용: 속의 픽셀 맞춤 기준이 그 상자로 바뀌어 **줄·괘선이 1px 안에서 달리 놓일 수 있다**(같은 화면을 걸기 전·후로 찍으면 글 줄이 1px 어긋난 곳이 있다 — 잘림은 아님). 고정 위치(`position: fixed`) 자손의 기준 상자도 그 상자가 된다.
- **`content-visibility: auto` 만으로는 안 준다**: 화면 밖 상자의 속을 건너뛰어도, 문서 전체의 자리를 읽는 코드(여백 표시 다시 그리기)가 건너뛴 상자를 강제로 갱신시킨다 — 열기 1.4~2.1초 그대로(스타일·배치 횟수만 19 → 466회).
  그 코드를 꺼 본 바닥값이 0.56~0.68초.
- **iframe 의 폭이 `@media (max-width: …)` 경계를 넘으면 그 iframe 문서 전체의 스타일을 다시 계산한다**: 같은 앱을 띄운 iframe(쪽 56개 · 요소 2만)이 700 → 390px 로 줄 때 `resize` 사건의 첫 자리 읽기에서
  `UpdateLayoutTree` 요소 20,770개 76~97ms(추적을 켠 값). 경계(540·460px)를 안 넘는 폭 변화에서는 안 든다 — 규칙 안의 선택자와 무관하게 미디어 질의의 참·거짓이 바뀌면 문서 전체다.
- **`ResizeObserver` 콜백은 크기가 바뀐 뒤**에 온다 — 그 안에서 「창 가운데에 있던 것」 을 지금 가운데 줄로 찾으면 틀린다. 스크롤 상자의 높이가 h₀ → h₁ 로 바뀌었고 스크롤 위치가 그대로면
  바뀌기 전의 가운데는 지금 가운데에서 `(h₀ − h₁) / 2` 만큼 떨어져 있다(상자의 위끝이 함께 움직였어도 같다). 이걸 안 빼면 도구 줄이 꺾여 32px 줄었다 늘 때마다 보던 자리가 20px 씩 밀렸다.
- 「보던 자리」 를 요소 + 그 안의 높이 비율로 적을 때 **`tr` 을 쓰지 않는다**: 세로로 합친 칸(rowspan)이 있는 행의 `tr.getBoundingClientRect()` 는 첫 줄 높이(18px)뿐이라 비율이 14 가 되고,
  배율마다의 작은 높이 차이가 그만큼 부푼다. `td`(합친 칸은 전체 높이)나 문단을 쓴다. `document.elementFromPoint` 는 문단 사이·그림에서는 그릇을 돌려주므로 그때는 가장 가까운 블록으로.
- **`document.elementFromPoint` 는 스타일·배치뿐 아니라 그리기 준비(PrePaint)까지 강제한다**(맞히기 검사가 그리기 속성을 쓴다). 배치가 깨끗해도 직전에 상자를 옮겼으면 그만큼 든다 —
  뒤에서 도는 조각(16ms 목표)마다 한 번 부르자 조각이 50~65ms 가 되고 `ScriptDuration` 이 0.15 → 0.6~0.9초로 늘었다(스타일·배치 시간에는 안 잡힌다). 되풀이 도는 길에서는 `getBoundingClientRect` 로 먼저 걸러 꼭 필요할 때만 부른다.
- 자리를 지키려고 `scrollTop` 을 고치면 `scroll` 사건이 난다 — 스크롤에 메뉴·도움말을 닫는 처리가 있으면 「보이는 것이 안 움직인 scroll」 을 가려야 한다(기준 요소의 화면 자리가 그대로인가).
