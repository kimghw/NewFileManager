  배율을 바꿀 때(단추·창 크기) 창 가운데 자리를 지킨다. 배율 범위 30~300%.
- **패널 폭**(2026-11-09): 오른쪽 패널 왼쪽 가장자리(손잡이 8px, 마우스를 올리면 파란 선)를 끌어 폭을 바꾼다 — 최소 280px, 문서 보기는 늘 360px 남김(창을 줄이면 패널이
  먼저 줄고 다시 넓히면 고른 폭으로). 키보드: 손잡이에 초점 → ←/→ 20px(Shift 80px), Home 최소·End 최대. 두 번 누르면 기본 폭(380px, 창 1100px 이하 320px).
  고른 폭은 이 브라우저 `localStorage`(`nfm.panelWidth`)에 기억 — 못 쓰면 기억만 안 함. 폭이 바뀌면 문서 맞춤 배율도 다시 맞춘다(위 「확대」). 좁은 창(820px 이하, 패널이 아래)은 손잡이 없음.
- **휠 쪽 넘김**(2026-11-09): 문서 위에서 마우스 휠 한 칸 = 한 쪽(2쪽 보기면 나란한 두 쪽 = 한 줄) — 쪽 위끝을 창 맨 위(쪽 번호 자리 아래)에, 「여백 빼고 맞춤」이면 본문 첫 줄을
  창 맨 위에(높이 맞춤과 같은 자리). 쪽이 창보다 길면 그 안에서 창 높이(−60px)만큼 먼저 움직이고 끝에 닿으면 넘긴다(거꾸로 올라갈 때 긴 쪽은 아래끝부터). 트랙패드는 손짓
  하나에 한 쪽(작은 값은 60px 모아서, 150ms 끊기면 새 손짓), 마우스 칸(|ΔY| ≥ 50px)은 칸마다(80ms 에 한 번까지). Ctrl·Shift·Alt+휠과 가로 휠은 브라우저대로.
  토글 「휠 쪽 넘김」(기본 켬) — 끄면 보통 스크롤.
- **2쪽 보기**(2026-11-09): 「2쪽」 단추 — 쪽 상자를 두 열 격자로(1·2, 3·4 … 줄마다 위끝 맞춤, 사이 24px), 폭 맞춤은 두 쪽 폭 + 사이로, 높이 맞춤은 그대로(지금 보는 쪽).
  켜고 끌 때 보던 쪽을 창 맨 위에 둔다. 두 설정 모두 이 브라우저 `localStorage`(`nfm.view`)에 기억.
- **도구 줄 한 줄**(2026-11-10): 문서 위 도구 2줄(확대·쪽 번호·휠 쪽 넘김 / 글자·문단·표·OWPML·실행 취소)을 **한 줄**로 합친다. 왼쪽 묶음 단추 「페이지 보기·폰트 수정·
  문단 수정·테이블 수정」 중 **하나만** 켜지고 그 묶음만 펼친다 — 페이지 보기 = −·배율·+·폭 맞춤·높이 맞춤·2쪽·쪽 번호·휠 쪽 넘김·키 안내 / 폰트 수정 = 굵게·기울임·밑줄·pt·색 /
  문단 수정 = 정렬 4·왼쪽 여백 ∓5mm·첫 줄·줄 간격 / 테이블 수정 = 행·열 넣기·지우기 6개(칸 안에서만 활성 — 항목은 [spec_owpml_편집.md](spec_owpml_편집.md) ② §4).
  오른쪽 「고친 문단 N개 ↑↓」·OWPML 상태·실행 취소는 늘 보인다. 고른 묶음은 `nfm.view`(`tool`)에 기억(기본 페이지 보기). 묶음 단추를 눌러도 문서 선택 범위는 남는다
  (도구 줄 전체 단추의 mousedown 기본 동작을 막음). 조작 높이가 모두 28px 라 묶음을 바꿔도 줄 높이(39px)가 같다. 줄이 좁으면 키 안내부터 줄이고(말줄임), 그래도 안 들어가면
  오른쪽 묶음이 둘째 줄(오른쪽 끝)로 꺾인다 — 가로 스크롤·겹침 없음, 그때 높이가 바뀌면 맞춤 배율을 다시 맞춘다(`refit`).
- **도구 묶음 아이콘**(2026-11-10): 페이지·글자·문단·표를 4개의 SVG 아이콘 버튼으로 표시한다. 기능 이름은 `aria-label`과 마우스 도움말로 제공하며 선택 표시(`aria-pressed`)·키보드 조작·기존 묶음 전환을 유지한다.

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| ① 패키지 왕복 | 연 그대로 `save()` | 원본과 바이트 동일(SHA-256) |
| ② XML 재직렬화 | 파서가 읽는 모든 XML 멤버(header·content.hpf·section*)를 lxml 로 다시 씀 | 멤버마다 바이트 동일 |
| ③ 웹 매핑 | 블록 트리의 글이 원본 XML 의 글과 같은지 — 재직렬화본을 다시 열어 블록 글 비교 | 모든 블록 글 동일 |
| ④ 한글 PDF | 원본 hwpx 를 한글 COM 으로 PDF | PDF 생성(쪽 수 기록) |
| ⑤ PDF 매핑 | 웹 블록(글 있는 문단·칸 문단)을 원본 PDF 글자열에 대응(글자·숫자만) → 블록마다 PDF 쪽 | 대응 비율 ≥ 90% 통과, 60~90% 주의, < 60% 실패 |
| ⑤-1 헤딩 레터 대조 | 헤딩 문단(§7)마다 PDF 첫 줄의 레터 글자·앞 공백·레터 뒤 공백·둘째 줄 들여쓰기·본문 왼쪽 여백(§3-2) | 모두 같으면 통과, 다른 곳이 있으면 주의, 레터 글자가 다른 헤딩 > 5% 면 실패 |
| ⑤-2 글꼴 대조 | 찾은 문단의 글자·숫자를 PDF 글자와 하나씩 맞춰 글꼴·크기·굵게·색(§3-2) | 모두 같으면 통과, 다른 글자·다른 글꼴이 있으면 주의, 크기(첨자 빼고)·굵게·색 중 하나라도 다른 글자 > 2% 면 실패 |
| ⑥ 재구성 렌더 | 전 XML 을 다시 쓴 zip 을 한글로 PDF → 원본 PDF 와 쪽마다 픽셀 비교(72dpi) | 쪽 수 같고 다른 쪽 0(미세 차이만 있으면 주의) |

- **병렬**(2026-11-08, `verify.run_flow`): 단계는 앞 단계가 끝나는 대로 스레드에서 시작한다 — `IMPORT_DEPS` = ③←②, ⑤←④, 쪽 나눔·⑤-1·⑤-2←⑤, ⑥←②+④
  (①·②·OWPML 검사·④ 는 함께 시작). ② 가 다시 쓴 바이트가 원본과 다르면 그 PDF 를 ④ 와 동시에 다른 한글 프로세스로 미리 찍는다(§5 풀 — 같은 바이트는 한 번만).
  앞 단계가 실패해 결과가 없으면 뒤 단계는 「건너뜀」(그 까닭), 단계가 예기치 않게 죽으면 그 단계 실패·뒤 단계 건너뜀.

- ⑤ 매핑 순서: (1) 칸 밖 본문 문단을 문서 순서대로(양쪽에 한 번뿐인 12자 이상 글 = 고정점, 나머지는 앞 항목 뒤·다음 고정점 앞에서),
  (2) 두 본문 문단 사이의 표 칸 묶음은 앞 문단 쪽 ~ 뒤 문단 쪽 범위에서 따로 순서대로, 그래도 남은 칸은 같은 범위에서 앞 칸 자리에 가장 가까운 것,
  (3) 남은 것 중 6자 이상이고 PDF 전체에 한 번뿐인 글은 그 자리. 한글 PDF 는 한 쪽의 본문 글을 먼저, 표 칸 글을 뒤에 쓰는 일이 많아 문서 순서 하나로는
  표 칸을 놓친다(연구개발계획서 양식: 문서 순서만 73.3% → 범위 검색 84.6% → 가까운 자리 95.2%).
- **미세 차이**: 다른 쪽이라도 PDF 줄마다 글(기호 포함 — 공백만 뺀 NFKC)이 같고 줄 상자가 1pt 안이며 그림(바이트 해시·자리)도 같으면 「미세 차이」로
  따로 센다. 선·도형 같은 벡터 그림 변화는 이 판정으로 모른다 — 화면은 「눈으로 확인 권장」으로 보인다.
- PDF 는 한 쪽씩 찍으므로(§5 「한 쪽씩 찍기」) 아래는 그래도 모아 찍힌 PDF(설정이 다른 꼴로 들어 있는 문서 등)가 올 때만 쓰인다.
  2쪽 모아 찍기 PDF(문서 첫 구역은 세로인데 PDF 장 대부분이 가로)면 장마다 왼·오른 반을 문서 쪽 둘로 나눠 매핑한다(`_halves`). 매핑·쪽 나눔은 **문서 쪽**,
  픽셀 비교·PDF 그림은 **장**(쪽 → 장 = `sheets`). 화면 단위: 쪽 상자 「n쪽 · PDF m장」, 비교는 「장」.

### 3-1. 쪽 나눔(쪽 상자 보기)

- 웹은 문서를 **쪽마다 종이 상자**로 나눠 그린다(구역 용지 크기·여백, 최소 높이 = 용지 높이, 위에 「n쪽」 — 누르면 PDF 탭에 그 쪽). 아래 여백은 padding 이 아니라 최소 높이가 남긴다
  (2026-11-10): 본문이 아래 여백 안으로 넘치는 동안은 상자가 용지 크기 그대로 — 한글도 2쪽 작성 요령 표를 본문 아래 286.6mm 까지 넘치게 찍는다(PDF 실측) — 여백을 다 쓴 뒤에야 길어진다.
- 나눔 단위 = 최상위 블록 하나 또는 **최상위 표의 행 묶음**(세로 병합 칸이 걸친 행은 한 묶음 — 그 사이는 못 나눔). 표는 행에서 잘라 쪽마다 조각 표로 그린다.
  글자처럼 취급한 개체 여럿은 본문 폭에 나란히 들어갈 때만 한 줄로 묶고, 넘치면 따로(한글도 줄을 바꿈 — 연구개발계획서 양식 일정표 2개가 한 문단에 있었다).
- 나눔 위치(서버 `pdf_map.paginate`): ① 단위의 쪽 = 안 문단들이 찍힌 가장 앞 쪽, 줄지 않는 가장 긴 부분열만 믿음 ② 쪽마다 PDF **맨 위 줄**(같은 높이 칸 글 모두)이
  어느 단위의 **첫 문단(표 행이면 칸마다 첫 글 문단) 첫머리**인지 찾아 나눔을 맞춘다. 같은 글의 표가 되풀이되면 앞 쪽 PDF 글에 그 글이 나온 횟수만큼 건너뛴 후보.
  짧은 칸 글(4자 미만·줄의 6할 미만)이 긴 줄 머리와 우연히 같은 것은 빼다. 맨 위 줄이 단위의 첫 문단이 아닌 곳에 있으면 **앞 쪽에서 이어진** 문단·행 → 그다음 단위에서 나눔.
- 결과 표지: ok(맨 위 줄 = 첫 단위) · moved(맨 위 줄로 나눔을 옮김) · split(앞 쪽에서 이어짐 — 쪽 상자에 「↑ 앞 쪽의 문단·표 행이 이어짐」) · short/blank(맨 위 줄이 1자·빈 쪽 —
  확인 못 함) · miss/none(못 맞춤). 「쪽 나눔 대조」 단계: 못 맞춤 0 이고 문단 쪽 일치(웹에서 놓인 쪽 ∈ 그 문단의 PDF 쪽) ≥ 90% 면 통과, 못 맞춤이 쪽의 10% 넘으면 실패.
- 매핑 전에는 한글이 저장한 줄 배치(`pageStart`)·구역 시작으로 「≈n쪽」 추정 나눔, 매핑이 오면 같은 노드를 다시 나눈다(편집 상태 유지).
- 요약 카드: 「파일 왕복 / 한글 출력 / PDF 위치 / 웹 화면(편집용 보기)」을 따로 적는다 — 위치를 못 찾은 문단도 파일에는 그대로 있다(① 바이트 동일).

- 한글이 없거나 PDF 출력이 실패하면 ④~⑥ 은 「건너뜀」(①~③ 만으로 판정)이라고 보인다.
- 매핑 결과(블록 → PDF 쪽)는 화면 블록 옆 쪽 번호로 보이고, 못 찾은 블록은 목록으로 보인다.

- **넘침 밀기**(2026-11-10, app.js `overflowPush`·`pushRow` — paginate 끝, 매핑이 있을 때만): 쪽 상자 본문이 용지 본문 높이(용지 − 위아래 여백)를 넘으면 그 끝의
  ① 자리 모르는 문단(빈 줄 — PDF 글이 없어 매핑 없음)·짧은 글 문단(5자 이하 — 「가까운 자리」 매핑이라 쪽이 틀릴 수 있음) ② 표 조각의 뒤 행(위 행의 세로 병합 칸에 안 덮이고
  다음 쪽에 들어갈 자리가 있는 행만 — 다음 쪽 머리의 이어짐 조각 `.cont` 로)을 다음 쪽 맨 위로 보낸다. 다음 쪽이 빈 쪽 표지(gap-page)·마지막 쪽이면 그대로, 표·그림·자리 아는 긴
  문단에서 멈춘다. 까닭: 쪽 머리 줄이 빈 줄·한 글자·「20××년」이면 위 매핑이 그 쪽 나눔을 못 잡아 앞 쪽이 길어진다(연구개발계획서 양식 28쪽 「o」「-」, 14쪽 빈 줄). 다음 쪽에
  자리가 없는 행은 안 민다 — 2쪽 작성 요령 249mm 행·11쪽 318mm 행은 한글도 넘치거나 행 안에서 나눈 것. url() 웹 글꼴이 늦게 오면 줄 수가 바뀌므로 `document.fonts.ready` 뒤
  한 번 더 밀고, 옮긴 게 있을 때만 배율·표시(tplMarksDraw·tblMarksDraw)를 다시 그린다.
- **넘침 나눔**(2026-11-10, app.js `overflowSplit`·`SPLIT_TOL` — paginate 끝, 넘침 밀기 뒤, 매핑이 있든 없든): **새 블록**(`kinds` 가 `new` — 구분 기준 반영·구조 편집으로 생긴 사본, 한글
  줄 배치도 PDF 매핑도 없어 앞 블록의 쪽에 쌓인다)이 든 쪽 상자만 보고, 본문이 용지 본문 높이의 **1.08배**를 넘으면 용지 높이로 어림해 뒤를 잘라 같은 용지·여백의 조각 상자
  `.sheet.over`(표지 「≈n쪽 +k」, `data-page` 는 원 쪽 번호·`data-over`=k)로 잇는다. 나눔 단위 = 최상위 문단·그림·표 행. 위 행의 세로 병합 칸이 덮는 행 앞에서는 못 자르므로 안전한
  경계 사이의 행 묶음을 **한 덩이로 재어**(덩이 아래끝) 들어가는지 본다(astra 11-10 ②: 남은 100px 에 150px 묶음이면 첫 행만 보고 넣어 앞 쪽이 넘치던 것) — 덩이 하나가 용지보다 길면
  그 조각만 길게 둔다. 조각마다 한 덩이는 남긴다. 행 0 부터 옮기는 표는 조각째, 중간 행부터면 이어짐 조각 `.cont`. 새 블록이 없는 쪽은 재지도 않는다 — 웹 글꼴·표 높이 차이로
  길어진 것이라(④ 「표·쪽 높이 — 남은 것」) 쪽 번호 = PDF 쪽을 지킨다. 조각은 **쪽 번호를 밀지 않는다**(뒤 쪽은 매핑의 PDF 쪽 그대로 — 실제 쪽은 출력파일 검증 뒤 PDF 탭에서),
  표지를 누르면 PDF 의 원 쪽. 높이·단위 위치는 쪽마다 한 번에 읽고(`getBoundingClientRect`, CSS zoom 환산) 그다음 DOM 을 옮긴다(읽기·쓰기 번갈아 강제 배치가 쪽 수만큼 나지 않게
  — 61 세션 부탁). `document.fonts.ready` 뒤(넘침 밀기와 같은 콜백) 조각까지 포함해 다시 재어 더 나누고 같은 쪽의 「+k」를 DOM 차례로 다시 매긴다(astra ③). 문턱 8% 는 새 블록
  두세 줄로 조각 하나를 만들지 않으려는 값(11-10 실문서: 13쪽 1.06배는 안 나눔) — 「모든 쪽 = 용지」를 보장하지 않는다(astra ①, 큰 설계는 ④·[artifacts/page_flow_astra_2026-11-10/](../artifacts/page_flow_astra_2026-11-10/)).

### 3-2. 헤딩 레터 대조 · 글꼴 대조 (`app/pdf_style.py`)

PDF 글자는 PyMuPDF `rawdict`(글자마다 자리·글꼴·크기·색) + `get_texttrace` 의 긋기(가짜 굵게 — references/HWPX_렌더링_검증.md)로 읽는다(`pdf_map.read_pdf(chars=True)`,
매핑 단계가 한 번 읽어 두 단계가 함께 쓴다). 매핑이 「가까운 자리」로 잡은 짧은 칸 글은 다른 칸 글자일 수 있어 둘 다 뺀다.

- **헤딩 레터 대조**(`check_heads`): §7 의 헤딩 문단(H·T)마다 매핑 자리의 PDF 줄(같은 블록·같은 높이 줄을 x 순으로 이음)에서
  - 웹 앞머리(첫 글자·숫자 앞 — 리터럴 레터 기호, 자동 번호·글머리는 라벨)를 PDF 줄에서 거꾸로 맞춰 문단 시작을 찾는다(그 앞 글자 = 같은 높이 다른 칸 글).
  - **레터**: 레터 글자(공백 뺀 NFKC)가 같은지. **앞 공백**: 줄 맨 앞 공백 칸 수가 웹 앞 공백 칸 수와 같은지(+ 폭 mm). **레터 뒤 공백**: 레터 끝 ~ 글 시작 사이
    공백 칸 수(+ 폭 mm) — 자동 번호·글머리 뒤 간격은 한글 번호 설정이라 폭만 잰다, 탭이 든 꼴도 폭만.
  - **둘째 줄 들여쓰기**: 같은 쪽에서 문단 글이 다음 줄로 넘어가면 (둘째 줄 x − 첫 줄 x) mm 가 서식의 `hangMm`(= −첫 줄 들여쓰기 — 내어쓰기면 양수)과 ±0.5mm 안인지.
  - **본문 왼쪽 여백**(맨 위 문단만): 첫 줄 x mm = 구역 왼쪽 여백 + 왼쪽 들여쓰기 + max(첫 줄 들여쓰기, 0) ±0.5mm. 2쪽 모아 찍기 반 쪽은 용지를 반 장에 맞춘 배율로 나눈다.
  - 가운데·오른쪽 정렬 문단은 둘째 줄·왼쪽 여백을 재지 않는다(줄 시작이 글 길이로 정해짐).
  - **웹에 없는 개요 번호**: 개요 문단(고정헤딩)은 웹이 레터를 안 보이는데 PDF 문단 시작 바로 앞에 글자가 붙어 있으면 그 글자(한글이 찍는 개요 번호)를 센다.
  - 꼴마다(자리·`full`) PDF 로 잰 앞 공백·레터 뒤 공백·둘째 줄 폭 mm 의 가운데 값(`heads.patterns`) — FileMergeManager 템플릿 패턴의 「들여쓰기 폭」 실측.
- **글꼴 대조**(`check_fonts`): 문단 글자(런 모양이 있으면 런마다)를 매핑 자리부터 PDF 글자와 하나씩 맞추고(어긋나면 그 문단은 거기까지), 8자보다 짧고 PDF 에 여러 번
  나오는 글은 뺀다(다른 자리의 같은 글 — 「작성 요령」·「합 계」).
  - **크기**(2026-11-08 고침): 웹이 바라는 크기 = 글자 크기 × (윗·아래첨자면 0.64) × √(장평/100) — PyMuPDF 크기는 글자 행렬 가로·세로 배율의 기하 평균이라
    장평 80% 글자는 0.894배로 읽힌다. 쪽 배율 = 쪽마다 PDF 크기 / 바라는 크기 의 가운데 값(한 쪽씩 찍기 ≈ 1.0), PDF 크기 ÷ 쪽 배율이 바라는 크기와 max(0.3pt, 3%) 안.
    웹 서식에 첨자가 없는데 바라는 크기의 55~75% 면 「첨자로 보임」(실패 셈에서 뺌). 웹 첨자·장평 글자 수는 단계 설명에 따로 적는다.
  - **굵게**: PDF span 굵게 비트·글꼴 이름 「Bold」·긋기 중 하나 ↔ 웹 굵게. Type3 글꼴(한글 HFT 「T1」…)은 알 수 없어 뺀다. **색**: span 색 ↔ 웹 색(없으면 검정).
  - **글꼴**(2026-11-08 고침): 글자마다 웹이 그리는 문서 글꼴 = 글자의 언어 글꼴(영문 U+0000–024F·한자·일어·기호 ㎎ 범위 — §3-3, 서식 요약 `fontLatin`…), 그 밖은 한글 글꼴.
    그 글꼴의 웹 계획(§3-3 — same·equiv·subst·fallback)이 가리키는 가족과 PDF 글꼴 가족(이름표 name table 1·4·6·16)을 견준다. PDF 이름이 「????」(한글 PostScript 이름을
    한글 PDF 가 ? 로 씀)면 웹 가족의 한글 PostScript 이름과 글자 수가 같을 때 같은 가족으로 본다(휴먼명조).
    판정: 같음 · 둘 다 대체(문서 글꼴이 없어 한글·웹이 같은 대체 글꼴로) · **같은 디자인**(HFT 를 한글은 Type3 로, 웹은 한컴 대응표의 TTF 로 — 이름으로는 확인 못 함,
    통과로 셈) · 웹이 다른 글꼴 · 한글 전용 글꼴(이름 모를 Type3 인데 대응표 없음) · 모름. 목록은 「한글 글꼴로 그린 글자」와 「언어 글꼴로 그린 글자」로 나눈다.
- 차이는 화면 「확인할 문단」 목록(`missing` [{id, text}] — 「레터 웹 「○」 · PDF 「□」(3쪽) — 글」, 글꼴은 끝에 문단 글 앞 40자)으로, 자세한 자료는 단계의
  `heads`·`fonts`. 검증 패널의 그 단계 아래 접힌 표 둘: **「레터 꼴별 PDF 실측」**(자리 · 꼴 · 문단 수 · 앞 공백 · 레터 뒤 · 둘째 줄 실측 / 서식 내어쓰기 mm — 서식 값은
  둘째 줄을 잰 문단들의 가운데 값), **「글꼴 판정」**(한글/영문 · 웹 글꼴(→ 웹이 그리는 대체) · 판정 · 한글 PDF 글꼴(글자 수), 「웹이 다른 글꼴」·「한글 전용 글꼴」 줄은 노랑).

### 3-4. 장평 · 줄 간격 · 문단 간격 웹 그리기 (app.js `paraLook`·`leadShift`, 2026-11-08 — 한글 PDF 실측으로 정함)

- **장평**(글자 가로 배율): 문단 상자를 폭 `100%/장평`·오른쪽 여백 `100% − 100%/장평`(자리 폭은 그대로)으로 잡고 `transform: scaleX(장평)` — 글자가 가로로 줄고
  줄 나눔도 한글과 같은 폭에서. 들여쓰기·여백은 1/장평 배로 준다. 한글 글자 간격 = 글자 폭 × 장평 × (1 + 자간) — **자간은 장평 적용 폭 기준**이라 줄인 상자 안의
  자간(letter-spacing)은 그대로. 런 장평이 문단과 다르면 글자 모양은 문단 장평, 간격만 `kr(1+s)/k − 1`em(전각 근사 — 두 예제엔 없음).
- **줄 간격**(%): 한글 줄 = 글자 높이(크기 s, 기준선 = 줄 위 + 0.85 s — lineseg 8,285줄 모두) + 여분 s × (줄 간격 − 100%)(아래). 줄 사이 거리 = s × 줄 간격으로 CSS
  `line-height` 와 같고, 다른 것은 여분 자리(CSS 는 위아래 반씩) — 문단 글자를 `position: relative; top: −(줄 높이 − s)/2` 로 올린다(배치·높이는 그대로).
  s = 문단에서 가장 큰 글자(런·문단 끝 빈 런 포함 — 첫 줄 기준 근사).
- **문단 끝 빈 런**: 마지막 hp:run 이 글 없는 런이고 그 글자 크기가 글보다 크면 한글은 마지막 줄을 그 크기로 잡는다(보이는 글 8pt + 끝 빈 런 10pt → 10pt × 줄 간격).
  블록 `endSizePt`(hwpx_doc `_end_size`, 읽기만) → 문단 끝에 보이지 않는 글자(`.para.end-size::after` U+200B, font-size = 그 크기).
- **문단 위·아래 간격**: 한글은 앞 문단 아래 간격 + 뒤 문단 위 간격을 **더한다**(CSS margin 은 겹쳐 큰 쪽만 남음) → padding 으로.
- Word(docx)는 줄 모형·간격 합치기를 안 쟀다 — 예전대로(줄 모형 이동 없음, margin).

### 3-5. 표 칸 크기 · 글자 폭 웹 그리기 (app.js `colWidths`·`renderTable`·`cellLastLine`·`scriptLook`·`renderPara`, fonts.py `extract_face`, 2026-11-10 — 한글 PDF 실측으로 정함)

11-09 ④ 「웹 표가 한글보다 길다」(3쪽 요약문 표 넘침 47mm — 쪽 상자가 용지 1.156배)를 고친 것. 쪽 상자 높이가 한글 쪽과 같아지도록 표와 글자 폭을 한글 모형에 맞춘다.
- **열 폭**: hwpx 칸 폭(`cellSz width`)을 행마다 아는 경계부터 더해(왼쪽→오른쪽·오른쪽→왼쪽) 만든 열 경계의 차 — 한글은 칸을 제 폭대로 놓으므로 PDF 괘선과 일치(요약문 표 경계 11곳).
  옛 추정(1칸짜리 칸 폭·병합 칸 균등 분할)은 18열 중 4열만 1칸짜리라 레이블 열이 좁아져 네 행이 줄 바뀌었다(23mm). 경계를 못 정한 열(폭 없는 칸)만 옛 추정. docx 도 같은 함수.
- **칸 높이 = 저장 높이**: td 는 `box-sizing: border-box`(style.css) — 기본(content-box)은 `height` 에 안쪽 여백과 모인 괘선 1px 이 더해진다(10mm → 11.25mm). 한글은 괘선을 저장한
  칸 크기 안에 긋고 CSS 모인 괘선(`border-collapse`)은 칸 네 변에 반 px 씩 더해지므로(행 +1px·글 폭 −1px) 안쪽 여백을 `calc(여백 − 0.5px)` 로(괘선 7mm, 「0,000,000」 18.16mm 칸 줄 바뀜).
  저장 높이는 최소 높이라 내용이 더 크면 그만큼(2쪽 작성 요령 표 — 저장 5.52, 한글도 16.9).
- **칸 줄 모형**(`cellLastLine`): 한글 칸 내용 = 글자 크기 + (줄 수 − 1) × 크기 × 줄 간격 + 위아래 칸 여백 — 마지막 줄엔 줄 간격 여분이 없다(문단이 여럿이어도 줄 사이 거리는 같음;
  글꼴 높이는 1em — 1쪽 10pt 1줄 칸 저장 4.33 = 3.53 + 0.4×2, 3쪽 4.52 = 3.53 + 0.5×2. 11-09 「+0.18mm」는 여백을 0.4 로 잘못 본 것). CSS 는 마지막 줄도 크기 × 줄 간격이라 칸의
  **마지막 문단** 아래를 크기 × (줄 간격 − 1) 만큼 당긴다(음수 margin — 글자 자리·줄 사이 거리는 그대로; s = 문단 가장 큰 글자, 줄 간격 없으면 1.35). docx 는 안 잼.
- **첨자**(`scriptLook`): 윗·아래첨자 올림·내림은 `vertical-align` 대신 `position: relative; top` — vertical-align 은 올린 만큼 줄 상자를 키운다(한글은 첨자가 줄 높이를 안 바꿈).
- **줄마다 가장 큰 글자**(`renderPara`): 한글 줄 높이 = 그 줄의 가장 큰 글자 × 줄 간격(13pt 라벨 + 11pt 설명 문단의 둘째 줄 = 11pt × 160% = 6.2mm, 웹은 13pt 기준 7.3mm 였음).
  런에 모두 크기가 있으면 문단 요소 크기를 런 최소 크기로 두고 런마다 크기를 준다 — CSS 줄 상자(strut)가 작아져 줄마다 그 줄 런으로 정해진다. 라벨(`::before`)은 `--para-size`
  로 문단 크기 그대로, 빈 문단·크기 없는 런(docx)은 문단 크기. `leadShift` 의 올림은 첫 줄(가장 큰 글자) 기준 근사 그대로.
- **표 바깥 여백**: hp:tbl `outMargin`(hwpx_doc `_table` → `outMarginMm`)을 표 위·아래 margin 으로(style.css `table.tbl` 의 CSS 변수 `--tbl-mt/--tbl-mb`, 없으면 1mm — docx).
  연구개발계획서 양식은 0.5mm(일부 0), 쪽 조각(.cont)은 위 0.
- **글자 폭 — 내장 비트맵 글꼴은 웹 글꼴로**(fonts.py `_faces`(표 목록)·face `bitmap`·`extract_face`·`css_src`·`file_of`, server `GET /api/fonts/{id}`): Chrome 은 `local()` 시스템 글꼴 중
  내장 비트맵(EBDT 표)이 있는 굴림·돋움·바탕·궁서 계열의 글자 폭을 **정수 px 로 반올림**한다(13pt 돋움체 17.33 → 18px = 3.8% 넓음, 10pt 돋움 13.33 → 13px = 2.5% 좁음, 11pt 14.67
  → 16px = 9% 넓음; 맑은 고딕·HCR·휴먼명조는 소수 그대로 — 11-09 「웹 Dotum 이 2~3% 좁음」의 정체). 같은 face 를 `url()` 로 주면 소수 폭 그대로(돋움체 13pt 「(1) (연구개발기관) …」
  165.07mm ↔ PDF 164.97). 그래서 그런 face 는 `url()` 을 local() 앞에 두고, 서버가 ttc 에서 그 face 의 표만 복사한 TTF(비트맵 표 EBDT·EBLC·EBSC 는 빼 13 → 6.4MB, 검사합 그대로)를
  내준다(메모리에 한 번만, `Cache-Control: private, max-age=86400`). ttc 의 다른 face 도 이제 url() 로 낼 수 있다(뒤 순위). 글꼴이 오는 동안은 `font-display: block`.
- 안 고친 차이는 ④ 「표·쪽 높이 — 남은 것」.

### 4. 출력파일 검증 (「출력파일 검증」 단추 — 옛 이름 「편집 검증」, 2026-11-08 바꿈)

내려받을 파일(「HWPX 저장」과 같은 `doc.save()`)을 한글로 출력해 원본 출력과 비교한다. 저장할 때 자동으로 돌지 않는다.

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| ⑦ 수정본 패키지 | 바뀐 멤버만 다시 썼는지, 다시 열면 고친 블록 외 글이 같은지 | 고친 블록만 글이 다름 |
| ⑧ 수정본 PDF | 저장본을 한글로 PDF, 원본 PDF 와 쪽마다 비교 | — |
| ⑨ 쪽 차이 대조 | 다른 쪽 = 고친 블록이 있는 쪽 / 미세 차이 / 그 뒤로 밀린 쪽 / 예상 밖(고친 첫 쪽보다 앞, 미세 아님) | 예상 밖 0 이면 통과, 밀린 쪽·쪽 수 변화는 주의 |
| ⑩ 수정 글 반영 | 고친 문단의 새 글이 수정본 PDF 에 있는지 — 기호까지(공백만 뺀 글), 안 되면 글자·숫자만 | 기호까지 모두 = 통과, 글자·숫자만 = 주의, 못 찾음 = 실패 |

- 「고친 곳 이후 차이(밀림 추정)」: 고친 첫 쪽 뒤의 미세 아닌 차이 — 줄 수가 바뀌어 밀린 것으로 **추정**할 뿐 원인은 확인하지 않는다(주의).
- 출력파일 검증은 시작할 때의 로컬 수정 번호를 단다(`revision`). 그 뒤 글을 더 고치면 요약 카드가 「지금 수정은 아직 검증 전」으로 바뀐다.
- 출력파일 검증은 수정본 PDF 에도 매핑을 만든다(`mappingEdited`) — PDF 탭에서 「수정본」을 고르면 그 위치를, 없거나 오래됐으면 「원본 기준」이라고 밝힌다.
- 고친 문단은 줄 캐시를 지워 한글이 이 PC 글꼴로 다시 나눈다 — 원래 글로 되돌려도 그 쪽이 다를 수 있다(references/HWPX_렌더링_검증.md).
- 쪽 비교 화면: 다른 쪽을 고르면 원본·수정본 쪽 그림과 차이 겹침을 나란히 보인다.
- **병렬**(`EDIT_DEPS`): 수정본 OWPML 검사·한글 다시 저장 ← 수정본 패키지, ⑨·⑩ ← ⑧. ⑧(수정본 PDF)과 한글 다시 저장은 다른 한글 프로세스에서 함께 돈다
  (다시 저장은 PDF 와 무관 — 한글만 있으면 원본 PDF 가 없어도 돈다).

### 5. 한글 PDF 출력

- 자식 프로세스마다 `HWPFrame.HwpObject` 를 계속 쓴다(파일 접근 확인 창은 프로세스마다 한 번 — 「모두 허용」). 자식은 **풀**(`pdf_render.Pool`, env `NFM_PDF_WORKERS`
  기본 2, 1~4)로 두어 검증 단계·문서가 동시에 출력한다 — 쉬는 자식에 하나씩, 없으면 기다림. 같은 바이트(캐시 이름)는 잠금으로 한 번만 찍는다.
  시간 한도 = 120s + 10s/MB(최대 900s), 넘거나 실패하면 자식·한글을 죽이고 다음에 새로 띄운다. PDF 는 내용 SHA-1 이름으로 캐시
  (`%LOCALAPPDATA%\NewFileManager\render`, env `NFM_RENDER`).
- **한 쪽씩 찍기**(2026-11-08 사용자 확정): 한글 PDF 출력은 문서 인쇄 방식을 따라 2쪽 모아 찍기 문서를 가로 장에 두 쪽씩 줄여 찍는다 — 실제 문서 모양과 달라
  비교 창이 헷갈린다(① 11-08 질의). 그래서 `export_pdf` 는 출력용 사본(`one_per_sheet`)의 `settings.xml` `PrintMethod`(0 아닌 값, 4 = 2쪽 모아 찍기)를 0 으로
  바꿔 찍는다 — 원본·다시 쓴 파일·수정본이 모두 같은 길을 지난다. 원본 파일 바이트·다운로드·한글 다시 저장 검증(`resave_hwpx`)은 그대로. zip 이 아니거나
  settings.xml·PrintMethod 가 없거나 이미 0 이면 받은 바이트 그대로, 다른 멤버는 원래 ZipInfo(순서·압축 — mimetype 첫 멤버 STORED)로 다시 쓴다.
  캐시 이름 = 사본 바이트 SHA-1(원본 바이트 이름으로 남은 옛 모아 찍기 PDF 를 다시 쓰지 않음).
- 확인 창을 없애려면 `tools/hwp_register_module.py`(보안 모듈 DLL 등록, HKCU) — 사용자가 실행 여부를 정한다.

### 7. 헤딩 레벨·레터 꼴 추출 (`app/headings.py` — FileMergeManager 에서 일부 이식)

- **레벨**(`levels`): 문서 순서로 열린 헤딩 스택 하나 — 고정헤딩(개요 문단 `outlineLevel`)은 제 수준(그 이상을 닫음), 문자헤딩은 가장 가까운 고정헤딩 위에서
  같은 레터 형제·더 깊은 십진 번호(「1.1」 아래 「1.1.1」)를 닫고 맨 위 + 1. 문자헤딩 = 기본 패턴 19종(「제N장」「N.N」「N.」「가.」「N)」「(N)」「①」「□」「○」「o」「ㅇ」
  「△」「-」「·」「▫」「*」 …, 뒤에 글이 있어야 함) · 글 없는 글머리 쓸 자리(「-」「o」) · 자동 번호·글머리(`list`, 레터 = `list:` + 라벨 모양, 형제 키에 수준 포함) ·
  판별 모양(`marker_token` — 두 번 이상 쓰이고 하나라도 위에 다른 헤딩이 있는 모양, FileMergeManager 자동 판정과 같음). 목차 줄·캡션·각주 안내 줄(「* …」)은 헤딩 아님.
- **표**: 표 칸은 표 앞 스택을 이어받고, 칸 안 고정헤딩은 표 뒤에도 남는다. 칸 2개 이상 표의 칸 안 문자헤딩은 H 없이 **T**(칸마다 새 스택, 칸 맨 앞 = T1),
  1칸 표(글상자)는 본문처럼 H. FileMergeManager 는 표 분류로 머리 칸을 H 로 빼고 작성요령 상자 안 줄을 헤딩에서 빼지만 여기엔 표 분류가 없어 모든 칸이 T, 상자 안도 헤딩.
- **레터 꼴**(`skeleton`·`head_of`): 줄 앞머리 = 앞 공백(`lead`) · 레터(`letter` — 공백 없이 붙은 첫 토큰 묶음 「1.1.」「(1)」「□」) · 레터 뒤 공백(`gap`).
  `full` = FileMergeManager 와 같은 꼴(공백 칸 수까지 `_2□_1`, 토큰 6개까지), `core` = 공백 뺀 꼴. 자동 번호·글머리는 레터 = 라벨, 앞 공백 없음, 뒤 공백 = 글 앞 공백.
- **둘째 줄**(`line2`): 강제 줄 바꿈이면 `forced`(둘째 줄 글의 꼴), 줄 배치 캐시 2줄 이상이면 `wrap`, 아니면 `single` — 셋 다 서식 왼쪽 여백·첫 줄 들여쓰기·
  `hangMm`(둘째 줄이 첫 줄보다 들어간 폭 = −첫 줄 들여쓰기)과 규칙 글(「왼 0 · 내어 5.5」).
- `extract(blocks, doc)` → 헤딩 문단마다 `{level, field, letter, source, parent, head, line2, place}`. 읽기만. 연구개발계획서 양식 918개·0.1초.

### 9. 작업별 도구와 병합 전 비교

- 검증·고친 문단·PDF·기록·헤딩 추출·구분 기준·문서 비교를 작업 영역 상단의 독립 진입점으로 제공한다. 현재 문서 이름과 각 도구의 목적을 표시하며, 검증 결과를 헤딩 분석의 통과/실패로 해석하지 않는다.
- 헤딩 추출은 결과 우선: 문서 구조·서식 라벨·템플릿·표 구조·확인할 항목을 바로 전환한다. 재실행·규칙·지침·상세 실행 기록은 추출·설정에 둔다. 결과의 실행 번호·문서 변경 여부를 표시한다.
- 문서 비교는 저장한 HWPX 작업 2~6개를 선택해 서식 라벨과 템플릿을 문서별로 나란히 확인한다(DOCX 구조 비교는 미지원 표시). 문서별 분석 시점·실행 번호·오래됨/결과 없음/읽기 실패를 구별한다. 조회 때문에 문서를 다시 열거나 추출·검증·LLM을 실행하지 않는다.
- S/F 라벨과 템플릿 번호는 문서 내부 식별자다. 문서 간 같은 번호를 동일 템플릿으로 취급하지 않는다. 같은 사슬/앵커는 비교 후보이며 병합 확정이 아니다. 사용자 확인 표시는 문서·편집 차례·추출 실행에 종속되며 오래된 결과에는 붙일 수 없다.
- 이번 범위는 비교와 확인까지다. 실제 문서 병합·대응 관계 확정·대상 서식 변환은 후속 구현이다.
- **탭 띠 한 줄·접기**(2026-11-10): 탭은 아이콘+이름 한 줄(부제 「파일·출력 확인」 등은 단추 도움말 title 로). 띠 오른쪽 끝 「접기 ▴」를 누르면 지금 탭 이름만 남는 얇은 띠로

### 10. 시작 화면

- **애플 스타일(2026-11-10)**: 시작 화면은 중성 흰색·옅은 회색 바탕, 검정에 가까운 큰 제목, 둥근 흰색 업로드 카드와 파란 알약 모양 버튼으로 통일한다. 상시 점선과 장식 색상을 줄이고 드래그 중에는 파란 테두리로 입력 영역을 알린다. 시작 상태의 상단 바·기능 아이콘·최근 작업도 같은 톤으로 맞추며 검증 상태 색상은 유지한다. 실제 작업 패널·편집 동작은 기존 계약을 유지한다.
- **시각 구성 보완(2026-11-10)**: 넓은 화면은 짧은 목적 안내와 흰색 업로드 카드를 나란히 배치하고, 좁은 화면은 한 열로 전환한다. 큰 단색 배경 대신 파일 선택 버튼·드래그 반응에 파란색을 집중한다. 지원 형식·한 문서 입력·환경 상태·접이식 예제는 업로드 주변에 모으고 최근 작업을 더 빨리 볼 수 있도록 상단 높이를 줄인다. 기존 파일 선택·드롭·예제·작업 재개 동작을 유지한다.
- 파일 선택을 가장 중요한 행동으로 둔다. 문서 편집·출력 확인이라는 목적을 짧게 안내하고, 넓은 드래그 영역과 큰 파일 선택 버튼을 제공한다. 입력은 HWPX·DOCX 한 문서이며 PDF는 출력 확인용이다.
- 편집·출력 검증·HWPX 구조 비교를 간단한 기능 안내로 나눈다. 예제는 접이식 보조 영역, 실행 환경은 짧은 상태 안내로 둔다. 원본과 수정본의 비교 등 세부 실행 설명은 작업 화면에서 제공한다.
- 최근 작업은 최신 4개만 표시하고 전체 목록으로 연결한다. 파일명·형식·작업 시점·실제 검증 상태를 읽기 쉽게 표시한다. 최근 목록 안의 별도 스크롤과 미실행 검증의 대시 표시는 없애며 삭제는 전체 작업 목록에 둔다.
- 좁은 화면에서도 파일 선택·예제·최근 작업에 접근할 수 있고, 페이지 전체가 하나의 세로 스크롤을 사용한다. 기존 문서 작업 화면은 유지한다.
