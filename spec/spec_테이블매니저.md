## ② 확정 사양

### 0. 말

- **테이블 매니저** = 표 하나의 「지금 판정」 을 내주는 모듈(`app/table_manager.py`). 화면이 아니다.
- **자동 역할** = 스크립트 초안, 또는 LLM 이 고친 역할(3단계 결과). **사람 지정** = 표 메뉴의 「헤더 지정」. 둘은 따로 지니고, 판정을 낼 때마다 합친다(최종 역할 = 자동 역할 위에 유효한 사람 지정).
- **보류** = 어느 칸의 지정인지 불분명해진 사람 지정. 쓰지 않고, 조용히 버리지도 않는다.
- **병합 방식** = 표(띠)를 여러 기관의 문서에서 모을 때 어떻게 모으는 표인지(§5).
- 이 사양서에서 **표**는 서브 테이블(띠)을 포함한다 — 판정 · 병합 방식은 띠마다다.

### 1. 층과 소유

- 엔진(`app/heading_tables.py` · `app/heading_calc.py`)과 3단계의 실행 · 저장 · 상태(`app/heading_runs.py`)는 그대로 둔다. `table_manager` 는 `heading_runs` · `app.server` 를 import 하지 않는 **순수 함수**다 — 지금 문서의 표 레코드 · 끝난 3단계 결과 · 사람 지정을 **인자로** 받는다. 세션 잠금은 부르는 쪽이 잡는다.
- **중립 층**(모든 문서): 칸 역할 · 띠 · 헤더 트리 · 필드 경로 · 숫자 · 합계/비율/코드 식. 프로젝트 구성이 있고 없음에 따라 달라지지 않는다.
- **프로젝트 귀속 층**(연구개발과제 문서만 — 관문은 구분 기준 판독과 같다: `division_scan_api.enabled`): 프로젝트 구성의 값(기관 · 차년도 · 단계)에 이은 것 — §5 병합 방식이 그 첫 소비자다.
  일반 문서에는 이 층이 **없다**(응답에 그 키가 없음 = 해당 없음). 머리글이 기관 · 연도 · 단계 꼴이라는 **일반 의미 후보**(3단계의 `basis`)는 어느 문서에나 있어 끄지 않는다.
- 「역할 판정이 모두 한 곳」 이 아니다 — 표 채우기의 대상 고르기 · 에이전트의 새 표 검산 · 서식 추출 LLM · 표 만들기 LLM · 취합 프레임의 칸 분류 · 이관의 표 서명 · `table_make.roles_of`(서식 구역 — docx · PDF · 웹 블록)는 따로 남는다.

### 2. 지금 판정

`table_manager.judge(stage1, tid, *, stored=None, user=None, same_doc=False, before=None)` → dict | None

- `stage1` = 그 표의 **지금** 문단 레코드 `{"paras": […]}`(`table_excel.records(doc, tid, …)` 의 꼴). `stored` = 끝난 3단계 결과의 그 표(dict — **고치지 않는다**) | None.
  `user` = **유효한** 사람 지정 `{칸 id: rowhead|colhead|field}` | None(§3 의 `check` 가 거른 것). `same_doc` = 그 3단계 결과가 지금 문서 차례의 것인가(`meta.rev == sess.rev`). `before` = 표 앞 문단 글(모르면 None — 저장된 것을 쓴다).
- 돌려주는 것: `{"table": 표, "subs": [띠…], "sem": 표 의미, "source": "stage3"|"draft", "reuse": {"ok": bool, "why": 글}, "inputKey": 글}`. 표가 아니거나 1칸 표면 None.
  - `table` = `heading_tables.collect` 꼴의 **새** 표: 칸의 글 · 문단 목록(`paras`) · 개체 · 좌표 · 숫자는 **지금 레코드에서**. 칸마다 `draft`(오늘의 초안) · `auto`(자동 역할) · `role`(최종) · `user`(사람 지정이 덮은 칸만 True) · `sub` · 경로 · 뜻(§9).
  - 헤더 경로 · 표 의미 · 수식 · 집계는 **역할을 합친 뒤에** 다시 계산한다(`finish_band` · `heading_calc.annotate`).
- **저장된 결과에서 다시 쓰는 것은 자동 역할과 띠뿐**이고, 다음이 모두 맞을 때만이다(`table_manager.reusable`) — 아니면 그 표 전체를 오늘의 초안으로(칸마다 섞지 않는다):
  ① `stored` 가 있다 ② 칸 id 집합이 같다 ③ `same_doc` 이거나, 저장된 `inputKey` 가 오늘 것과 같다 ④ 사람 지정이 녹은 칸(`reason` 「사용자 지정」)에는 `auto` 가 있다(없는 옛 결과는 못 가른다).
- **`inputKey`**(`heading_tables.input_key(tb, occ, bs)`) = 그 표로 LLM 에 보내는 자료(초안 띠 + 격자 토막 — 칸 id · 크기 · 음영/굵게/문단 종류 · 글 30자 · 초안 역할)의 해시. 3단계 `build` 가 표마다 저장하고(`inputKey`), 매니저가 오늘 것을 같은 함수로 낸다.
  문서의 다른 곳을 고쳐도 그 표의 자료가 그대로면 LLM 역할이 살아 있고, 그 표의 칸 글 · 모양이 바뀌면 초안으로 돌아간다. `inputKey` 가 없는 옛 결과는 `same_doc` 일 때만 다시 쓴다.
- **`auto`**: 3단계 `build` 는 사람 지정이 덮은 칸에 덮기 전 역할을 `auto` 로 남긴다(지정을 풀면 풀리게).
- 에이전트 판단(사용자 확인 전): 표 앞 문단 · 지침 글이 바뀐 것은 아직 안 본다(④) · 「값만 채운 표」 에서 LLM 역할을 살리는 느슨한 규칙은 두지 않았다(④).

### 3. 사람의 헤더 지정

- 저장(`table_heads.json`): 지정(`tables: {표 id: {칸 id: 역할}}` — 전과 같은 꼴)마다 **도장**을 따로 같이 둔다 — `stamps: {표 id: {칸 id: {"at": [행, 열, 행 병합, 열 병합], "text": 견줄 글}}}`. 견줄 글 = 칸 글에서 공백을 뺀 앞 60자. 도장이 없는 지정(옛 지정)은 유효로 본다.
- `table_heads.stamp(cell)` → 도장 dict(칸 = collect 꼴). `table_heads.put(wid, tid, cells, role, alive=None, stamps=None)` — `stamps = {칸 id: 도장}` 을 주면 같이 저장(안 준 칸의 옛 도장은 지운다). `table_heads.get(wid, tid)` 은 전처럼 `{칸 id: 역할}`(모든 지정 — 옛 호출자용). `load(wid)` 는 `stamps` 도 준다.
- `table_heads.check(wid, tid, tb)` → `(유효 {칸 id: 역할}, 보류 [{cell, role, why}])` — `tb` = 지금 표(collect 꼴). 도장의 자리나 글이 지금 그 칸과 다르면 **보류**(`why` = 「자리가 바뀜」 | 「글이 바뀜」). 지금 표에 없는 칸의 지정은 유효에도 보류에도 넣지 않는다(다음 저장 때 버린다 — 전과 같다).
- 보류가 있는 표: 읽는 끝점은 유효한 지정만 쓰고 응답에 `held` 를 싣는다. **문서를 바꾸는 끝점은 409**(「헤더 지정 n칸이 지금 표와 맞지 않습니다 — 표 메뉴에서 다시 지정하거나 풀어 주세요」) — 이 걸음에서는 표 서식 「맞추기」 와 빈 필드 제거.
  지정을 다시 하면(`put`) 새 도장이 찍히고, 풀면 지워진다.
- 구조 편집 뒤 지정을 칸 따라 옮기기(열 넣기 · 표 나누기 · 합치기의 매핑)는 다음 걸음(④). 그때까지 그런 지정은 위 규칙으로 보류된다.

### 4. 지우거나 쓰는 도구

- **기본 역할**: 문서에서 지우거나 칸 글을 쓰는 도구는 「스크립트 초안 + 유효한 사람 지정」 이 기본이다 — 빈 필드 제거 · 엑셀화의 기본 수식 · 표 서식의 빈 값 표시 맞추기. LLM 이 고친 역할로 달라지는 것은 검토 대상으로만 보인다(다음 걸음 — ④).
  표 서식 점검의 **서식 견주기**(글꼴 · 정렬 · 여백 — 글을 안 바꾼다)는 `judge` 의 판정(다시 쓸 수 있으면 LLM 역할)을 쓴다.
- **표 서식 점검**(`tables_api._style_tb` → `judge`): 응답에 `source` · `reuse` · `held` 가 실린다. 다른 서식 항목마다 `sig`(그 항목의 키 · 지금 값 · 맞출 값 · 대표의 해시)가 붙는다.
  - 빈 값 표시 항목(`mark` · `blank`)은 **초안 + 유효한 사람 지정**의 역할로 정한다(위 기본 역할) — `judge` 의 판정이 `stage3` 여도 그 항목만은 초안 판정에서 필드인 칸에 한한다.
  - `POST …/style/apply {keys, rev?, sigs?: {키: sig}}`: `rev` 가 지금과 다르면 409 · `sigs` 가 있으면 지금 점검의 `sig` 와 다른 항목은 건너뜀(`skipped` — why 「달라짐 — 다시 점검」) · 보류가 있으면 409. 화면은 `rev` 와 `sigs` 를 늘 보낸다.
  - 빈 값 표시를 쓰기 직전에 **지금 그 칸 전체**(칸의 모든 문단)를 본다 — 글이 빈 값 표시 하나뿐(또는 빈 칸)이고 개체가 없을 때만 쓴다. 아니면 건너뜀(why 「칸에 다른 글이 있습니다」).
- **빈 필드 제거**(`table_prune` — 2026-11-22 다시 정의: 빈 레코드 줄 · 서브 테이블 · 표째 · 소속 헤딩 · 열은 안 지움 · 열쇠 칸 · 쓴 값 검사는 §12): ⓐ 역할이 헤더(열헤더 · 행헤더 · 귀퉁이)여도 **성격이 필드인 칸**(긴 글 · 문장 · 값 — `nature == "field"`)에 글이 있으면(자리표시뿐이 아님) 그 줄은 채워진 줄이다(사람이 그 칸을 헤더로 지정했으면 지정이 먼저 — 그대로 헤더).
  실제 양식으로 재 보고 둘을 좁혔다(연구개발계획서 양식에서 그런 칸 66개가 작성 글이 아니었다 — 순번 55 · 짧은 글 여러 문단의 양식 제목 11): **순번 칸**(「1」·「①」 홀로)은 보호하지 않는다(번호 붙은 표의 빈 행이 후보에서 다 빠진다) ·
  **여러 줄에 걸친 칸**은 걸친 줄이 **모두** 지울 줄일 때만 막는다(남는 줄이 있으면 합친 칸이 줄어들 뿐 글은 남는다 — 참여 연구자 표의 빈 사람 줄이 전처럼 후보). 세 견본 문서(표 2 · 145 · 92)의 계획은 고치기 전과 같다(`_written` · `_guard`).
  ⓑ 미리보기에 줄마다 **빈 것으로 본 까닭**을 싣는다(`why: {rows: {줄: [자리표시 글…]}, cols: {…}}` — 글이 없는 칸뿐이면 빈 목록): 「00%」·「0,000」 같은 수 자리표시 꼴은 값일 수도 있어, 화면이 줄 이름 옆에 그 글을 보인다.
  ⓒ 보류가 있으면 지우기는 409, 미리보기는 `held` 를 싣는다. ⓓ 지우기 요청은 `rev` 가 있어야 한다(없으면 400 — 화면은 늘 보낸다).

### 5. 병합 방식

여러 기관의 문서를 한 문서에 모을 때 그 표(띠)를 어떻게 모으는 표인지를 **식별**한다 — 취합 · 이관의 넣기 동작은 바꾸지 않는다(읽는 쪽이 참고한다). 연구개발과제 문서만(§1 프로젝트 귀속 층) · 스크립트만(LLM 없음) · 문서는 안 바뀐다.

- 방식 넷(화면 말은 사용자의 말 그대로):
  - **기관마다 작성**(`perOrg`) — 그 표(띠)가 통째로 한 기관의 것: 기관마다 같은 표를 하나씩 쓴다.
  - **구분 기준에 따라 병합**(`byDivision`) — 표 안에서 구분 기준의 값마다 행 · 열이 갈린다(기관 행 · 기관 열 · 차년도 열 …): 들어온 값은 그 값의 행 · 열에 들어간다.
  - **셀 값 합산**(`sum`) — 기관이 갈리지 않은 공통 표인데 숫자를 채우는 표: 기관마다 낸 값을 같은 칸에 더한다.
  - **공통**(`common`) — 위 셋이 아닌 표(한 번만 쓰는 글 표 · 양식 표).
- `app/table_kinds.py`(순수): `kinds(table, zone_of=None, repeats=None)` → `{"table": 표 id, "kind": 방식 | "mixed", "subs": [{"sub": 띠 id, "kind": 방식, "basis": [org|year|stage…], "axes": [{"basis", "on": "row"|"col", "values": n}], "orgs": n, "why": 글, "sure": bool}]}`.
  `table` = 3단계 결과 꼴의 표(칸 `role` · `sub` · `basis` · `num` · 띠 `axes` · `calc` · `signature` · 표 `owner` · `labels`). `zone_of(블록 · 칸 id)` → `{"org": 값|None, "year": …, "stage": …}` | None — 편집 구역이 읽은 귀속(`zones_api.read` · `zones.label_of` — 여기서 다시 계산하지 않는다).
- 정하는 차례(띠마다 — 먼저 맞는 것. 처음 적은 다섯 차례를 실물(저장된 3단계 결과 29개 · 견본 양식에 값을 반영한 문서)에 재 보고 다듬은 것 — 원본은 `app/table_kinds.py` 머리 설명):
  1. 기관(**편집 구역**): 띠의 칸이 서로 다른 기관 둘 이상 → **구분 기준에 따라 병합** · 띠의 모든 칸이 한 기관 → **기관마다 작성**.
  2. 기관(머리글의 꼴 — 한 기관의 표): 표 소속이 기관 구분 줄 아래 · 표 안의 기관 구분 칸 하나 · 「기관별 작성」 이라 적힌 표 → **기관마다 작성**(구분 칸이 둘 이상이면 구분 기준에 따라 병합).
  3. 기관(띠 안에서 갈림): 편집 구역이 띠의 일부 칸에만 한 기관을 줌 · 머리 칸의 기관 행/열 → **구분 기준에 따라 병합**. 값 머리 하나뿐(「주관연구개발기관 | 값」)은 행/열로 치지 않는다.
  4. 기관(머리글의 꼴 — 한 기관의 양식): 표의 기관 머리가 기관 이름 칸(「연구개발기관명 | 값」)뿐 → **기관마다 작성**(활용계획서 · 인적사항 꼴).
  5. 계산식 표(`calc.is`)이고 **합계 · 비율 · 코드 식**이 있으며 숫자를 채우는 필드가 있다 → **셀 값 합산**(숫자 필드가 여럿일 뿐인 띠 — 번호 칸 · 성능 목표 표 — 는 아니다).
  6. 차년도 · 단계 · **연도**(기관은 없음): 편집 구역이 칸에 서로 다른 차년도(단계) 둘 이상을 줌 · 값 머리(「1차년도」 · 「2차년도」 — 연도 값 머리 「2024」 · 「2025」 도: 3단계의 basis `period`)가 둘 이상 → **구분 기준에 따라 병합**. 표 전체가 한 차년도의 것인 표는 아니다(「표 안에서 갈린다」 가 아니라서).
     연도 열은 2026-11-19 사용자 답 「일단 하고 추가로 수정할게」 로 넣음(그 전에는 구분 기준으로 치지 않았다) — `why` 는 「연도 열 n」.
  7. **공통**.
- 방식을 정하는 띠는 값을 모으는 띠(matrix · form · plain · list)뿐이다 — 제목 · 안내 · 간격 띠는 뺀다(그런 띠뿐인 표는 모든 띠). 띠마다 `by`(정한 근거: zone · owner · labels · text · heads · form · calc · none)가 더 붙는다.
- `sure` = 편집 구역(프로젝트 구성의 값)이 근거일 때 True, 머리글의 꼴(3단계의 `basis` · 표 소속)만이 근거면 False. 편집 구역이 기관을 못 읽은 곳(「기관 모름」 · 「기관 확인 필요」)은 한 기관으로 치지 않는다 — 근거로 쓰지 않고 `sure` 만 내리며 `why` 끝에 칸 수를 적는다.

### 7. 키-값 추출과 매핑

표를 **키-값**(값 칸마다 「어느 헤더 아래의 칸인가」 = 키, 그 칸의 글 = 값)으로 뽑고, 그 키-값을 **다른 표**의 같은 키 칸에 넣는다. 스크립트만(LLM 없음) · 어느 문서에서나(중립 층) · hwpx 만.
이관 · 취합의 표 잇기(`merge_fixed` · `merge_tables` · `merge_table_map`)는 TASK 안의 길이라 그대로 두고, 이것은 표 하나를 다루는 공통 도구다.

- `app/table_kv.py`(순수):
  - `extract(tb)` → `{"table": 표 id, "items": [{"cell", "ref"(A1), "sub", "row": [행 경로의 머리 글…], "col": [열 경로의 머리 글…], "key": 견줄 키 | None, "label": 보일 키 글, "text": 값 글, "empty": bool, "num": 수 | None, "calc": bool}], "dups": [키…], "counts": {items, keyed, empty, dups}}`.
    `tb` = `judge()["table"]`(칸마다 `role` · `rowPath` · `colPath` · `formulas`). 필드 칸만. **키** = 행 경로 · 열 경로의 머리 글을 각각 핵심 글(`heading_calc.key` — 각주 번호 · 단위 괄호 · 코드를 떼고 공백 없이 소문자)로 바꿔 이은 것(「행1›행2|열1›열2」). 경로가 둘 다 빈 칸은 키 없음(`key` None).
    `empty` = 빈 칸이거나 자리표시뿐(`table_prune.cell_empty`). `calc` = 수식으로 셈하는 칸(`formulas` 가 있음). 한 표에 같은 키가 둘 이상이면 `dups` 에 적고 그 키는 매핑에 쓰지 않는다.
  - `plan(src, dst)`(둘 다 `extract` 의 결과 — src 의 값을 dst 에) → `{"pairs": [{"key", "label", "from": 칸, "to": 칸, "text": 넣을 글, "was": 지금 글, "status"}], "unmatched": {"src": [키 없는 · 짝 없는 항목…], "dst": […]}, "counts": {fill, same, clash, calc, emptySrc, unmatched}}`.
    `status`: **`fill`**(dst 칸이 비었고 src 에 값이 있음 — 넣을 수 있음) · `same`(글이 같음) · `clash`(dst 칸에 다른 글이 있음 — **덮지 않는다**) · `calc`(dst 칸이 수식으로 셈하는 칸 — 안 넣음) · `emptySrc`(src 가 빔).
    키가 꼭 같을 때만 짝짓는다(어림 · 차례 짝 없음 — 틀린 칸에 넣는 것보다 안 넣고 알리는 것이 낫다).
- 역할: 값을 쓰는 도구라 **초안 + 유효한 사람 지정**(§4 기본 역할) — 두 표 모두 `judge(…, stored=None)`.
- **API**(`app/table_kv_api.py`): `GET /api/docs/{id}/tables/{tid}/kv` → `extract` 결과 + `rev` + `held`(문서 안 바뀜) ·
  `POST /api/docs/{id}/tables/{tid}/kv/plan {from: {table: 원본 표 id, doc?: 원본 문서 id}}` → `plan` 결과 + `rev` + 짝마다 `sig`(to 칸 · 넣을 글 · 지금 글의 해시)(문서 안 바뀜) ·
  `POST /api/docs/{id}/tables/{tid}/kv/apply {from, cells: [to 칸 id…], rev, sigs: {to 칸 id: sig}}` → 고른 `fill` 짝만 쓴다 — 쓸 때 계획을 다시 세워 `sig` 가 같은 것만(그 밖은 `skipped`) ·
  한 트랜잭션(`server._edit`: 실행 취소 1 · OWPML 지역 검사 · 기록 `tableKv`) · 응답 = 구조 편집 응답 + `mapped {table, from, done[칸], skipped[{cell, why}]}`.
  `{tid}` = 값을 받을 표. 원본 표는 같은 문서의 표, 또는 서버에 열려 있는 다른 문서(`from.doc`)의 표(안 열려 있으면 400). `rev` 가 다르면 409 · 받을 표에 보류된 헤더 지정이 있으면 `apply` 는 409(§3) · 칸의 글을 쓰는 길은 표 채우기와 같은 것(칸의 서식을 지킨다 · 칸 안에 표 · 그림이 있는 칸은 안 씀).
- **화면**(`app/static/table_kv.js` · `table_kv.css`): 표 메뉴 「키-값으로 보기 · 매핑…」 → 문서 옆 2열(kind `tblKv` — 팝업 아님): 이 표의 키-값 목록(키 · 값 · 빈 칸 표지 — 줄에 올리면 문서의 그 칸을 칠함) ·
  「다른 표에서 가져오기」 = 원본 표 고르기(이 문서의 표 목록) → 계획(「넣을 수 있음 n · 같음 n · 겹침 n · 짝 없음 n」) → 짝마다 「지금 (빈 칸) → 넣을 값 …」 · 체크 → 「고른 n칸 넣기」. 겹침 · 수식 칸은 고를 수 없고 까닭을 보인다.
- **매핑 규칙**(2026-11-19 사용자 "그리고 동일한 테이블이 아니면 매핑규칙은 관리되어야지" — ①): 키가 서로 다른 칸을 어느 키로 읽을지를 **규칙으로 저장해 관리**한다 — 한 번 정하면 같은 두 **표 타입**에 다시 쓰이고, 보고 고치고 지울 수 있다.
  - **표 타입**(같은 날 사용자 "같은 표 가 아니라 같은 타입 이런걸로 하면 되지" — 처음의 「표 지문」(키 묶음의 해시 `form_key`)을 바꿈: 값을 짧은 글로 채우면 견본 105표 가운데 54표의 키 묶음이 바뀌어 저장한 규칙을 못 찾았다):
    `table_kv.type_key(tb)` = 그 표의 **머리글 지문** — 음영이 있는 칸의 글을 (행, 열) 차례로, 빈칸 · 숫자 · 문장 부호를 빼고 칸마다 24자까지 이은 것의 해시(12자리). 음영 칸이 없으면 첫 행의 글, 그것도 없으면 키 묶음의 해시.
    「표 양식」(머리글이 같은 표 — spec_hwpx_웹편집 ② §8-11 · `outline_match` 의 머리글 지문)과 같은 규칙이다. 값을 채워도 안 바뀌고(값 칸은 음영이 없다), 기관 · 연도마다 되풀이되는 같은 표는 같은 타입이다(숫자를 빼므로 「1차년도」 표와 「2차년도」 표도). 화면 말 = 「타입」(「같은 타입」 · 「다른 타입」).
    **같은 타입이어도 키는 다를 수 있다**(「1차년도 › 현금」 ↔ 「2차년도 › 현금」) — 그래서 규칙은 같은 타입끼리도 둘 수 있고, 「같은 타입이면 규칙이 필요 없다」 고 보지 않는다.
  - **규칙 묶음** = (원본 타입 → 대상 타입) 한 짝마다 하나(같은 타입 → 같은 타입도 한 짝): `{id, name, from: {type, label}, to: {type, label}, alias: [{from: 원본 머리글, to: 대상 머리글}], pairs: [{from: 원본 키, to: 대상 키, fromLabel, toLabel}], version, updated}`.
    `alias`(머리글 바꿔 읽기) = 원본 키의 조각(머리글의 핵심 글)이 꼭 그 글이면 대상의 그 글로 바꿔 읽는다(「1차년도」 → 「1년차」 — 그 머리글 아래의 칸이 모두 따라온다). `pairs`(칸 짝) = 그 원본 키 하나를 그 대상 키 하나에(바꿔 읽기보다 먼저).
  - `table_kv.plan(src, dst, rules=None)`: 규칙이 있으면 원본 키를 ① `pairs` ② `alias` 로 바꿔 읽은 뒤 **꼭 같은 키끼리** 짝짓는다. 바꿔 읽은 뒤 같은 키가 둘 이상이 되면 그 키는 짝짓지 않는다(`dups`). 짝마다 `by`: `key`(그대로 같음) | `alias` | `pair`. 규칙으로 맺은 짝도 상태(`fill` · `same` · `clash` · `calc` · `emptySrc`)와 넣는 조건은 같다 — **규칙은 짝만 정하고, 넣는 것은 여전히 사람이 고른 빈 칸뿐**이다.
  - 저장(`app/table_maps.py`): 서버 전체에 하나(헤딩 저장소 폴더의 `table_maps.json` — 문서 · 작업에 묶이지 않는다: 같은 두 표 타입이면 다른 문서에서도 다시 쓰인다). `list()` · `find(from_type, to_type)` · `put(묶음)`(없으면 새로 · 있으면 기대 `version` 이 맞을 때만 — 아니면 `StaleVersion`) · `delete(id)`. 저장이 꺼져 있으면 메모리.
  - 끝점(`app/table_kv_api.py`): `GET /api/table-maps`(목록) · `GET /api/table-maps/find?from=&to=`(그 짝의 묶음 | null) · `PUT /api/table-maps`(만들기 · 고치기 — 409 판 다름) · `DELETE /api/table-maps/{id}`. `kv/plan` · `kv/apply` 는 그 짝의 묶음을 **저절로** 쓴다(응답 `rules: {id, name, alias: n, pairs: n, used: n} | null` · `types: {from, to, same: bool}`) — 요청에 `rules: false` 면 규칙 없이.
  - 화면(2열 `tblKv` 의 계획 보기): 계획 머리에 「같은 타입」 | 「다른 타입」 표지 · 「매핑 규칙」 묶음 — 쓰인 규칙 줄(「1차년도 → 1년차」 · 「칸 짝 …」 · ✕ 지우기) · 「짝 없는 항목」 에서 원본 하나와 대상 하나를 골라 「짝짓기」:
    두 키가 조각 수가 같고 **조각 하나만** 다르면 「머리글 바꿔 읽기」(그 머리글 아래 다른 칸 n개도 함께 — 수를 보인다)와 「이 칸만」 가운데 고르고, 그 밖에는 「이 칸만」(칸 짝). 고치면 바로 저장하고 계획을 다시 세운다. 이 묶음은 **짝 없는 항목이 있거나 쓰인 규칙이 있을 때** 보인다(같은 타입이어도).
    저장된 규칙 묶음 전체 목록(이름 · 원본 표 · 대상 표 · 규칙 수 · 이름 바꾸기 · 지우기)은 같은 열의 「저장된 매핑 규칙 n」 에서.
- **구분 기준으로 묶어 넣기**(다대일 — 2026-11-19 사용자 "구분기준에 따라 열헤더가 있을거 아냐? 거기 분류대로 넣으면 되지.. 넣을때 팝업으로 기준을 뭘로 할래 , 년차로 할래, 기관으로 할래 또 뭐가 있으면 어떤 기준으로 각각 그룹핑해서 넣으면 되지." — ①):
  값을 받을 표에 구분 기준의 머리글(「1차년도 | 2차년도」 · 기관 이름 열 …)이 있으면, 원본 표(하나 또는 여럿)를 **그 기준의 값마다 묶어** 그 값의 머리글 아래 칸에 넣는다. 원본 표는 그 머리글이 없는 표다(한 차년도 · 한 기관의 표).
  - **대상의 기준**(`table_kv.bases(tb)` — `tb` = `judge()["table"]`): 값 머리(`basisKind == "value"` · basis 가 year · org · stage · period)가 **둘 이상** 있는 곳마다 `{basis, on: "row"|"col", level: 경로에서 몇째, values: [{part: 키 조각, label: 머리 글, cells: 그 아래 필드 수}]}`. 없으면 빈 목록(묶어 넣기를 권하지 않는다).
  - **넣을 때 기준을 묻는다**(사용자의 말 「팝업으로 기준을 뭘로 할래」): 「가져오기」 를 누르면 작은 고르기 창이 대상 표에 있는 기준(「차년도로」 · 「기관으로」 · 「단계로」 · 「연도로」)과 「기준 없이(키 그대로)」 를 보인다 — 대상에 기준이 하나도 없으면 묻지 않고 키 그대로. 전체 화면을 덮는 창이 아니라 단추 옆의 작은 메뉴다(design.md — 큰 목록은 문서 옆 열).
  - **원본이 어느 값의 것인지**: 원본 표마다 그 기준의 값을 ① 편집 구역이 그 표에 준 귀속(기관 · 차년도 · 단계 — `zones_api.read` · 연구개발과제 문서) ② 표의 소속(3단계 `owner.division` — 기관 · 차년도 구분 줄 아래) ③ 표 앞 문단의 글에 대상의 값 머리 글이 든 것, 차례로 읽어 **권한다**(`by`: zone · owner · text | 못 읽음).
    못 읽었거나 대상의 값 머리와 안 맞으면 사람이 고른다 — 값이 정해지지 않은 원본은 넣지 않는다(짐작하지 않는다). 권한 값도 사람이 바꿀 수 있다.
  - **계획**(`table_kv.plan_grouped(sources, dst, group, rules=None)` — `sources = [{"ex": 추출, "value": 키 조각 | None, "table": 표 id}]` · `group = {basis, on, level}`): 원본마다, 대상 항목 가운데 **그 값 머리 아래의 칸**만 보고, 대상 키에서 그 조각을 뺀 키와 원본 키를 꼭 같을 때 짝짓는다(매핑 규칙 `rules` 는 그 뒤에 같이 — 타입 짝마다).
    짝마다 `group`(값의 머리 글)과 `from: {table, cell}`. 두 원본이 같은 칸에 걸리면 둘 다 넣지 않는다(`clash` — why 「원본 둘이 같은 칸」). 상태 · 넣는 조건은 1대1 과 같다(빈 칸만 · 겹치면 안 덮음 · 수식 칸 제외 · 사람이 고른 칸만).
  - **끝점**: `kv/plan` · `kv/apply` 의 `from` 이 목록도 받는다(`from: [{table, value?}]`) + `group: {basis}`(없으면 1대1 — 지금 그대로). 응답에 `bases`(대상의 기준) · `sources: [{table, label, value, valueLabel, by}]` · 짝의 `group`. `GET …/kv` 응답에도 `bases`.
  - **화면**: 「다른 표에서 가져오기」 의 원본 표를 **여럿** 고를 수 있다(목록에서 체크) → 「가져오기」 → 기준 고르기(위) → 원본마다 「어느 값의 것」 줄(권한 값 · 어디서 읽었나 · 바꾸기) → 계획은 값마다 묶어 보인다(「2차년도 — 넣을 수 있음 12 · 겹침 0」) → 「고른 n칸 넣기」.
  - 에이전트 판단(사용자 확인 전): 원본은 그 머리글이 **없는** 표라고 본 것(있으면 1대1 이 이미 맞는다) · 값을 못 읽으면 넣지 않고 사람이 고르게 한 것 · 값을 **더하는** 것(셀 값 합산 — 여러 원본의 값을 한 칸에)은 이 걸음에 넣지 않은 것(④) · 같은 문서의 표만 화면에서 고르는 것.
- **더해서 넣기**(다대일 — 셀 값 합산. 2026-11-19 사용자 「진행해줘」 — ②§8 의 다음 걸음): 원본 표 여럿의 **같은 키** 칸의 수를 더해 받을 표의 그 키 칸에 넣는다(§5 의 「셀 값 합산」 표 — 기관이 갈리지 않은 공통 숫자 표).
  - `table_kv.plan_sum(sources, dst, rules=None)`(`sources = [{"ex": 추출, "table": 표 id}]`): 받을 칸마다 `parts: [{table, cell, text, num}]`(그 키의 원본 칸들) · `sum` · `text`(넣을 글 — 수 글: 천 단위 쉼표는 원본 · 받을 칸의 자리표시 가운데 쉼표를 쓴 것이 있으면 · 소수 자리 = 원본들의 최대) · `status`:
    `fill`(받을 칸이 비었고 수인 원본이 하나 이상) · `same`(받을 칸의 수 = 합) · `clash`(받을 칸에 다른 값 — 덮지 않는다) · `calc`(받을 칸이 수식으로 셈하는 칸 — 안 넣는다: 합계 줄은 표의 수식이 셈한다) · `nonnum`(원본에 수가 아닌 글 — 안 넣는다) · `emptySrc`(원본이 모두 빔).
    원본 가운데 **일부만** 값이 있으면 있는 것만 더하되 `missing: n`(빈 원본 수)과 `check: true` 를 붙인다(화면이 처음에는 고르지 않는다 — 「원본 3 가운데 2개만 값이 있습니다」). 수는 `heading_calc.parse_num`(단위 · 쉼표 · 「-」 = 0)으로 읽는다 — 자리표시는 빈 것.
  - 끝점: `kv/plan` · `kv/apply` 에 `mode: "sum"`(`from` 목록 · `group` 과 함께 쓰지 않는다 — 400). 화면: 기준 고르기 메뉴에 「값을 더해서 넣기」 — 원본을 둘 이상 골랐을 때. 계획 줄 = 「지금 (빈 칸) → 넣을 값 1,200 (= 500 + 700)」.
  - 에이전트 판단(사용자 확인 전): 일부만 값이 있을 때 넣을 수 있되 처음에는 안 고르는 것 · 합계 줄(수식 칸)에는 안 넣는 것 · 구분 기준으로 묶은 뒤 더하는 것(묶음마다 합산)은 넣지 않은 것.
- **나눠 넣기**(일대다 — 같은 날): 구분 기준의 머리글이 **있는** 표 하나의 값을, 그 기준의 값마다 **받을 표 여럿**(그 머리글이 없는 표 — 한 기관 · 한 차년도의 표)에 나눠 넣는다 = 「구분 기준으로 묶어 넣기」 의 반대 방향.
  - `table_kv.plan_split(src, targets, group, rules=None)`(`targets = [{"ex": 추출, "value": 키 조각 | None, "table": 표 id}]` · `group = {basis, on, level}` — 원본의 기준): 받을 표마다, 원본 항목 가운데 그 값 머리 아래의 칸만 보고 **원본 키에서 그 조각을 뺀 키**와 받을 표의 키가 꼭 같을 때 짝. 짝마다 `to: {table, cell}` · `group`. 값이 정해지지 않은 받을 표는 넣지 않는다. 상태 · 넣는 조건은 1대1 과 같다.
  - 받을 표가 어느 값의 것인지는 묶어 넣기와 같은 차례로 권한다(편집 구역 · 표의 소속 · 표 앞 글 — 사람이 바꿀 수 있다).
  - 끝점: `POST /api/docs/{id}/tables/{tid}/kv/split/plan` · `…/kv/split/apply`(`{tid}` = 원본 표 · `to: [{table, value?}]` · `group: {basis}` · `cells: [{table, cell}]` · `rev` · `sigs`) — 받을 표 여럿에 **한 트랜잭션**으로 쓴다(`server._edit` — 실행 취소 1 · 기록 `tableKv`). 받을 표 가운데 보류된 헤더 지정이 있는 표가 하나라도 있으면 409.
  - 화면: 2열 `tblKv` 에 「다른 표로 나눠 넣기」 묶음 — 이 표에 기준(`bases`)이 있을 때만 보인다: 받을 표 체크 목록 → 「나눠 넣기」 → 기준 고르기(이 표의 기준) → 받을 표마다 「어느 값의 것」 줄 → 계획은 받을 표마다 묶어 → 「고른 n칸 넣기」.
- **구분 기준의 값 고르기**(2026-11-19 사용자 "테이블에 구분기준이 있으면 빼거나 일부 선택할 수 있게 해줘 예로 2027년 내용만 너허는다던지.. 이런거" — ①): 값을 받을 표(나눠 넣기에서는 원본 표)에 구분 기준의 머리글(`bases`)이 있으면, 계획에서 **그 기준의 값을 빼거나 일부만 골라** 넣는다 — 1대1 · 묶어 넣기 · 더해서 넣기 · 나눠 넣기 모두.
  - 계획 응답의 짝마다 `div: {기준(year · org · stage · period): 그 칸이 놓인 값 머리의 키 조각}`(받을 칸의 키에서 — 그 기준의 머리 아래가 아니면 그 기준은 없다)과 `bases`(기준마다 값 목록 · 값마다 짝 수 · 넣을 수 있는 수).
  - 화면: 계획 위에 기준마다 값 표지 줄(「연도: ☑ 2026 ☑ 2027 ☐ 2028」 · 「모두」 · 「모두 풀기」) — 표지를 끄면 그 값 머리 아래의 짝이 **고름에서 빠지고 목록에서 흐리게** 보인다(「2027 만」 = 나머지를 끔). 기준이 여럿이면 모두 켜진 값의 짝만 넣는다. 넣기 요청에는 고른 칸만 간다(끝점은 그대로 — 고르기는 화면의 일이고 서버는 짝에 `div` 를 실어 준다).
  - 묶어 넣기에서는 원본 표의 값 줄(「어느 값의 것」)과 같은 기준이면 그 원본을 통째로 빼는 것과 같다.
  - **같은 기준이 행 · 열 양쪽에 있는 표**(astra 4차 — 행 머리도 열 머리도 「2026년 | 2027년」 인 표에서 「2026년 행 × 2027년 열」 칸의 `div` 에 열 쪽 값만 남아, 2026 을 꺼도 그 칸이 들어갔다): 짝의 `div[기준]` 은 그 칸이 놓인 **모든** 값 머리의 조각이다 — 하나면 글, 둘 이상이면 목록.
    화면은 그 가운데 **하나라도** 꺼져 있으면 그 짝을 뺀다. `bases` 의 값마다 짝 수도 그렇게 센다(양쪽에 걸린 짝은 두 값에 다 센다).
  - **꺼 둔 값을 기억한다**(2026-11-19 사용자 "꺼 둔 값을 기억할게" — ①): 꺼 둔 값은 그 기준이 있는 표의 **타입**마다 저장한다(`app/table_maps.py` — 규칙 묶음과 같은 파일에 따로: `offs: {표 타입: {기준: [키 조각…]}}` · `get_offs(type)` · `put_offs(type, offs)`) — 같은 타입의 표를 다음에 열어도, 다른 문서에서도 꺼진 채로 보인다.
    끝점 `GET /api/table-maps/offs?type=` · `PUT /api/table-maps/offs {type, offs}`. 화면은 표지를 켜고 끌 때마다 바로 저장하고, 계획을 그릴 때 저장된 것으로 시작한다(값 표지 줄 끝에 「꺼 둔 값 n — 기억됨」 · 「모두」 를 누르면 지워진다). 저장된 조각이 지금 표에 없는 값이면 무시한다.
- **칸마다 넣는 방식**(2026-11-19 사용자 "어떤건 더해서 합이되는 필드가 있고 어떤건 다른걸 덮어 씌우면 합하거나 빼는게 있고 하잖아" → 물음에 답 「둘 다」 — ①): 받을 칸(키)마다 값을 **어떻게 넣을지**를 사람이 정하고 매핑 규칙에 기억한다.
  - 방식 넷: **빈 칸에만**(`fill` — 기본 · 지금까지의 동작: 받을 칸에 다른 글이 있으면 겹침으로 두고 안 넣는다) · **더하기**(`add` — 받을 칸의 수 + 원본의 수) · **빼기**(`sub` — 받을 칸의 수 − 원본의 수) · **덮어쓰기**(`replace` — 받을 칸의 글을 원본의 글로).
  - 규칙 묶음(타입 짝마다 — 위 「매핑 규칙」)에 `ops: [{part: 받을 표의 머리글 조각, op} | {key: 받을 칸의 키, op}]` — `part` 는 그 머리글 아래의 칸 모두, `key` 는 그 칸 하나(칸 쪽이 먼저). 없는 칸은 `fill`.
  - 계획: 짝마다 `op` 와 그에 따른 상태 — `fill`(전과 같다) · `add`/`sub`: 받을 칸이 비었으면 0 으로 보고 셈한 수 글(`text`)과 식(「= 500 + 700」) · 원본이나 받을 칸이 수가 아니면 `nonnum`(안 넣음) · `replace`: 글이 같으면 `same`, 다르면 「지금 … → 넣을 값 …」.
    **받을 칸에 이미 값이 있는 `add` · `sub` · `replace` 는 `check: true`** — 처음에는 고르지 않는다(같은 매핑을 두 번 하면 두 번 더해진다: 사람이 그때마다 보고 고른다). 수식으로 셈하는 칸에는 어느 방식도 넣지 않는다(아래 「계산 칸 다시 계산」 이 맡는다).
    「더해서 넣기」(여러 원본)에서 방식은 원본들의 합에 걸린다(`add` = 받을 칸의 수 + 합).
  - 화면: 계획의 줄마다 방식 표지(기본 「빈 칸에만」 은 표지 없음) · 줄을 골라 「넣는 방식…」(이 칸만 | 이 머리글 아래 모두 — 넷 가운데 고름) → 바로 저장 → 계획 다시 · 「넣는 방식」 묶음에 저장된 것 목록(머리글 · 칸 → 방식 · ✕).
  - 이관 · 취합의 「겹치면 덮지 않는다」(`jobs/plan_merge.md`)는 그 TASK 의 길 그대로다 — 여기는 사람이 표 하나를 보며 칸마다 방식을 **고른** 경우다. 기본은 여전히 빈 칸에만.
  - **셈하는 수의 단위**(2026-11-19 astra 4차 — 「2백만원」 + 「1,200천원」 이 「1,202」 로, 「2건」 + 「3명」 이 「5」 로 들어갔다): 더하기 · 빼기 · 더해서 넣기에서 셈하는 수들(원본들 + 값이 있는 받을 칸)의 **뒤 글(단위)** 을 견준다 —
    서로 다른 뒤 글이 섞이면 **셈하지 않는다**(`nonnum` — why 「단위가 다릅니다(천원 · 백만원)」: 환산하지 않는다). 뒤 글이 있는 수와 없는 수가 섞이면 셈하되 `check: true`(처음에는 안 고름 — why 「단위를 적지 않은 수가 섞여 있습니다」).
    넣을 글에는 뒤 글을 지킨다(받을 칸의 것 → 없으면 원본들의 공통 뒤 글). 수 앞의 글(「약 」 등)이 있는 것은 수가 아닌 글로 본다(전과 같다).
  - **「같음」 은 수가 꼭 같을 때만**이다 — 검산의 허용 오차(정수 원본이면 0.5)를 쓰지 않는다(「40 + 60」 과 받을 칸 「100.4」 는 같음이 아니라 겹침 · 덮어쓰기면 확인).
- **계산 칸 다시 계산**(같은 날 · 답 「둘 다」): 그 표에서 다른 칸을 더하거나 빼서 나오는 칸(합계 · 소계 · 코드 식 · 비율 — §9 의 수식이 걸린 칸)을 **수식대로 다시 계산해 넣는다**. 한글 문서에는 살아 있는 수식이 없어, 값을 넣거나 덮은 뒤 이 칸들은 누가 채워야 한다.
  - `table_kv.recalc(table, sem)`(순수 — `judge()` 의 표 · 표 의미에서): 수식 칸마다 `{cell, ref, formula(엑셀 수식 글), note(근거), now(지금 글), value(계산한 수), text(넣을 글), status}` — `missing`(칸이 비었고 계산됨 — 넣을 수 있음) · `mismatch`(지금 값과 계산이 다름 — `check: true`: 처음에는 안 고름) · `ok`(같음) · `incomplete`(더할 칸 가운데 빈 것이 있음 — 안 넣음) · `conflict`(그 칸의 두 수식(가로 합 · 세로 합)이 서로 다른 값 — 안 넣고 둘 다 보인다).
    여러 겹(소계 → 합계)은 **한 번의 계획에서 끝까지** 푼다(메모리에서 계산한 값을 넣어 다시 셈 — 5번까지). 넣을 글의 꼴(천 단위 쉼표 · 소수 자리 · % · 뒤 글)은 「더해서 넣기」 와 같은 규칙 + 그 칸의 자리표시 꼴.
  - **기대는 칸을 모두 따진다**(astra 4차 — 소계 「999」(계산은 30)와 빈 합계를 같이 고르면 합계에 옛 소계로 셈한 「1,039」 가 들어갔다 · 두 수식이 다른 칸에 기대는 칸이 「넣을 수 있음」 으로 나왔다): 수식 칸이 기대는 다른 수식 칸의 상태마다
    ⓐ `missing`(이번에 채우는 칸) → `needs`(그 칸들이 같이 들어갈 때만 쓴다) ⓑ `mismatch`(지금 값과 계산이 다른 칸) → 이 칸의 값은 **지금 값으로** 셈한 것이다: `stale: [그 칸…]` 과 `check: true`(처음에는 안 고름 — why 「기대는 칸 B4 의 지금 값(999)으로 셈했습니다 — B4 는 계산과 다릅니다」),
    그리고 **그 칸을 이번에 같이 고치면 이 칸은 넣지 않는다**(반영이 건너뛰고 `skipped` 로 알린다 — 넣은 뒤 다시 읽은 계획에 새 값으로 나온다 · 화면은 그 칸을 켜면 이 칸을 끄고 못 고르게 한다: 「B4 를 고친 뒤 다시 계산합니다」)
    ⓒ `conflict` · `incomplete`(셈하지 못한 칸) → 이 칸도 `incomplete`(안 넣음 — why 「기대는 칸 B4 를 셈하지 못했습니다」). 기대는 것은 겹겹이 따라간다(소계 → 합계 → 총계).
  - **넣을 글은 계산한 수와 같은 수여야 한다**(astra 4차 — 「0.0005 − 0.0002」 가 「0」 으로, 「100천원 − 20천원」 이 「80」 으로 나왔다): 소수 자리 = 셈에 든 칸들 · 그 칸의 글 가운데 가장 긴 소수 자리(비율 · 나눗셈은 그 칸의 꼴 · 없으면 2자리)이고,
    그렇게 적은 글을 다시 읽은 수가 계산한 수와 다르면(반올림으로 0 이 되는 등) 같아질 때까지 자리를 늘린다(6자리까지 — 그래도 다르면 `incomplete`: 「계산한 값을 이 칸의 꼴로 적을 수 없습니다」). 뒤 글(단위)은 위 「셈하는 수의 단위」 와 같은 규칙(서로 다르면 안 넣음 · 하나로 같으면 지킨다 · 비율은 「%」 만).
    구현하며 좁힌 것: 「같아질 때까지」 와 단위 견줌은 **더하고 빼는 식에만** 건다 — 비율 · 나눗셈 · 곱셈이 든 식은 그 칸의 꼴(없으면 2자리)로 반올림하고(1/3 같은 값이 모두 `incomplete` 가 되지 않게) 반올림해 0 이 될 때만 자리를 늘리며, 단위는 견주지 않는다(원 × 개 — 달라야 정상). 받을 칸의 꼴(자리표시 · 지금 글)에 적힌 뒤 글과도 같아야 한다(「00%」 자리에 「천원」 의 합을 넣지 않는다). 「-」(0)는 단위를 따지지 않는다.
    기대는 칸은 **그 값을 낸 수식이 셈에 쓴 칸**으로 따진다 · 「같음」 인 칸은 기대는 칸이 틀려도 같음이다(쓸 것이 없다) · 손으로 적힌 소계라도 그 소계를 셈하지 못하면(더할 칸이 빔) 합계는 `incomplete` 다 — 소계만 적는 표에서는 합계를 채우지 못한다(④).
  - **% 머리글의 합**(astra 4차 — 「%」 단위 머리글 아래 「10%」 · 「15」 가 있고 합계 칸이 비면 「15」 만 더했다): 그 줄의 머리글 단위가 % 면 「%」 를 적었든 안 적었든 그 줄의 칸을 모두 더한다(`heading_calc._sum_record` — 수식 판정 쪽). 「%」 를 적은 수와 안 적은 수가 섞인 것은 위 단위 규칙대로 `check: true`.
  - 끝점: `POST …/tables/{tid}/kv/recalc/plan`(문서 안 바뀜 — 목록 + `rev` + 칸마다 `sig`) · `POST …/kv/recalc/apply {cells, rev, sigs}`(한 트랜잭션 — 실행 취소 1 · 기록 `tableKv`). 보류된 헤더 지정이 있으면 409. 역할 = 다른 넣기와 같다(확정본 > 초안 + 유효한 지정).
  - 화면: 2열 `tblKv` 에 「계산 칸 다시 계산」 묶음 — 넣기를 한 뒤 저절로 다시 읽어 「다시 계산할 칸 n」 을 보이고(넣기 전에도 단추로 볼 수 있다), 줄마다 「지금 (빈 칸) → 계산한 값 400 (=SUM(B5:E5))」 · 체크 → 「고른 n칸 넣기」. 「더해서 넣기」 계획에서 수식 칸의 까닭 글은 「수식으로 셈하는 칸 — 넣은 뒤 다시 계산합니다」.
  - 에이전트 판단(사용자 확인 전): 넣기와 다시 계산을 두 걸음으로 둔 것(한 번에 묶지 않음 — 무엇이 계산된 값인지 보이게) · 지금 값과 다른 계산 칸을 처음에는 고르지 않는 것 · 두 수식이 다른 칸은 넣지 않는 것 · 이미 값이 있는 칸의 더하기 · 빼기 · 덮어쓰기를 처음에는 고르지 않는 것.
- 구현하며 더한 것(사양의 키를 빼거나 바꾸지 않음): `extract(tb, lines=None, objs=())`(`lines` = 칸의 글을 문단마다 줄로 — 넣을 때 문단 나눔을 지킨다 · `objs` = 칸 안에 표 · 그림이 있는 칸) · 짝의 `why` · `fromKey` · `fromLabel` · 짝 없는 항목의 `why` · `as`(바꿔 읽은 키) · `counts.unmatchedSrc`·`unmatchedDst`·`byRule`.
  상태를 정하는 차례: 원본 빔 → 글 같음 → 수식 칸 → 칸 안 표 · 그림(겹침) → 빈 칸(넣을 수 있음) → 겹침(수식 칸이라도 글이 같으면 `same`). `apply` 는 `rev` · `sigs` 가 없으면 400 · 넣을 칸이 하나도 안 남으면 409.
  다른 문서의 원본은 서버 메모리에 열려 있을 때만(작업 폴더에서 다시 열지 않는다). 「머리글 바꿔 읽기」 는 키 조각과 꼭 같을 때와 핵심 글로 바꾼 것이 같을 때 듣는다. 화면은 넣을 수 있는 칸을 처음부터 골라 둔다(표 서식 점검과 같은 방식).
- **잰 것 — 한계**(견본 `연구개발계획서_양식.hwpx` · 값 칸이 있는 표 105 · 빈 값 칸 3,314): ⓐ **표 지문이 값을 채우면 바뀔 수 있다** — 빈 값 칸을 모두 짧은 글로 채우면 105표 가운데 54표의 지문이 바뀐다(수 · 문장으로 채우면 4표).
  스크립트 초안이 짧은 보통 글 칸을 머리로 읽기 때문이다(§4 기본 역할 = 초안). 채운 표와 빈 양식이 「다른 표」 로 보일 수 있고, 저장한 규칙이 값을 넣은 뒤 그 짝으로 안 찾아질 수 있다.
  ⓑ **키가 하나뿐인 칸이 적다** — 빈 값 칸의 27%(902)만 짝지을 수 있다: 행 머리가 없는 목록형 표는 행마다 키가 같아 모두 `dups`(짝짓지 않음). → ④.
- 에이전트 판단(사용자 확인 전): 키를 헤더 경로의 핵심 글로 정한 것 · 꼭 같은 키만 짝짓는 것 · 겹치면 안 덮는 것 · 표 메뉴에 둔 것 · 한 번에 원본 표 하나 · 매핑 규칙을 서버 전체에 두고 표 지문의 짝으로 찾는 것 · 규칙의 두 꼴(머리글 바꿔 읽기 · 칸 짝) · 규칙을 LLM 이 제안하는 것은 나중(④).

### 8. 표 모듈의 묶음

사용자 2026-11-19(① 같은 날): 표의 일은 **네 묶음**이다. 차례대로 하는 단계가 아니라(「단계는 순차적이지 않지만」) 각각의 모듈 묶음이고, 필요한 것을 골라 쓴다.
표 기능을 새로 만들 때 어느 묶음인지 먼저 정하고 그 묶음의 모듈에 둔다 — 분석이 아닌 묶음은 칸 역할을 다시 판정하지 않고 분석(§2 `judge`)을 부른다.

- 묶음 사이의 방향: 분석 → (구성 개선 · 매핑 · 작성). 구성 개선 · 매핑 · 작성이 문서를 바꾸면 그 표의 분석은 다시 읽힌다(§2 — 지금 레코드에서).
- 프로젝트 구성(기관 · 차년도 · 단계)이 관여하는 것은 구성 개선(구조 변경)과 매핑(다대일 · 일대다 · 병합 방식)이고 **연구개발과제 문서에서만**이다(§1). 분석의 칸 역할은 구성과 무관하다.
- 파일을 묶음마다의 폴더로 옮기지는 않는다(지금) — 묶음은 이 표와 워크플로우 등록부(「표 도구」)의 말이다.

### 9. 표 하나만 프로젝트 구성에 맞추기

구성 개선 묶음(§8) — 표 메뉴에서 **그 표의** 구분 기준 자리만 프로젝트 구성(단계 · 차년도 · 기관)에 맞춰 행 · 열을 늘리고 줄인다. 연구개발과제 문서만(§1 — 관문은 구분 기준 판독과 같다).
- **새 실행 길을 만들지 않는다**: 구분 기준 엔진과 「프로젝트 구성 반영」 의 자리별 반영(`POST …/divisions/plan {only: 묶음 key}` → 계획 → `POST …/divisions/apply` — spec_구분_기준 ② §3·§7)을 그대로 쓴다. 이 기능은 그 표에 든 자리(묶음)를 찾아 그 길로 들어가는 **입구**다 — 안전 검사(멈추는 조건 · 계획에 묶인 확인)는 그 길의 것 그대로.
- 표 메뉴 「프로젝트 구성에 맞추기…」: 그 표에 든 구분 기준 자리(행 묶음 · 열 묶음 — 지금 수 → 구성의 수)를 보이고, 자리마다 기존의 계획 보기 · 「반영」 으로 간다. 그 표에 자리가 없으면 「이 표에는 프로젝트 구성으로 늘리고 줄일 자리가 없습니다」, 프로젝트 구성 값이 없으면 「프로젝트 구성을 먼저 정하세요」, 일반 문서에서는 항목이 안 보인다.
- 에이전트 판단(사용자 확인 전): 표마다의 새 반영 끝점을 만들지 않고 기존 자리별 반영의 입구로 둔 것(자리가 여럿인 표는 자리마다 차례로).
- **구현하며 드러난 것**(2026-11-19): 화면에는 「자리별 반영」 이 없었다 — `only` 는 서버 끝점에만 있고 화면의 계획은 늘 문서 전체(+ 「빼기」)였다. 그래서 이 입구가 그 길을 **처음** 쓴다. 그 길에서 둘을 고쳤다:
  ⓐ 한 자리만의 계획에서 손대지 않은 다른 자리가 「미해결 — 반영 뒤에도 수가 맞지 않음」 으로 나오던 것(견본 양식: 미해결 85) → 「제외 — 이번엔 한 자리만 반영」(`division_plan.make` — 모의 실행이 손댄 묶음 · 오류가 있는 묶음은 그대로)
  ⓑ 한 자리만 반영해도 `applied`(문서 전체를 그 값으로 반영함)를 적던 것 → **적지 않는다**(`server.divisions_apply` — TASK 의 「프로젝트 구성 반영」 단계가 끝남으로 보이고 다음 전체 계획이 자리표시를 다시 안 본뜨던 것: 견본에서 다른 표의 후보 10곳이 달라졌다).
  「빼기」(`skip`)로 일부를 뺀 계획의 반영은 전처럼 `applied` 를 적는다(기존 동작 — ④).
  화면: 표 메뉴의 하위 목록(「빈 필드 제거하기 ▸」 와 같은 꼴 — 자리마다 「기관 행 — 지금 2개 → 프로젝트 구성 3개」)에서 자리를 고르면 `divPlan({only, table})` → 기존 2열 「프로젝트 구성 — 바꿀 자리」(그 표의 자리로 좁혀 보임 · 「표 <id> 의 자리만」 단추로 오감) → 패널 「반영」.
  읽기 전용 값 하나를 더함: `GET …/divisions/members?targets=1` → `targets: {묶음 key: {target, done, reason, why}}`(프로젝트 구성 값이 없으면 None — 안 청하면 응답은 전과 같다).
  에이전트 · 대시보드는 표 하나만의 계획을 TASK 의 계획으로 보지 않는다(`doc_agent_work.js` `agwTaskPlan` — 그 계획으로 「문서에 반영」 카드를 내지 않는다) · 「한 번에 진행」 은 그런 계획을 이어 쓰지 않고 문서 전체로 다시 계획한다(`divRunAll`).
- **한 자리만 반영한 기록**(2026-11-19 astra 4차 — `applied` 를 안 적으니 ⓐ 전체 반영이 없던 문서에서 한 표만 맞추고 기관의 차례를 바꿔도 차례 검사가 그냥 지나가 값의 소속이 바뀌고 ⓑ 전체 A 반영 → 한 표만 B 반영 → 설정을 A 로 되돌리면 「프로젝트 구성 반영」 이 끝난 것으로 보였다):
  한 자리 반영은 문서 전체의 `applied` 와 **따로** `division.partial: [{values, only, rev, at, planId}]`(마지막 20개 — 같은 자리는 마지막 것만)에 적는다. 전체 반영이 끝나면 지운다(문서가 다시 한 값으로 맞았다). 실행 취소 · 작업 저장 · 확정 · 「지금 문서로 새 작업」 에 `applied` 와 같이 다닌다. `GET …/divisions` 응답에 `partial`.
  ⓐ 기관의 차례 검사(`divOrgsMoved` — 「한 번에 진행」 류가 멈추는 조건)는 마지막 전체 반영뿐 아니라 **한 자리 반영 때의 차례**와도 견준다 ⓑ 전체 반영 뒤에 **다른 값으로** 한 자리만 반영한 문서는 「프로젝트 구성 반영」 을 끝남으로 세지 않는다(`agwFitApplied` — 문서가 더는 그 값 그대로가 아니다: 다시 계획하면 그 자리를 되돌릴 계획이 나온다).

### 10. 양식의 표 판정

정해진 양식(사업계획서 · 연차보고서 …)은 표가 문서마다 같다 — **사람이 한 번 확정한 표 판정**을 양식에 저장해 두고, 구조가 꼭 같은 표를 만나면 내용으로 다시 어림하지 않고 그것을 쓴다(값을 채워도 칸 역할 · 키가 안 흔들린다).
사용자 2026-11-19 "사업계획서나 연차보고서 같은 경우는 형식이 동일 하니깐 테이블 정보를 가지고 있어도 좋을거 같긴한데" → (astra 3차 뒤 「사람이 표 타입마다 한 번 확정하는 절차를 넣어도 될까요」 에) "astra 해주고, 넣어줘". 방식은 astra 3차 합의(④ 「양식의 표 정보」) — 저절로 배워서 저절로 쓰지 않는다.

- **양식**: 「양식 정보」 의 양식(`heading_forms.for_session(sess)` 의 `key` — 사람이 고름 → 올린 원본의 sha256 → 파일 이름 꼴). 양식이 정해지지 않은 문서에는 이 기능이 없다(응답 `form: null` · 화면에 안 보임). 구분 기준 엔진의 양식 판정(`PROFILE.form_of`)은 쓰지 않는다(설명 문서도 양식으로 읽는다).
- **확정본**(양식마다 여럿 — 타입마다 하나로 덮지 않는다): `{id, form: 양식 키, type: 표 타입(§7 `type_key`), name: 보일 이름(머리글), geometry: [[행, 열, 행 병합, 열 병합, 음영 0|1]…](모든 칸 · 정렬), roles: [[행, 열, 역할]…](**모든 칸**), bands: [{id, rows, cols, kind, headerRows, headerCols}…],
  labels: [[행, 열, 견줄 글, 가변 0|1]…](헤더 · 제목 · 안내 역할의 칸 — 고정 머리글), from: {work, table, rev, source}(확정할 때의 작업 · 표 · 문서 차례 · 그때 판정의 출처), rev: 판(고칠 때마다 +1), at}`. **칸의 값은 저장하지 않는다** — 자리 · 역할 · 머리글뿐.
  견줄 글 = 공백을 뺀 글. **가변 머리글**(문서마다 달라도 되는 머리 칸 — 기관 이름 · 연도 · 차수)은 `가변 1` 로 두고 견주지 않는다: 확정할 때 구분 기준의 값 머리(`basisKind == "value"`)는 저절로 가변으로 두고, 사람이 확정 화면에서 더하거나 뺄 수 있다.
- **맞는 확정본**(`table_types.match(entries, tb)` — 순수): 같은 양식의 확정본 가운데(타입으로 거르지 않는다 — 아래 「구현하며 바뀐 것」 ⓐ) ① `geometry` 가 꼭 같고(모든 칸의 자리 · 병합 · 음영 — 행 수 포함) ② 가변이 아닌 `labels` 의 글이 모두 같은 것. **하나만** 맞을 때 그것, 둘 이상이면 쓰지 않는다(`ambiguous`). 행이 늘어난 표 · 병합이 다른 표 · 머리글이 바뀐 표는 안 맞는다 — 그때는 지금처럼(§2).
  - **더 좁은 확정본이 먼저**(2026-11-19 astra 4차 — 격자 · 음영 · 머리행이 같은데 한 표에서는 값 칸인 자리가 다른 표에서는 고정 행머리인 두 표: 첫 표만 확정하면 둘째 표의 그 행머리가 값 칸으로 바뀌어 읽혔다): 맞는 확정본이 둘 이상일 때, 그 가운데 하나의 **고정 머리글 칸**(가변이 아닌 `labels` 의 자리)이 다른 모든 것의 고정 머리글 칸을 **다 품고 더 많으면** 그것을 쓴다
    (둘째 표를 따로 확정하면 그 확정본에는 그 행머리의 글이 고정 머리글로 더 있다 → 그 글이 있는 표는 둘째 확정본, 그 자리에 다른 값이 든 표는 첫 확정본). 서로 품지 않으면 전처럼 쓰지 않는다(`ambiguous`).
  - **확정할 때 같이 쓰이는 표를 보인다**: `GET …/type` · 확정 응답에 `also: [{table, differs: n}]` — 이 문서에서 이 확정본이 맞아 쓰이는 **다른 표**와, 그 표의 지금 판정(초안 · 3단계 — 확정본 없이 낸 것)이 확정본과 다른 칸 수.
    화면: 「이 문서의 다른 표 2개에도 이 판정이 쓰입니다 — t45: 지금 판정과 2칸 다름(확인)」 — 표 번호를 누르면 그 표의 판정 화면으로. 다른 칸이 있는 표는 사람이 보고, 그 표의 판정이 따로여야 하면 그 표에서 헤더 지정으로 고친 뒤 **「이 표만 따로 확정」** 한다.
  - **고치기와 따로 확정**: 그 표에 지금 맞아 쓰이는 확정본이 있는데 지금 판정이 그것과 다르면 사람이 고른다 — 「이 확정본 고치기」(그 확정본이 맞는 모든 표의 판정이 바뀐다 — 이 문서에서 몇 표인지 보인다) | 「이 표만 따로 확정」(새 확정본 — 고정 머리글이 달라 구조 열쇠가 다를 때만 고를 수 있다: 같으면 둘 다 맞아 어느 쪽도 안 쓰이게 된다). `PUT …/type {…, mode: "update" | "new"}` — 맞는 확정본이 없으면 `mode` 는 필요 없다.
    구현하며 좁힌 것: 「이 표만 따로 확정」 은 구조 열쇠가 다른 것만으로는 모자라다 — 새 판정이 **지금 확정본의 고정 머리글 칸을 다 품고, 글이 있는 고정 머리글 칸이 더 있을 때만** 고를 수 있다(`table_types.separable`: 더 좁지 않으면 따로 확정해도 이 표에 옛 확정본이 쓰이거나 어느 쪽도 안 쓰이고, 더 있는 칸이 빈 칸뿐이면 그 자리가 빈 다른 표까지 새 확정본으로 읽힌다).
    골라야 하는데 `mode` 가 없으면 409 · 판정이 확정본과 같으면 전처럼 다시 확정(rev +1 — 이때 `new` 는 409) · 응답에 `choose {needed, canNew, why}`. `also` 는 확정본이 맞을 때만 나온다(확정 전에는 빈 목록 — 확정 응답에서 처음 보인다).
- **쓰는 차례**(`table_manager.judge(..., template=맞는 확정본)`): 그 작업의 유효한 헤더 지정 > **확정본** > 그 문서의 3단계 결과(입력이 같을 때) > 스크립트 초안. 확정본이 있으면 모든 칸의 자동 역할 · 띠를 확정본에서(자리로) 가져오고 `source: "template"` · `template: {id, rev}` 를 싣는다. 헤더 경로 · 표 의미 · 수식은 그 뒤에 지금 글로 다시 계산(§2 와 같다).
  확정본의 역할은 **그 작업의 헤더 지정과 따로 선 층**이다 — 칸의 `user` 는 그 작업에서 사람이 지정한 칸에만 붙는다(빈 필드 제거의 작성 글 보호가 양식의 확정으로 풀리지 않게).
- **확정**(`PUT …/tables/{tid}/type`): 지금 그 표의 판정(헤더 지정 · 3단계 결과 · 초안을 합친 것) **전체**를 사람이 화면에서 보고 확정한다 — 몇 칸의 헤더 지정만으로 저절로 확정되지 않는다. 보류된 헤더 지정이 있으면 확정하지 못한다(409). 같은 구조의 확정본이 이미 있으면 그것을 고친다(`rev` +1).
- **끝점**(`app/table_types_api.py` — 저장 · 견주기는 `app/table_types.py` 순수 · 저장 파일은 헤딩 저장소 폴더의 `table_types.json`):
  `GET /api/docs/{id}/tables/{tid}/type` → `{form: {key, name} | null, type, name, match: {id, rev, at} | null, state: "confirmed"|"none"|"ambiguous"|"changed"(같은 타입의 확정본은 있으나 구조 · 머리글이 달라 안 맞음), differs: [{cell, ref, now, template}](지금 초안 · 3단계 판정이 확정본과 다른 칸), judgment: {표 · 칸마다 역할 · 출처}(확정 화면이 그릴 것), variants: [같은 타입의 확정본 요약…], rev}` ·
  `PUT /api/docs/{id}/tables/{tid}/type {variable?: [칸 id…](가변 머리글), rev}` → 확정(문서는 안 바뀜) · `DELETE /api/table-types/{entry}` · `GET /api/table-types?form=` → 그 양식의 확정본 목록 · `GET /api/docs/{id}/tables/types` → 문서의 표마다 `{table, type, state}`(「테이블」 탭의 표지용).
  `table_types_api.template_for(s, tb)` → 맞는 확정본(`judge` 의 `template` 꼴) | None — 다른 끝점 모듈이 부른다(세션 잠금 안에서 불러도 된다 — 파일 읽기뿐).
- **이 걸음에서 확정본을 쓰는 곳**: 표 서식 점검(`tables_api._style_tb`) · 키-값 추출과 매핑(`table_kv_api` — 넣기는 짝마다 `sig` 로 묶여 있다). 표 서식 점검의 항목 `sig` 에는 판정의 출처 · 확정본의 판도 든다(확정본이 바뀌면 달라지게).
  **빈 필드 제거 · 엑셀화는 아직 잇지 않는다**(지우기의 미리보기–적용을 판정의 판에 묶은 뒤 — ④).

### 11. 표 · 띠 정체 — 소속 헤딩으로 저절로 · LLM 판정 · 사람은 지침

2026-11-22 사용자 확정(①): **id 는 소속 헤딩으로 저절로 · 판정은 LLM · 사람은 지침만**. 아래 세부는 에이전트 판단(사용자 확인 전) — 아직 구현 전이다(③).

- **양식의 표 목록**(양식마다 · 스크립트가 짓는다): 등록된 빈 양식(연구개발계획서 = `samples/연구개발계획서_양식.hwpx` · 연차보고서 = KEIT 서식 — 양식 정보에 그 파일을 건다)의 헤딩 · 표 분석에서
  표마다 **양식 표 id = 양식 열쇠 + 소속 헤딩 사슬(양식의 고정 헤딩 — 「※」 안내 · 대괄호 안의 기관 이름 · 빈칸을 뺀 글) + 같은 소속 아래 차례**, 띠마다 **띠 id = 양식 표 id + 자리 차례(A, B …)**.
  사람이 확정하지 않는다 — 빈 양식이 바뀌면 다시 짓는다(같은 사슬 · 차례면 같은 id). 칸 안의 표 = 바깥 표 id + 「›칸표」 + 차례. 값은 안 둔다.
- **문서의 표를 목록에 잇기**(작업마다): ⓐ 스크립트 — 그 문서의 소속 헤딩 사슬을 **양식의 고정 헤딩만 남겨**(작성 글의 줄 「o …」 · 「▪ …」 은 사슬에서 뺀다) 목록의 사슬과 견주고, 같은 소속 아래는 차례 + 머리글(표 타입)로 짝짓는다 —
  하나로 정해지면 잇는다. ⓑ **LLM** — 못 정한 표(사슬이 안 맞음 · 같은 소속 아래 후보 여럿 · 표가 빠지거나 더해짐 · 기관 · 차년도 되풀이)는 목록의 후보(id · 사슬 · 머리글 · 띠)와 그 문서 표의 격자 · 앞 글 · 소속을 보고 고른다(없으면 「양식에 없는 표」).
  LLM 은 목록의 id 가운데서만 고른다(새 id 를 짓지 않는다). 되풀이(기관마다 · 차년도마다)는 같은 양식 표 id + 그 자리의 편집 구역(기관 · 차년도)으로 가른다.
- **사람은 지침만**: 판단 기준은 일반 지침(`heading_guides_default/tables.md`) · 양식 정보의 「## 표」 절(구조 · 정체) · 「자리 연결」 절(이관 — 매칭 지침)에 사람이 적고, LLM 이 그 글을 읽는다. 잇기 결과를 사람이 고치는 칸은 두지 않는다.
- **기록과 다시 쓰기**: 잇기 결과(문서 표 id → 양식 표 id · 띠 id · 근거 · 스크립트|LLM)는 작업에 저장하고 3단계 결과 · 「테이블」 탭 · 병합 방식에 같이 보인다. 다음 작업은 같은 양식 표 id 로 그 표의 지침과 지난 판정을 찾는다.
- 지금 있는 「양식의 표 판정」(§10 — 사람이 확정한 격자의 칸 역할)은 그대로 둔다(없애지 않는다 — 이 절과 이어 쓰는 것은 ④).
- 차례: ① 빈 양식에서 목록 짓기 + 문서 잇기의 스크립트 몫(잰 것으로 얼마나 정해지나 보고) → ② LLM 잇기(새 에이전트 — `agents.AGENTS` 등록) → ③ 3단계 결과 · 병합 방식 · 「테이블」 탭에 id 보이기 → ④ 이관 · 취합 · 표 판정 LLM 이 id 로 지침 · 지난 판정을 읽기(옛 계획과 견준 뒤).

  ⓓ 사람이 **채워진 값 칸을 헤더로 지정**하고 확정하면 그 글이 고정 머리글로 저장 파일에 들어간다(가변으로 두면 안 들어간다 — 「값은 저장하지 않는다」 는 필드 · 간격 칸에만 성립) ⓔ 빈 필드 제거 · 엑셀화에 잇기(지우기의 미리보기–적용을 판정의 판에 묶은 뒤) ⓕ 행이 늘어나는 목록형 표.
