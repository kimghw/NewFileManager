## ① 질의·요청 히스토리

- 2026-11-16 사용자: "hwpx shared 기능을 추가할게 다른 것들과 의존성을 줄여주길 바래. sharedpoint 에 공유폴더를 놓고 거기에 링크를 받은 사용자와 같이 글을 작성할 수 있게 해줘.
  링크랑 키?를 받은 사용자만 접속해서 할 수 있게 해줘."
- 같은 날 물어서 받은 답 셋:
  - 접속 방식 = **「브라우저로 링크 접속」** — 받은 사람은 설치 없이 링크를 브라우저로 연다. 이 PC 의 서버가 문서를 잡고 모두가 거기에 쓴다. 공유 전용 포트만 열고 8114 는 그대로 닫아 둔다. 문서 파일은 SharePoint 공유폴더에 저장.
  - 폴더 연결 = **「동기화된 폴더 경로」** — SharePoint 폴더를 OneDrive 로 이 PC 에 동기화해 두고 앱은 그 폴더 경로만 안다(Graph API·Azure 인증에 기대지 않는다).
  - 손님 권한 = **「글 쓰기만」** — 문단 글 고치기 · 줄 나누기/합치기까지. 서식 · 표 구조 · LLM · TASK 실행 · 작업 삭제는 주인만.
- 같은 날 문서 갱신 검토(사용자 답 「검토한다」 — 세션 에이전트, 읽기만): 35항목 → 코드 결함은 고치고(③) 나머지는 이 문서에 적음.

## ② 확정 사양

### 0. 말

- **공유**: 문서 하나를 링크와 키를 받은 사람과 같이 쓰게 여는 것. 문서(작업) 하나에 켜진 공유는 하나. 주인이 화면을 닫아도 공유는 이어진다(서버가 잡고 있다) — 끄기 전까지.
- **주인**: 공유를 켠 사람 — 이 PC 의 8114 화면을 쓰는 사람. **손님**: 링크와 키로 들어온 사람.
- **링크**: 손님이 브라우저로 여는 주소 `<접속 주소>/s/<공유 id>`. 비밀이 아니다 — 손님 화면에서는 키 없이 문서 이름도 안 보인다.
- **키**: 12자(`XXXX-XXXX-XXXX` — 헷갈리는 I·O·0·1 없음). 서버에는 해시만 남는다. 서버는 켠 직후·새로 만든 직후의 응답에만 키를 싣고, 주인 화면은 그 화면을 새로 고치기 전까지 쥐고 보인다 — 잊으면 「키 새로 만들기」.
- **공유폴더**: 주인이 고른 폴더(SharePoint 폴더를 OneDrive 로 동기화한 이 PC 의 경로). 문서의 저장본과 링크 바로가기가 놓인다.
- **키가 막는 것은 「들어와서 쓰기」 다**: 공유폴더의 저장본(글 전체)과 바로가기 이름은 **그 폴더를 볼 수 있는 사람이면 키 없이 읽는다** — 읽기는 SharePoint 폴더 권한이 정한다. 읽히면 안 되는 사람이 있는 폴더를 공유폴더로 고르지 않는다.
- **작성 중**: 누가 지금 커서를 두고 쓰는 문단. 그 문단은 그 사람만 고친다(§5).

### 1. 구성 — 다른 모듈과의 접점

공유는 모듈 하나로 따로 선다. 다른 코드가 공유를 부르지 않고, 공유가 기대는 것은 아래 접점뿐이다.

| 파일 | 일 | 기대는 것 |
|---|---|---|
| `app/share.py` | 공유 기록 · 키 · 손님 세션 · 작성 중 · 변경 알림(순수 로직 — 웹·문서 객체를 모름) | 표준 라이브러리 |
| `app/share_api.py` | 주인 끝점(8114) · 손님 앱(공유 포트) · 공유폴더 저장 · 공유 포트 띄우기 | `share.py` + `attach()` 로 받은 것 |
| `app/static/share/` | 손님 화면(`guest.html`·`guest.js`·`guest.css`) — 제 그리기 · 제 편집 | 블록 JSON 의 모양(`HwpxDoc.blocks()`) |
| `app/static/share.js`·`share.css` | 주인 화면의 「공유」 단추 · 떠 있는 창 · 남의 변경 반영 | `app.js` 의 이름들 — **목록의 원본은 `share.js` 머리의 주석**(`state`·`api`·`paraEl`·`applyServer`·`applyEditState`·`applyTops`·`applyDoc`·`flushAll` …) |

- `app/server.py` 의 접점은 두 곳: ① `_bump` 가 편집 한 번마다 `BUMPED` 의 함수들을 부른다(세션 잠금 안 · 차례 순) ② `share_api.attach(app, …)` 한 번 — 넘기는 것은
  세션 얻기(`session=_sess`) · 메모리에 있는 세션(`loaded=DOCS.get`) · 보이는 이름(`name=_shown_of`) · 끝점 함수 `doc=get_doc`·`patch=patch_block`·`split`·`merge`·`media` ·
  `bumped=BUMPED` · 작업 저장소 뿌리(`store=works.root`) · 작업이 아직 있는가(`exists` = 작업 폴더가 있는가). 공유 모듈은 `app.server` 를 import 하지 않는다.
- 손님 화면은 `app.js` 를 읽지 않는다. 손님 앱은 `/static` 을 통째로 내지 않고 `app/static/share/` 만 낸다.
- 공유를 끄는 법: env `NFM_SHARES=off`. 작업 저장이 꺼져 있어도(`NFM_WORKS=off`) 공유는 꺼진다(`NFM_SHARES` 가 파일 경로여도 — 공유할 작업이 없다).
  꺼져 있으면 바꾸는 주인 끝점은 503 · `GET …/share` 는 200 `{available: false}`(단추 안 보임) · `GET …/share/changes` 는 200 `{active: false}`.

### 2. 공유 기록 · 키

- 파일 `shares.json` = 작업 저장소 폴더의 옆(`%LOCALAPPDATA%\NewFileManager\shares.json` — 임시 작업 폴더로 띄운 검사 서버는 제 임시 폴더의 것) · env `NFM_SHARES` 가 파일 경로면 그것.
  `{version, url, shares{공유 id: {id, doc, name, host, folder, file, link_file, salt, key(해시), created, active, stopped, saved{rev, at, sha, error, conflict}}}}`.
- 공유 id = 무작위 16자(16진). 키 = 무작위 12자(32글자 알파벳 — 60비트), 저장은 scrypt(소금 16바이트) 해시뿐.
- **키 넣기 제한**: 같은 주소에서 5번 틀리면 60초 잠금(틀릴 때마다 두 배 · 최대 1시간) · 공유 하나에 10분 동안 50번 틀리면 10분 잠금. 맞으면 그 주소의 횟수는 지운다. 잠긴 동안에는 맞는 키도 안 받는다.
  - **주소** = 접속한 쪽 주소. 이 PC 안에서 온 요청(터널이 넘긴 것)이면 터널이 적어 준 `CF-Connecting-IP` → `X-Forwarded-For` 첫 값. 터널이 안 적어 주면 **주소를 모르는 것**으로 치고 주소별 잠금은 세지 않는다
    (공유 하나의 상한만 — 한 사람이 틀린 것으로 터널 뒤의 모두를 잠그지 않게). 밖에서 직접 온 요청의 그 머리말은 믿지 않는다.
- 「키 새로 만들기」 = 새 키 + 들어와 있던 손님 모두 내보냄(다시 키를 넣어야 한다). 손님이 없어도 이미 보낸 키는 못 쓰게 된다 — 늘 확인을 거친다.
- 공유 끄기 = 손님 모두 내보냄 · 마지막 저장(폴더의 파일이 밖에서 바뀌었으면 안 쓴다 — §8) · 링크 바로가기 지움(우리가 쓴 것일 때만) · 저장본은 폴더에 남긴다. 켜진 공유가 없으면 **4초 뒤에** 공유 포트를 닫는다 —
  그 사이 손님 화면이 「공유가 끝났습니다」 를 받는다(바로 닫으면 손님에게는 「연결 끊김」 으로만 보인다). 그 사이 다시 켜면 닫지 않는다.
- **작업을 지운 문서의 공유는 저절로 걷는다**(서버를 켤 때 · 공유가 켜져 있는 동안 15초마다) — 판정 = 그 작업의 **폴더가 없음**(작업 정보를 잠깐 못 읽은 것으로는 걷지 않는다). 끄기와 같은 일을 한다(마지막 저장만 빼고).
- 서버를 다시 켜면 켜져 있던 공유는 이어진다(공유 포트를 다시 연다 · 키는 그대로) — 손님은 키를 다시 넣는다(손님 세션은 메모리에만 있다). 그때 공유 포트를 못 열었으면 15초마다 다시 열어 본다.
- 작업 기록(`log.jsonl`)에는 누가 고쳤는지 남지 않는다 — 손님의 편집도 주인의 편집과 같은 줄이다.

### 3. 손님 접속 — 공유 포트

- 공유 포트 = **8119**(env `NFM_SHARE_PORT`) · 듣는 주소 `0.0.0.0`(env `NFM_SHARE_HOST`). 8114 서버 **프로세스 안**에서 켜진 공유가 있을 때만 연다(서버를 켤 때 켜진 공유가 있으면 그때 · 공유를 켤 때).
  8114 는 전처럼 `127.0.0.1` 만 듣는다 — 손님은 8114 의 어떤 끝점에도 닿지 못한다.
- **접속 주소**(링크의 앞부분) = 주인이 정한 주소(`shares.json` 의 `url` — 터널 주소 `https://…` 등) → env `NFM_SHARE_URL` → 없으면 `http://<이 PC 의 사내망 주소>:8119`.
  접속 주소는 **모든 공유가 같이 쓴다** — 한 문서의 창에서 고치면 켜져 있는 다른 공유의 링크(와 링크 바로가기)도 같이 바뀐다.
- 손님 앱의 끝점은 아래가 전부다(문서 끝점은 키로 들어온 손님만 · 그 공유의 문서만):

| 끝점 | 일 |
|---|---|
| `GET /s/{sid}` | 손님 화면(키 넣기 → 문서) |
| `GET /s/{sid}/info` | `{active, joined}` — 키 없이는 문서 이름도 안 준다 |
| `POST /s/{sid}/join {key, name}` | 키 확인 → 손님 세션 쿠키. 400 이름 없음 · 403 키 틀림 · 429 잠금(`wait` 초) · 409 자리 없음(동시 12명) |
| `POST /s/{sid}/leave` | 나감 |
| `GET /s/{sid}/doc` | `{name, host, rev, epoch, blocks, me, people}` — 블록은 손님 화면이 쓰는 키만(`slim`) |
| `GET /s/{sid}/changes?since&epoch&block` | 남의 변경 + 사람들(§4·§5) — 1.2초마다(가려진 탭은 5초) |
| `PATCH /s/{sid}/blocks/{id} {text}` | 문단 글 고침 |
| `POST /s/{sid}/split {id, offset}` · `POST /s/{sid}/merge {id, dir}` | 줄 나누기 · 합치기 — 422 = 표준에 어긋나 되돌림(까닭 글만 준다 · 8114 의 판정 전체는 넘기지 않는다) |
| `GET /s/{sid}/media?name` | 그 문서 hwpx 안의 그림 파일(png·jpg·gif·bmp·svg·webp) |
| `GET /share-static/*` | 손님 화면의 JS·CSS |

- **상태 코드의 뜻(손님 화면이 갈라 쓴다)**: 401 = 세션 없음 → 키 넣기 · **410 = 공유가 끝났거나 없는 링크 · 문서(작업)가 없어짐** → 「공유가 끝났습니다」 · **404 = 그 문단·그림이 없음** → (쓰던 문단이면) 문서를 다시 읽는다 ·
  409 = 남이 작성 중 · 400 = 요청이 틀림(`X-Share` 없음 포함) · 413 = 본문이 256 KB 를 넘거나 `Content-Length` 없음.
- 손님 세션 = 쿠키 `nfms_<sid>`(HttpOnly · SameSite=Strict · 경로 `/s/<sid>` · https 면 Secure). 쿠키 수명은 **들어온 때부터 12시간**이고, 서버는 12시간 소식이 없던 세션을 끝낸다. 서버 메모리에만 있다 — 서버를 다시 켜면 키를 다시 넣는다.
- 바꾸는 요청(PATCH·POST)은 머리말 `X-Share: 1` 이 있어야 한다(다른 사이트가 쿠키로 보내는 요청 막기). 요청 본문 256 KB · 문단 글 20,000자 상한.
- 응답 머리말(모든 응답): `X-Content-Type-Options: nosniff` · `Referrer-Policy: no-referrer` · `X-Frame-Options: DENY` · `Cache-Control: no-store`(따로 준 것이 없으면) · `Server` 머리말 없음 ·
  CSP — 화면은 `default-src 'self'; script-src 'self'; style-src 'self'; …`, 그 밖의 응답은 `default-src 'none'; frame-ancestors 'none'; sandbox`. API 문서(`/docs`·`/openapi.json`)는 없다.
- 손님이 못 하는 것(끝점이 없다): 서식 · 표 행/열 · 실행 취소 · 내려받기 · LLM · TASK · 작업 목록 · 다른 문서.

### 4. 변경 알림 — 누가 무엇을 고쳤나

- 서버가 문서 하나의 편집을 **차례(rev) 순**으로 적어 둔다(`share.Feed` — 공유가 켜져 있고 누가 읽기 시작한 문서만): `_bump` 가 잠금 안에서 부르므로 빠짐·뒤바뀜이 없다.
  - 글 고침(`text` · 모양 없는 `revert`) = `{rev, by, t: "text", id, text}` — 그 자리에서 다 찬다.
  - 그 밖(나누기·합치기·서식·표·실행 취소·내용 반영 …) = 자리만 잡아 두고(`wait`), 그 편집의 **응답**(`tops` = 바뀐 최상위 블록 `{drop, blocks}` · `rev`)이 오면 채운다 —
    주인의 편집은 8114 앱의 미들웨어가 응답을 읽어서(`/api/docs/<id>/…` 의 200 JSON 응답만 · 4 MB 까지), 손님의 편집은 손님 앱이 받은 결과로.
    1.5초 안에 안 채워지면 「다시 읽기」 가 된다 — 실행 취소처럼 `tops` 가 없는 응답 · 쪽 설정이 바뀐 편집(`paged`) · 다시 보낸 답(`replayed`) · 4 MB 넘는 응답 · 한 요청이 `_bump` 를 여러 번 지난 편집.
- 읽기 `changes?since=<내가 아는 rev>&epoch=<알림 묶음>` → `{epoch, rev, items[…], people[…], denied?}` 또는 `{reload: true}`.
  - 내 편집(`by` = 나)은 건너뛴다(제 응답으로 이미 반영했다). 아직 안 채워진 자리 앞에서 멈춘다(다음 읽기에 이어서).
  - `reload` = 「문서를 다시 읽어라」: 내가 아는 rev 가 적어 둔 것보다 옛것 · 묶음(epoch)이 바뀜(서버 다시 켬 · 차례가 뒤로 감) · 「다시 읽기」 자리를 지남.
  - 적어 두는 양: 200개를 넘지 않게, 3분이 지난 것은 지운다(다음 편집이 올 때 정리).
  - `epoch` 를 비워 보내면 「방금 문서를 읽었다」 는 뜻이다 — `since` 만 본다(화면을 처음 열 때 문서를 한 번 더 읽지 않게).
- **차례 어긋남은 서버가 가린다**(`Feed.read` — 항목마다 그 편집이 닿은 문단·블록 id 를 적어 둔다): 남의 편집이 **그 뒤 차례의 내 편집**과 같은 문단에 닿으면 —
  글 고침은 보내지 않고(내 글이 더 새것), 블록 바꿔 끼우기(`tops`)는 `reload`(옛 블록이 내 새 글을 덮지 않게). 내 편집이 어디에 닿았는지 아직 모르면(응답 전) 기다리고,
  끝내 모르면(내 실행 취소 등) 그 앞의 남의 편집을 얹지 않고 `reload`.
- 화면은 **아직 못 보낸 내 글**만 본다: 남의 `tops` 가 그 문단을 품고 있으면 먼저 내 글을 보낸 뒤 문서를 다시 읽고, 남의 글 고침이 내가 치는 중인 문단이면 버린다.
- 남이 글만 고친 문단은 화면에서 글자 모양이 한 가지로 보인다(문단 안 굵은 글씨 등 — 저장되는 문서에는 그대로 있다. 문서를 다시 읽으면 맞는다).

### 5. 작성 중 — 한 문단은 한 사람

- 화면은 `changes` 를 부를 때마다 지금 커서를 둔 문단(`block`)을 알린다. 먼저 잡은 사람이 **작성 중**이다.
- 풀리는 때: 커서를 다른 곳으로 옮김 · **커서만 두고 60초 동안 아무것도 안 함**(치거나 누르면 다시 잡는다 — 자리를 비운 사람이 문단을 붙잡고 있지 않게) · 탭을 닫거나 끊겨 8초 동안 읽기가 없음.
- 남이 작성 중인 문단은 화면에서 못 고친다(그 사람 색 띠 + 이름) — 늦게 잡으려 한 쪽은 응답의 `denied` 로 알고 커서를 뺀다.
- 손님의 글 고침·나누기·합치기는 서버도 본다 — 남이 작성 중인 문단이면 409(손님 화면은 방금 친 글을 걷고 서버의 글로 되돌린다). 같은 문단에 두 글이 닿으면 합치지 않는다 — 문단 통째로 뒤에 닿은 쪽이 남는다.
- **주인의 편집은 화면만 막는다**(주인은 8114 로 고친다 — 그 길에는 공유가 끼어들지 않는다): 주인의 서식 · 표 편집 · 내용 반영 · 실행 취소는 손님이 작성 중인 문단에도 들어간다.
- 사람들 = `people[{id, name, color, block, host}]` — 20초 안에 소식이 있던 사람. 색은 들어온 차례로 8색.

### 6. 손님 화면

- 종이 한 장 폭(첫 구역의 쪽 폭·여백)의 **이어진 글**로 그린다 — 쪽 나눔 · PDF 견줌 · 글꼴 내려받기는 없다(주인 화면의 몫). 문단 글꼴 크기·굵게·정렬·줄 간격·들여쓰기·글머리·줄 나눔 규칙, 표(병합·열 폭·괘선·음영), 그림.
- 편집: 문단을 눌러 쓴다 — 0.45초 뒤 서버에 반영 · Enter = 줄 나누기 · 맨 앞 Backspace / 맨 끝 Delete = 합치기(바로 옆이 문단이고 남이 작성 중이 아닐 때) · Shift+Enter = 줄 바꿈 · Tab = 탭 글자 · 붙여넣기는 글만.
  한글 조합 중의 Enter 는 조합만 확정한다(주인 화면과 같은 법 — 한글 IME 가 조합이 끝난 뒤 Enter 를 한 번 더 보낸다).
- 상태: 「반영 중…」 · 「모두 반영됨」 · 「반영 실패 N개 — 눌러서 다시」(그 문단은 붉게 남는다) · 「연결 끊김 — 다시 잇는 중…」. 「나가기」 = 손님 세션을 끝내고 키 넣기로.
- **쓰던 문단이 없어지면**(남의 합치기 · 주인의 실행 취소 — 404): 알리고 문서를 다시 읽어 이어 간다. 그 문단에 못 보낸 글은 잃는다.
- **공유가 꺼지거나(410) 키가 바뀌면(401)**: 문서를 가리고 「공유가 끝났습니다」 / 키 넣기로 돌아간다. 그때 못 보낸 글은 잃는다.

### 7. 주인 화면

- 상단 바 「저장」 앞에 **「공유」** 단추(문서를 연 hwpx 작업일 때만). 켜져 있으면 「공유 중 · N명」. 좁은 폭에서는 줄인다(541~1100px = 꺼져 있으면 아이콘만 30px · 541~880px = 켜져 있어도 아이콘 + 손님 수 ·
  540px 아래는 상단 바가 두 줄로 꺾여 그대로) — 상단 바를 넘치게 하지 않는다.
- 누르면 떠 있는 창(모달 아님 · ✕/Esc/바깥 누름):
  - 꺼져 있을 때 — 공유폴더 경로 · 내 이름 · 「공유 켜기」. 이 PC 의 동기화 폴더를 한 줄로 알려 준다(넣은 경로는 켜기 전에 견주지 않는다).
  - 켜져 있을 때 — 링크(복사) · 키(복사 — §0) · 접속 주소 고치기 · 공유폴더(동기화 폴더가 아니면 알림 — 그래도 쓴다)와 저장 상태(「지금 저장」 · 밖에서 바뀌었으면 「덮어쓰기」) ·
    사람들(누르면 그 사람이 작성 중인 문단으로) · 「안내 글 복사」(문서 이름 + 링크 + 키를 한 글로) · 「키 새로 만들기」 · 「공유 끄기」.
- 공유 중이면 1.2초마다(가려진 탭은 약 5초) `GET /api/docs/{id}/share/changes` 로 손님의 변경을 받아 화면에 반영한다(글 = 그 문단 · 나누기/합치기 = 그 블록만 · 그 밖 = 문서 다시 읽기).
- 손님이 작성 중인 문단은 주인 화면에서도 못 고친다(색 띠 — 누르면 누가 쓰는지 알린다).
- **주인의 「실행 취소」 는 손님의 편집도 되돌린다**: 손님의 줄 나누기·합치기도 문서의 구조 편집이라 실행 취소 묶음에 쌓이고, 실행 취소는 마지막 구조·서식 편집 직전으로 문서를 통째로 되돌린다 —
  그 뒤 모두가 친 글도 함께 사라진다(손님 화면은 문서를 다시 읽어 맞춘다).
- 주인 끝점(8114): `GET|POST|PUT|DELETE /api/docs/{id}/share` · `POST …/share/key` · `POST …/share/save` · `GET …/share/changes`.

### 8. 공유폴더에 저장

- 공유를 켤 때 공유 포트를 먼저 열고(못 열면 503 — 폴더에 아무것도 남기지 않는다) 문서의 지금 저장본을 `<공유폴더>/<문서 이름>.hwpx` 로 쓴다 — **같은 이름의 파일이 이미 있으면 덮지 않고** ` (2)`, ` (3)` … 을 붙인 새 이름.
  단, 이 문서를 지난번에 같은 폴더로 공유했고 그때 우리가 쓴 저장본이 **그대로 있으면**(sha256 이 같음) 그 파일을 이어 쓴다 — 껐다 켤 때마다 번호가 늘지 않게. 밖에서 바뀌었으면 새 이름.
- 그 뒤로는 문서가 바뀌고 4초 동안 조용하면(계속 바뀌면 30초마다) 같은 파일에 다시 쓴다. 쓰기 = 같은 폴더의 `~$….tmp` 에 쓰고 바꿔 넣기
  (OneDrive 가 동기화하지 않는 이름이라고 문서에 적혀 있다 — 실측 아님: [references/SharePoint_공유폴더.md](../references/SharePoint_공유폴더.md) §2).
- **밖에서 바뀐 파일은 덮지 않는다**: 쓰기 전에 폴더의 파일이 우리가 마지막에 쓴 것과 다르면 멈추고 「공유폴더의 파일이 밖에서 바뀌었습니다」 — 주인이 「덮어쓰기」 를 눌러야 쓴다(끌 때의 마지막 저장도 안 쓴다 — 마지막 내용은 문서에만 있다).
  공유폴더의 hwpx 를 한글로 직접 고친 것은 같이 쓰는 문서에 **들어오지 않는다**(저장본은 내보내기 전용).
- **공유폴더가 사라지면**(이름 바꿈 · 동기화 해제): 저장 줄에 「공유폴더에 쓰지 못했습니다 …」 · 단추 주황 — 같이 쓰기는 이어지고, 몇 초마다 다시 써 본다(폴더가 돌아오면 이어 쓴다). 저장본만 지워졌으면 새로 쓴다.
- 링크 바로가기 `<저장본 이름> 같이 쓰기.url` 도 같은 폴더에 둔다(SharePoint 폴더 링크를 받은 사람이 거기서 손님 화면을 연다 — 키는 넣지 않는다). 접속 주소를 고치면 다시 쓴다. 지워진 바로가기는 접속 주소를 고칠 때 다시 생긴다.

## ④ 미결/후속

- **사내망 밖 접속**: 공유 포트를 터널(이 PC 의 포트를 인터넷 주소로 이어 주는 프로그램 — 예: Cloudflare Tunnel)로 내고 그 주소를 「접속 주소」 에 넣으면 된다 — 터널 설정은 이 앱 밖의 일(안 만듦).
  터널이 손님이 보낸 `X-Forwarded-For` 를 그대로 넘기는 제품이면 주소별 잠금을 피할 수 있다(공유 하나의 상한은 남는다 — 제품별로 확인하지 않았다).
- **Windows 방화벽**: 공유 포트를 처음 열 때 방화벽이 물을 수 있다(허용해야 다른 PC 에서 들어온다). 앱이 방화벽 규칙을 바꾸지는 않는다.
- **사내망의 http 는 평문이다**: 접속 주소가 `http://…` 이면 키와 글이 암호화 없이 오간다(같은 망에서 엿볼 수 있다) — 망 밖으로 낼 때는 https 터널 주소를 쓴다.
- **공유 하나의 잠금은 링크만 아는 사람도 걸 수 있다**(10분에 50번 틀리기 — 새로 들어오기만 막히고 들어와 있는 손님은 그대로).
- 실제 SharePoint 폴더·다른 PC 에서 아직 써 보지 않았다(검사는 이 PC 의 임시 폴더 · 127.0.0.1) — OneDrive 가 저장본을 올리는 것, 다른 PC 의 접속,
  SharePoint 가 올린 파일을 서버에서 고쳐 되돌려 주어 「밖에서 바뀜」 이 저절로 뜨는지([references/SharePoint_공유폴더.md](../references/SharePoint_공유폴더.md) §2)는 사용자가 확인.
- 손님 한 사람만 내보내기 · 공유 중 실행 취소 앞의 확인 창 · 기록에 누가 고쳤는지 남기기.
- 손님 화면의 쪽 보기 · 문서 글꼴(지금은 손님 PC 에 있는 글꼴로) · docx 공유 · 손님의 서식 편집.
- 주인이 같은 문서를 탭 둘에 열면 두 탭 사이에는 변경이 오가지 않는다(둘 다 「주인」 — 공유 전부터 그랬다).
- 손님의 줄 합치기가 닿는 **이웃 문단**의 작성 중은 화면만 본다(서버는 합칠 문단 하나만 본다) — 그 이웃을 쓰던 사람은 「쓰던 문단이 없어짐」(§6)을 겪는다.
