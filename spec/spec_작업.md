## ② 확정 사양

### 1. 작업이란

- **작업 = 올린 파일 하나의 작업 공간**: 파일을 올리거나 예제를 열면 작업이 하나 생긴다. 작업 id = 문서 id(`docId`) — 기존 `/api/docs/{id}/…` 가 그대로 작업 안의 일이다.
- **같은 파일은 이어 열기**(2026-11-10 사용자 확정): 이름·형식·올린 바이트(sha256)가 모두 같은 작업이 있으면 새로 만들지 않고 그중 가장 최근 것을 연다(메모리에 없으면 §3 다시 열기 —
  확정이 있으면 기준 확정 위의 편집 상태로). 올리기·예제 열기 모두. 이어 연 작업은 `updated` 를 올려 최근 작업 맨 위로, 기록에 `reupload`.
  응답 `{docId, name, size, reused, work?{created, updated, rev, edited, commits}}` — 화면은 알림 「같은 파일로 하던 작업을 이어서 엽니다 — … · **새 작업으로 열기**」(12 초).
  `?new=1`(`POST /api/docs?new=1`·`POST /api/samples/{name}?new=1`)이면 늘 새 작업. 이름이 다르면(바이트가 같아도) 다른 파일. 이어 열 작업을 못 열면(폴더 깨짐) 새 작업으로.
  작업 저장이 꺼져 있으면(`NFM_WORKS=off`) 늘 새 작업. 실서버(8114)를 쓰는 도구(`check_pages`·`measure_table_rows`·`screenshot_ui`)는 `?new=1` 로 연다 — 사용자의 편집본을 재거나 고치지 않게.
- 작업이 품는 것: 올린 원본(바이트 그대로) · 지금 편집 상태 · 검증 기록(실행마다) · 편집·내려받기 기록 · 검증하거나 내려받은 출력 파일.
- 서버를 다시 켜거나 메모리에서 비워져도(최근 8개) 작업 목록에서 다시 열면 같은 블록 id·고친 문단·되돌리기 기준(원본)·마지막 검증 결과로 이어진다.
  **실행 취소 기록은 남지 않는다**(다시 열면 비어 있음 — 묶음마다 저장 바이트 하나라 큼).
- **hwp 올리기**(2026-11-11 사용자 요청 — ① 같은 날): hwp(바이너리)를 올리면 서버가 **한글로 열어 HWPX 로 저장한 것**을 받아 hwpx 작업을 만든다 — 작업 이름은 `이름.hwpx`, 원본 hwp 는 작업에 남기지 않는다(변환본은 렌더 캐시 `{sha}.from-hwp.hwpx` — 같은 hwp 를 다시 올리면 같은 바이트라 이어 열린다).
  올리는 길은 모두 같다(상단 「열기」 · 작업 목록 「새 파일 올리기」 · 첨부 파일 칸의 폴더 단추 — `POST /api/docs`). 한글이 없는 PC(`pdf_render.available` 이 거짓)면 400 「한글이 있어야 …」, 변환 실패·시간 초과도 400(까닭 포함). 변환은 요청 스레드 밖에서 돈다(서버가 멈추지 않게).

### 2. 저장 폴더 (`app/works.py`)

- 폴더 `%LOCALAPPDATA%\NewFileManager\works\<작업 id>\`(env `NFM_WORKS`, `off`·`0` 이면 저장 끔 — 그때는 예전처럼 메모리만). 시험은 conftest 가 임시 폴더로.
- 꼴:
  - `work.json` — 목록용 요약 {id, name, format, size, sha256, source(upload|sample), created, updated, rev(편집 차례), edited(고친 문단 수), verify: {import·edit: {status, at, revision, outputSha}}}
  - `original.<ext>` — 올린 바이트(한 번 쓰고 안 바꿈)
  - `current.<ext>` — 지금 편집 상태의 저장 바이트(= 「저장」 으로 내려받을 파일) · `doc.pkl` — 어댑터 묶음의 나머지(고친 XML 부분 이름 `dirty`, 새 멤버 `new`/`blobs`, 블록 id 자리표 `ids`)
  - `state.json` — 세션 집합: texts · unrestored · formatted · struct · removed · origin · owpml_last · pdf(렌더 캐시 경로) · mapping · mappingEdited(화면이 쓰는 키만)
  - `log.jsonl` — 기록(§4), 한 줄 한 사건, 덧붙이기만
  - `verify/<n>-<kind>.json` — 검증 실행마다 결과 전체(§5)
  - `outputs/<sha256 앞 16자>.<ext>` — 출력파일 검증한 파일·내려받은 파일(원본과 다를 때만, 같은 바이트는 한 번)
- 쓰기는 임시 파일 → 바꿔 넣기(원자적). 못 읽는 작업 폴더(work.json 없음·깨짐)는 목록에서 빼고 지우지 않는다.

### 3. 저장 시점 · 다시 열기 (`server.py`)

- **편집 상태 저장**: 편집이 성공할 때마다 세션 `rev` +1(글 고침·되돌리기·나누기·합치기·글자/문단 모양·표 행/열·실행 취소). 배경 스레드가 1.5 초마다 `rev` 가 저장한 것과 다른 세션을
  잠금 안에서 묶고(`struct.snapshot` — 실행 취소와 같은 묶음) 잠금 밖에서 쓴다. 서버를 정상으로 끌 때, 메모리에서 비우기 전, 출력파일 검증을 시작할 때 한 번 더.
  강제 종료는 마지막 1.5 초 안의 편집을 잃을 수 있다. 상태는 직렬화를 다 끝낸 뒤에 세 파일(current·doc.pkl·state.json)을 쓴다 — 못 쓰는 값이 있으면 하나도 안 바꾸고
  세션에 실패를 달아 응답 `persistError` 로 알린다(화면 「작업 저장 실패」). 메모리에서 비운 세션(늦게 끝난 검증 스레드)은 쓰지 않는다 — 다시 연 세션을 덮지 않게.
  doc.pkl·state.json 에 같은 차례(`rev`)와 current 의 sha256 을 적어, 다시 열 때 셋이 맞는지 본다.
- **다시 열기**: `/api/docs/{id}…` 가 메모리에 없는 id 를 받으면 작업 폴더에서 연다 — 원본으로 세션을 만들고(`orig_texts` 는 원본에서 다시), `current` + `doc.pkl` 을
  `struct.restore(cls, original, 묶음)` 으로 붙인다(기준 `_data`·`_zip` = 원본 → 「원본과 바이트 동일」·되돌리기 기준이 원본 그대로, `adopt_ids` 로 같은 블록 id).
  `state.json` 의 집합·매핑·PDF 경로를 되놓고(PDF 파일이 렌더 캐시에서 지워졌으면 그 PDF 만 뺌), 검증은 종류마다 **마지막 기록**을 결과로 보인다.
  가져오기 검증 기록이 없으면(끝나기 전에 꺼짐) 가져오기 검증을 다시 돈다. 묶음을 못 붙이면(블록 id 자리표 불일치 등) 원본으로 열고 기록에 「편집 상태 복원 실패」.
- 작업 지우기 = 폴더와 메모리에서 지움(되살릴 수 없음 — 화면이 확인을 받는다).

### 4. 기록 (`log.jsonl`)

한 줄 = `{"t": 시각(초), "rev": 편집 차례, "kind": …, …}`. 화면 「기록」 탭이 최근 것부터 보인다.

| kind | 언제 | 더 적는 것 |
|---|---|---|
| `create` | 작업 만들 때 | name · size · sha256 · source |
| `text` | 문단 글 고침(PATCH) | id · before · after(문단 글 전체) · restored(원본 XML 로 되돌림) |
| `revert` | 「되돌리기」 | id · restored |
| `split`·`merge`·`chars`·`para`·`table` | 구조·서식 편집 성공 | 요청 본문(id·offset·changes·op…) · owpml(검사 상태·요약) |
| `rejected` | 구조·서식 편집을 표준 검사가 되돌림(422) | op · 요약 |
| `undo` | 실행 취소 | — |
| `verify` | 검증 시작 | verify(`import`·`edit`) · revision(화면 수정 번호) |
| `verified` | 검증 끝 | verify · n(기록 번호) · status · seconds · outputSha(출력파일 검증) · 단계마다 {key, title, status} |
| `download` | 「저장」 내려받기 | name · size · sha256 · same(원본과 동일) · verified(마지막 출력파일 검증 파일과 같은지) |
| `reopen` | 디스크에서 다시 엶 | ok(편집 상태 복원 여부) |
| `reupload` | 같은 파일을 다시 올리거나 같은 예제를 다시 열어 이 작업을 이어 엶(§1) | source(upload·sample) |

- 글 고침은 화면이 문단마다 모아 보내는 요청 단위로 적힌다(타자 하나하나가 아님). 화면은 같은 문단의 잇단 `text` 를 한 줄로 묶어 보인다(처음 before → 마지막 after).

### 5. 검증 기록

- 검증(가져오기·출력파일)이 끝나면 `verify/<n>-<kind>.json` = 그 실행의 결과 전체(`Job.view()` — 단계·상세·차이 목록·레터/글꼴 표) + revision + 매핑 요약 +
  출력파일 검증이면 검사한 파일의 sha256(그 파일은 `outputs/` 에). 번호 n 은 작업 안에서 1 부터.
- `work.json` 의 `verify` 는 종류마다 마지막 기록 요약 — 목록 화면이 이것으로 상태를 보인다.
- 내려받은 파일이 마지막 출력파일 검증 파일과 같은 바이트인지 기록에 남긴다(`download.verified`) — 「검증한 파일을 내려받았는가」의 근거.

### 7. 화면

- **시작 화면**: 파일 놓는 곳 아래 「최근 작업」 목록 — 이름 · 형식·크기 · 만든 때 · 바뀐 때 · 고친 문단 수 · 가져오기/출력파일 검증 상태 표지. 누르면 그 작업을 열고, × 는 확인 뒤 지움.
- **상단**: 「작업」 단추 = 작업 목록 창(같은 목록) — 다른 작업으로 바꾸기. 파일 이름 옆에 「작업 · 만든 때」.
- 주소에 작업 id(`#w=<id>`) — 브라우저를 새로 고치거나 다시 열어도 그 작업.
- **시작 화면으로**(2026-11-12 사용자 — ① 같은 날 "넣어줘"): 상단 바 왼쪽 **로고**(`#homeLink.brand` — 문서 아이콘 + 앱 이름, 좁은 창에서는 아이콘만)를 누르면 연 작업을 **화면에서만 닫고**
  시작 화면(파일 놓는 곳 + 최근 작업)으로 간다(app.js `goHome` → `closeDoc`). 작업은 지우지 않는다 — 최근 작업에서 다시 연다. 주소의 `#w=<id>` 도 걷혀 그 뒤 새로 고쳐도 시작 화면이다.
  - 서버에서 도는 일(헤딩 추출·검증)은 끊지 않는다 — 그 작업을 다시 열면 이어 읽는다. 화면이 기다리던 답은 다른 작업을 열 때와 같이 버린다.
  - 묻는 때는 둘(다른 작업을 열 때·2열을 닫을 때와 같은 물음): 서버에 아직 반영 안 된 수정이 있을 때 · 2열에 저장 안 한 글(지침·표 지침·양식 정보)이 있을 때. 「취소」 면 그대로 둔다.
  - 로고는 링크(`<a href="/">`)다 — Ctrl·Shift·가운데 누름은 브라우저대로 **새 탭·새 창에 시작 화면**(지금 작업은 그대로). 시작 화면에서는 눌러도 아무 일도 없다(손가락 커서도 안 뜸).
    옆 문서 화면(`?peek=`)에는 상단 바가 없어 해당 없음.
- **패널 「기록」 탭**: 최근 것부터 사건 목록(§4 — 같은 문단 잇단 글 고침은 묶음, 문단 id 를 누르면 문서의 그 문단), 검증 실행은 상태 표지 + 펼치면 그 기록의 단계 목록(지난 실행도),
  「원본 받기」. 작업 저장이 꺼져 있으면 탭을 숨긴다.
- **저장 표시**: 작업에 저장되는 문서는 고친 것이 있어도 상단에 **글을 두지 않는다**(2026-11-11 ① — 전의 「고친 문단 n개 · 작업에 자동 저장」 을 없앰: 고친 수는 도구 탭 「고친 문단」 배지에 있다).
  저장 실패만 「고친 문단 n개 · 작업 저장 실패 — 저장으로 받아 두세요」 로 알린다. 다른 작업을 열거나 창을 닫을 때는
  서버에 아직 반영 안 된 수정이 있을 때만 묻는다. 「출력파일 검증이 지금 수정을 검사했는가」는 서버 편집 차례(`rev` — 편집 응답마다 옴)로 견준다(다시 연 화면에서도 맞게).

### 8. 확정 — 고친 문단을 깃처럼 (2026-11-10)

깃에 견주면: 고친 문단 = 작업 트리의 변경, **확정** = 커밋, **확정 기록** = 로그, **기준** = HEAD, 문단 「되돌리기」 = 그 문단만 기준으로, 「버리기」 = 변경 모두 버림,
「이 확정으로 복원」 = 그 시점으로 되돌리는 새 커밋.

**용어**
- **기준**: 고친 문단을 견주는 대상. 처음엔 올린 원본(확정 0), 확정하면 마지막 확정. 「고친 문단」 = 기준과 다른 문단(수·목록·왼쪽 띠·되돌리기 모두 기준 대비).
- **확정**: 지금 편집 상태 전체를 작업 안에 한 시점(번호 1부터)으로 남기고 새 기준으로 삼는 것. 문서 전체 단위 — 문단을 골라 확정하지 않는다.
- **확정 기록**: 확정 목록(최근 것부터, 맨 아래 「올린 원본」). 지우지 않는다.

**확정하면**
- 고친 문단이 0 이 된다(문서 글·블록 id 는 그대로 — 화면을 다시 그리지 않음). 그 뒤 고친 것만 「고친 문단」에 모인다.
- 「되돌리기」·「저장하면 기준과 같은 바이트」 판정·출력파일 검증(기준 PDF ↔ 저장본 PDF)·PDF 탭의 왼쪽 단추가 모두 **확정본 기준**이 된다.
  가져오기 검증을 새 기준으로 다시 돈다(배경 — 기준 PDF·쪽 매핑이 새로 생김, 같은 바이트를 막 출력파일 검증했으면 렌더 캐시로 빠름). 지난 출력파일 검증 결과는 화면에서 내린다(기록에는 남음).
  검증이 도는 중에도 확정할 수 있다 — 돌던 검증은 옛 기준으로 끝까지 돌되 결과를 세션에 쓰지 않고 기록도 남기지 않는다.
- 실행 취소 기록을 비운다(확정 앞으로 돌아가려면 확정 기록의 「복원」). 구분 기준 계획(반영 전)은 버린다 — 다시 계획. 편집 차례(`rev`)는 그대로(문서가 안 바뀜 → 헤딩 추출 결과 유지).
- 확정할 것이 없으면(고친 문단 0 이고 저장 바이트가 기준과 같음) 거절(400). 작업 저장이 꺼져 있으면 확정 기능 없음.

**버리기 · 복원**
- **버리기**: 확정하지 않은 변경을 모두 버리고 기준 상태로(확정이 새로 생기지 않음, `rev` +1). 화면이 확인을 받는다.
  기준이 그대로라 기준 쪽 결과(가져오기 검증·기준 PDF·쪽 매핑·표준 검사 기준선)는 그대로 쓴다 — 한글 PDF 를 다시 찍지 않는다.
  지난 출력파일 검증은 편집 차례가 달라 화면이 「검증 전」으로 본다.
- **이 확정으로 복원**(올린 원본 포함): 문서를 그 확정 상태로 되돌리고 **새 확정으로 남긴다**(「확정 k 로 복원」, 파일 바이트는 그 확정과 같음 — 같은 파일을 가리키기만).
  확정 기록은 한 줄로만 자라고 어떤 확정도 지워지지 않는다. 확정하지 않은 변경이 있으면 화면이 「버리고 복원」 확인을 받는다(서버는 `discard` 없이는 409).
  그 확정 때의 블록 id·구분 기준 적용 상태·개요 편집 오버레이도 함께 되돌린다(버리기도 같다 — 기준 확정 때의 것으로). 구분 기준의 「추가한 자리」는
  되돌린 문서에 그 문단이 있는 것만 남긴다. 블록 id 번호표는 줄이지 않는다(되돌린 뒤 새 문단이 옛 id 를 다시 쓰지 않게).

**저장** (`app/works.py`)
- `commits/<n>.json` — 요약 {n, at, message, sha256, size, counts {text, format, struct, new, removed, total}, restoreOf?}
- `commits/<n>.data.json.gz` — 블록 id 자리표(`ids`) · 구분 기준 적용 상태(`division`) · 개요 오버레이(`outline`) · 변경 목록 `changes` [{id, kind, before, after}](문서 차례, 지운 문단은 끝)
- 파일 바이트는 `outputs/<sha256 앞 16자>.<ext>`(§2 — 검증·내려받기 파일과 같은 곳, 같은 바이트는 한 번). `work.json` 에 `commits`(마지막 확정 번호 — 목록용,
  원본은 `commits/` 폴더). 확정 파일을 읽을 때 적어 둔 sha256 과 맞는지 본다(깨진 파일로 기준을 삼지 않음).
- 쓰기·읽기는 Windows 의 「바꿔 넣는 중 거절」을 몇 번 다시 한다(`_write`·`_read_json` — [references/Windows_파일_바꿔넣기.md](../references/Windows_파일_바꿔넣기.md)).
- `state.json`·`doc.pkl` 에 `base`(이 편집 상태가 기대는 확정 번호, 없으면 0) — 다시 열 때 그 확정의 바이트·id 자리표로 세션을 만들고 편집 상태를 그 위에 붙인다.
  편집 상태가 없으면 마지막 확정으로, 기준 확정 파일을 못 읽으면 올린 원본으로 열고 기록에 남긴다. 검증 기록에도 `base` — 다시 열 때 지금 기준의 기록만 결과로 보이고 없으면 가져오기 검증을 다시.
- 헤딩 규칙 저장소의 문서 키는 확정해도 **올린 원본의 sha256** 그대로(같은 문서가 두 문서로 세어지지 않게).

**API**

| 메서드·경로 | 입력 → 출력 |
|---|---|
| `GET /api/docs/{id}/commits` | → `{base, edited, commits: [{n, at, message, sha256, size, counts, restoreOf}]}` 최근 것부터, 끝에 n=0 「올린 원본」 |
| `POST /api/docs/{id}/commits` | `{message?}`(200자까지) → `GET /api/docs/{id}` 꼴 + `commit`(블록은 확정 전과 같다 — 화면은 다시 그리지 않고 블록 표·원래 글만 바꿈) · 확정할 것 없음 400 |
| `POST /api/docs/{id}/commits/{n}/restore` | `{discard?}` → `GET /api/docs/{id}` 꼴 + `commit`(n = 기준이면 버리기 — `commit: null`) · 변경이 있는데 `discard` 없음 409 · 이미 그 상태 400 · 없는 확정 404 |
| `GET /api/works/{id}/commits/{n}` | `?limit=`(기본 200) → 요약 + `changes`(앞 limit 개) + `more` |
| `GET /api/works/{id}/commits/{n}/file` | 그 확정의 파일(`<이름>_확정<n>.<ext>`, 0 = 올린 원본) |

- 응답 `state()` 에 `base`(기준 확정 번호). 기록(§4)에 `commit`{n, message, counts, sha256} · `restore`{n, of, discarded} · `discard`{base, count}.
  작업 목록(§6 `GET /api/works`)에 `commits`. 내려받기 이름: 저장 바이트가 기준과 같아도 기준이 확정본이면 `<이름>_수정`(올린 파일과 다른 파일).
- 세션(`server.py`): `s.original`·`s.orig_texts`·`s.blocks` = 기준(올린 원본이 아닐 수 있음), `s.base_n`·`s.base_ids`(기준의 블록 id 자리표), `s.doc_key` = 올린 원본의 sha256.
  검증 스레드는 시작 때의 기준을 붙든 보기(`_JobView`)로 돈다.

**화면** (「고친 문단」 탭 — 배치·폭은 [design.md](../design.md))
- 맨 위 확정 줄: 「기준 확정 n · 고친 문단 N(글 a · 모양 b · 새 문단 c · 지움 d)」 한 줄 + [확정 메시지(선택)] [확정] [버리기] 한 줄. 고친 것이 없으면 두 단추는 꺼짐.
- 그 아래 접힌 「확정 기록 n」: 줄마다 번호 · 때 · 메시지 · 종류별 수, 펼치면 [파일 받기] [이 확정으로 복원] + 그 확정의 변경 목록(앞 200개, 누르면 문서의 그 문단). 기준인 확정에 「기준」 표지.
- 그 아래 고친 문단 목록(전과 같음) — 「원본으로 되돌리기」는 기준이 확정이면 「확정본으로 되돌리기」.
- 상단 저장 표시: 고친 것이 없으면 「확정 n · 고친 것 없음」(기준이 원본이면 전처럼 「원본과 바이트 동일」). PDF 탭 왼쪽 단추 「원본」 → 「확정 n」. 작업 목록에 「확정 n」.
- 「기록」 탭에 확정·복원·버리기 줄.
- 확정 뒤 쪽 나눔: 문서가 그대로라 지금 쪽 나눔을 두었다가 새 기준의 쪽 매핑이 오면 다시 나눈다. 복원은 문서가 바뀌므로 줄 배치 추정으로 먼저 그리고 매핑이 오면 다시.

### 9. 첫 분석 — 새 작업을 처음 열 때 저절로 도는 것 (2026-11-10)

올리면 저절로 이어지는 것이 가져오기 검증뿐이던 것(① 같은 날 조회)에 분석 둘을 더한다. 사용자 선택: 헤딩은 **스크립트만**, 구분 기준은 **빠진 자리 검토만**.

- **언제**: 화면이 **새 작업**을 열었을 때 한 번 — 올리기·예제 열기 응답이 `reused: false`(§1). 이어 연 작업(`reused`)·작업 목록·주소(`#w=`)로 연 작업에서는 돌지 않는다.
  서버의 올리기 끝점(`POST /api/docs`·`/api/samples/{name}`)은 그대로이고 **화면이 아래 끝점 둘을 부른다** — API 로만 올리는 시험·도구는 첫 분석이 돌지 않는다(LLM 호출·헤딩 작업 409 없음).
  가져오기 검증과 함께 돈다(서로 기다리지 않음).
- **무엇**:
  1. **헤딩 추출 2단계(헤딩 그래프) → 3단계(표 구조)** 를 스크립트만으로, 한 작업으로 잇달아 — `POST /api/docs/{id}/headings {first: true}`(`heading_runs.run_first`; 응답·폴링은 여느 헤딩 작업과 같고 작업 보기에 `first: true`, `stage` 는 3).
     hwpx 만. 1단계는 2단계가 스스로 뽑는다. **이미 결과가 있는 단계는 건너뛴다**(LLM 결과를 덮지 않음). 기록은 단계마다 `headings`(2단계 줄에 `first`). LLM 실행은 지금처럼 사람이 단추로.
  2. **구분 기준 LLM 검토** — `POST /api/docs/{id}/divisions/review {auto: true}`([spec_구분_기준.md](spec_구분_기준.md) ② §14, 원본은 거기). 지원 양식이고 LLM 연결이 있고 아직 검토 결과가 없을 때만 돌고,
     아니면 호출 없이 끝난다. 갓 올린 문서에는 표시한 자리가 없어 **빠진 자리 검토만** 돈다(그 양식 실측 31초·$0.22).
- **화면**: 시작할 때 알림 한 줄. 헤딩 탭을 열지 않아도 2단계가 끝나면 쪽 여백 「TN Lk」 표시·개요 편집 키가 켜지고 표 표지에 소속이 채워진다(헤딩 탭의 상태 읽기와 같은 길 — `headsPoll`).
  구분 기준 검토가 끝나면 알림 「구분 기준 LLM 검토 — 빠진 자리 후보 N · **보기**」(누르면 구분 기준 탭 + 2열 검토 결과). 첫 분석의 실패(끝점 없음·409·LLM 실패)는 알림 없이 콘솔에만 — 탭에서 손으로 다시 돌릴 수 있다.
- **저장**: 헤딩 결과는 여느 실행처럼 `headings/<n>/`, 구분 기준 검토는 `state.json` 의 `division.review`(다시 열어도 남음).

### 10. 작업 종류 · 첨부 파일 · 할 일 · 과제 묶음 · 문서 목록 (2026-11-11)

작업(올린 파일 하나)마다 「어느 과제의 어떤 파일이고 무엇을 할지」 를 적어 둔다. 작업은 여전히 파일 하나다(§1) — **과제 = 같은 과제 이름을 적은 작업들**(따로 저장하는 과제 기록은 없다).

- **값** — `work.json` 의 `task = {kind, file, job, project}`(모두 문자열, 빈 글 = 안 고름). 병합 등 다른 기능은 이것을 읽는다.

  | 키 | 값 → 화면 이름 |
  |---|---|
  | `kind` 작업 종류 | `rnd` 연구개발과제 |
  | `file` 첨부 파일 | `plan` 사업계획서(양식 판정 「연구개발계획서」) · `report` 연차보고서 · `part` 기관 문서(취합에 든 기관 제출 문서 — 2026-11-12, 꼬리표일 뿐 취합에 든 문서의 원본은 취합본의 `gather.json`: [spec_취합.md](spec_취합.md) ② §2) |
  | `job` 할 일 | `plan_fit` 사업계획서 양식 맞추기 · `plan_merge` 사업계획서 취합 · `plan_to_report` 사업계획서 → 연차보고서 이관 · `report_fit` 연차보고서 양식 맞추기 · `report_merge` 연차보고서 취합 — 목록 차례 = 일의 흐름. 이름은 「문서 + 동작」, 동작 낱말은 양식 맞추기(= 구분 기준에 맞춰 양식을 늘리고 줄임 — [spec_구분_기준.md](spec_구분_기준.md)) · 취합 · 이관 셋(2026-11-11 사용자 확정 — 전에는 취합 둘 + 「…초안 만들기」 셋. 키 `plan_merge`·`plan_to_report`·`report_merge` 는 그대로라 저장된 값은 유효) |
  | `project` 과제 | 과제 이름(사용자가 쓰는 글 — 앞뒤를 떼고 빈칸을 하나로, 60자까지) |

- **과제 묶음**(사용자 선택 「과제로 묶기」 — ① 같은 날): 같은 `project` 이름을 적은 작업들이 한 과제다. **할 일은 과제에 하나** — 과제에 들어온 문서(이름을 새로 적거나 바꿈)는 그 과제에 이미 있는 문서의
  `job` 을 따르고(그쪽이 비어 있으면 제 것), 과제 안에서 `job` 을 바꾸면 묶인 문서 모두에 적는다. `kind`·`file` 은 문서마다 따로. 이름을 지우면 과제에서 나온다(다른 문서는 그대로). 과제 이름 바꾸기는
  문서마다 새 이름을 적는 것(한 번에 바꾸는 기능 없음).

- **안 고른 문서는 짐작**: `task` 가 없으면 문서의 양식 판정(구분 기준 프로파일 `form_of` — [spec_구분_기준.md](spec_구분_기준.md) ② §0)으로 — 국가R&D 양식이면 `kind = rnd`,
  `file` = 연구개발계획서 → `plan` · 연차보고서 → `report`, `job`·`project` 는 빈 글. 국가R&D 양식으로 짐작한 것은 그때 `work.json` 에 적어 둔다(문서 목록이 종류를 보이게). 그 밖의 문서는 모두 빈 글이고 적지 않는다.
- **API**: `GET /api/docs/{id}` 의 `work.task`(고른 것 또는 짐작) · `GET /api/works` 항목의 `task`(적힌 것만, 없으면 null) ·
  `PUT /api/works/{id}/task` `{kind, file, job, project}` → `{task}`(과제에 들어가 `job` 이 바뀌었으면 바뀐 값) — 저장만(문서·분석은 그대로), 모르는 값 400, 없는 작업 404.
  `kind` 를 비워도 `file`·`job`·`project` 는 지우지 않는다(다시 고르면 그대로).
- **목적 문서의 보이는 이름**(2026-11-12 사용자 "목적문서는 과제 이름을 뒤에 붙여주도록 해줘" — ① 같은 날): 목적 문서(내용을 받는 문서 — [spec_병합.md](spec_병합.md) ② §0)가 과제에 묶여 있으면 이름을 **「<올린 파일 이름>_<과제 이름>.<확장자>」** 로 보인다
  (「연차보고서 양식_260319.hwpx」 + 과제 「JO_TEST2」 → 「연차보고서 양식_260319_JO_TEST2.hwpx」) — 같은 빈 서식을 과제마다 올려 이름이 같아지는 것을 가른다.
  - **목적 문서** = `task` 의 (할 일 · 첨부 파일)이 (`plan_to_report` · `report` — 이관의 연차보고서) 또는 (`plan_merge` · `plan` — 취합의 취합본)이고 `project` 가 있는 작업(`works.TARGET_FILE`). 원본 문서(이관의 사업계획서 · 취합의 기관 문서) · 과제에 안 묶인 문서 · 다른 할 일의 문서는 올린 이름 그대로.
  - **저장된 이름은 안 바꾼다**(`work.json` `name` · 세션 이름 = 올린 그대로) — 같은 파일 이어 열기(§1) · 양식 판정(파일 이름 꼴) · LLM 에 보내는 문서 이름 · 기록(`log.jsonl`)은 올린 이름을 본다. 보이는 이름은 읽을 때마다 `task` 에서 만든다(`works.shown_name(name, task)`) —
    과제 이름·할 일·칸이 바뀌면 따라 바뀌고, 과제에서 나오면 올린 이름으로 돌아간다.
  - **붙는 곳**: `GET /api/works` 항목의 `name` · `GET /api/docs/{id}` 의 `name` · `GET /api/works/{id}/log` 의 `work.name` · `…/headings-preview` 의 `work.name` · 자리 연결 응답의 `from.name`·`to.name` · 내려받는 파일 이름(「저장」 = `…_<과제>.<ext>` 또는 `…_<과제>_수정.<ext>` · 지금 편집본 · 확정 파일 `…_<과제>_확정n`).
    화면은 받은 이름을 그대로 보인다(작업 목록 · 상단 바 · 첨부 파일 칸 · 둘째 면 탭 · 같은 과제 문서 줄 · 연결 목록 머리) — 지금 문서의 이름은 작업 목록을 다시 읽을 때 함께 맞춘다(과제 이름·칸을 바꾼 바로 뒤에도).
  - **안 붙는 곳**: 올린 원본 받기(`file/original` · 확정 0 — 올린 파일 그대로) · 같은 파일 이어 열기 응답의 `name` · 올린 이름이 이미 `_<과제 이름>` 으로 끝나는 파일(두 번 안 붙임).
    과제 이름에 든 파일 이름에 못 쓰는 글자(`\ / : * ? " < > |`)는 `_` 로 바꿔 붙인다.
  - 취합 쪽 끝점(`merge_gather_api` — 취합본 내려받기 등)은 [spec_취합.md](spec_취합.md) 가 정한다(여기서는 안 바꿈).

  닫혀 있는 문서는 서버가 작업 폴더에서 연다(§3). 문서가 바뀌어 오래된 결과는 다시 돌리지 않는다(없는 것만). 고르는 목록의 문서마다 과제·첨부 파일 종류를 보이고,
  지금 문서가 과제에 묶여 있으면 같은 과제의 hwpx 문서를 처음부터 함께 골라 둔다(6개까지). 두 문서를 함께 보는 화면은 이 탭이다(사용자 선택 「분석 결과를 나란히」 — 문서 본문은 한 번에 하나). 문서 본문을 나란히 보는 것은 이관의 「같이 보기」(§12 — 같은 날 뒤에 추가, 옆 문서는 보기만).
- **「할 일」 은 고른 값을 저장한다** — 이관을 고르면 첫 카드에 첨부 파일 칸 둘과 단계가 보인다(§11·§14, 내용 반영은 [spec_병합.md](spec_병합.md)). 「사업계획서 취합」 은 취합본 칸 하나 + 기관 문서 줄 여럿과 묶음 둘이며, 내용 반영은 [spec_취합.md](spec_취합.md) ② §4·§5. 양식 맞추기는 같은 패널의 구분 기준이고, 할 일을 무엇으로 골랐든(안 골라도) 그대로 보인다(할 일로 패널의 구분 기준을 가르지 않음). 「연차보고서 취합」 은 아직 준비 중이다.
- 작업 저장이 꺼져 있으면(`NFM_WORKS=off`) 고른 값은 그 화면에서만 산다(저장 요청을 안 보냄).

### 11. 할 일의 차례 — 이관 (2026-11-11 사용자 요청 — ① 같은 날)

할 일을 고르면 그 일에 드는 **첨부 파일 칸**과 **단계**가 첫 카드에 차례로 보인다. 지금은 `plan_to_report`(사업계획서 → 연차보고서 이관)와 `plan_merge`(사업계획서 취합 — 칸·단계는 [spec_취합.md](spec_취합.md) ② §5, 아래는 이관) — 다른 할 일은 §10 그대로(첨부 파일 = 이 문서의 종류 하나).
새 API·저장 값은 없다(화면이 있는 끝점만 부른다 — §10 `PUT …/task` · spec_구분_기준 ② §7 `GET …/divisions`·`…/divisions/read` · 헤딩 요약 `GET /api/docs/{id}/headings`). 작업 저장이 꺼져 있으면 전과 같다(칸·단계 없음).

- **첨부 파일 칸**(이관 = 사업계획서 · 연차보고서 — 앞의 것이 기준): 첫 카드의 「첨부 파일」 자리가 종류마다 한 줄(문서를 고르는 select `select[data-task-file=plan|report]`)이 된다.
  줄 이름 = 「사업계획서(기준)」 · 「연차보고서」(「첨부 파일」 이라는 낱말은 줄에 안 쓴다 — 패널 320px 에서 목록 폭이 모자람. 도움말과 단계 ① 이름에 있다).
  - 칸의 문서 = 지금 문서의 `file` 이 그 종류면 지금 문서, 아니면 같은 과제에서 `file` 이 그 종류인 첫 문서. 없으면 「선택 안 함」.
  - 고를 수 있는 문서 = 지금 문서 + 같은 과제의 문서 + 과제 이름이 없는 문서(다른 과제의 문서는 안 나옴). 과제 이름이 비어 있으면 지금 문서뿐이다(과제 이름을 먼저 적는다). 이름 뒤에 「— 지금 문서」, 종류가 다르게 적힌 문서는 「(연차보고서)」 꼬리.
  - 고르면: 그 문서의 `task` 가 `{kind: rnd, file: 그 종류, project: 이 과제}` 가 된다(할 일은 과제를 따름 — §10). **칸에 있던 문서는 빠진다** — 과제에서 나온다(`project` 비움 · 종류는 그대로).
    **지금 문서가 그 칸에 있었으면 고른 문서를 연다**(2026-11-12 사용자 "연차보고서는 빈건데 왜 화면에 보이는 것은 1단계가 진행된 문서로 나오냐?" — ① 같은 날): 화면이 고른 문서로 바뀌고 작업 내용(연구개발과제 패널)이 다시 열리며, 지금 문서도 다른 문서처럼 과제에서 나온다 —
    칸은 새 문서인데 화면·「문서 반영 상태」 는 옛 문서인 엇갈림을 없앤다. 반영 안 된 수정이 있으면 먼저 묻고, 그만두거나 못 열면 화면은 그대로이고 지금 문서는 종류만 비운다(과제에는 남음 — 보고 있는 문서의 과제 칸이 비지 않게).
    「선택 안 함」 을 고르면 빠지기만 한다(지금 문서면 종류만 비움 — 과제에는 남음). 이관은 종류마다 문서 하나로 본다(같은 과제에 같은 종류가 여럿이면 고를 때 나머지도 과제에서 나온다).
  - 칸에 안 든 같은 과제 문서는 전처럼 「같은 과제 문서 N개 — …」 한 줄.
  - **칸 오른쪽 폴더 단추**(`button.dv-flow-up[data-task-up=plan|report]` 28×28 · 2026-11-11 사용자 "사업계획서 올리는 버튼이 없어" · "우측에 … 폴더 모양으로"): 누르면 파일 고르기(hwpx) → 새 작업으로 올리고(`POST /api/docs?new=1`) 바로 그 칸에 넣는다(위 「고르면」 과 같은 길).
    지금 문서가 그 칸의 문서가 아니면 **지금 보는 문서는 그대로**(올린 문서를 열지 않는다 — 연차보고서를 보며 사업계획서를 올릴 때), 그 칸의 문서면 **올린 문서로 화면이 바뀐다**(위 「고르면」 — 2026-11-12 · 단추 도움말이 어느 쪽인지 말한다).
    올린 문서의 헤딩·표 분석(스크립트 — `POST …/headings {first: true}`)은 바로 걸어 둔다. 과제 이름이 비어 있으면 단추가 막힌다(도움말 「과제 이름을 먼저 적으세요」).
- **단계**(칸 아래 번호 목록 `ol#taskSteps.dv-flow-steps` — 줄마다 `data-step`·`data-state`): 앞 단계가 끝나야 다음 단계가 「지금」 이 된다. 상태 = `done`(끝남 ✓) · `now`(지금 — 할 일과 단추) · `todo`(앞 단계 뒤) · `soon`(아직 없는 기능).

  단계의 이름·번호·차례는 **공통 차례**([spec_병합.md](spec_병합.md) ② §0-1 — 같은 날 사용자 확정 "일단 권장으로 진행")를 따른다: 준비 → ① 구분 기준 확인 → ② 자리 연결 → ③ 표 안 연결 → 넣기 계획 → ④ 내용 반영 → ⑤ 합계 계산 → 결과 확인.

  - 반영한 뒤 글을 고쳤다고 「다시」 를 요구하지 않는다(반영 값이 같으면 끝남 — 「반영 후 문서 수정」 표시는 아래 「문서 반영 상태」 에 그대로).

  (문서 비교의 `headings-preview` 는 안 쓴다 — 그래프까지 실려 큰 문서에서 2.6 MB.)
- **다시 읽는 때**: 탭을 열 때·계획/반영/실행 취소 뒤(`divShow`) · 칸을 바꾼 뒤 · 과제 이름·할 일을 바꾼 뒤 — 두 칸이 다 찼을 때만 읽는다. 지금 문서의 구분 기준은 화면 값이라 입력을 바꾸면 바로 다시 견준다(다른 문서 쪽은 읽어 둔 것).
  다른 문서의 값은 `GET /api/docs/{id}/divisions` 로 읽는다 — 닫혀 있으면 서버가 연다(§3 — 큰 문서는 처음 몇 초).
- **줄 모양**: 순서 번호는 완료 뒤에도 유지하고, 이름 옆에 완료·다음 작업·대기 등 상태를 글로 보인다. 설명·결과와 단추는 아래 줄. 묶음과 세부 목록의 현재 규칙은 §14 및 [design.md](../design.md) §11(패널 320px·480px 에서 가로 넘침 없음).

### 12. 같이 보기 — 이관의 다른 칸 문서를 문서 열 옆에 (2026-11-11 사용자 요청 — ① 같은 날)

이관에서 지금 문서 옆에 다른 칸의 문서(연차보고서를 보고 있으면 사업계획서)를 **읽기 전용**으로 나란히 띄운다. 화면만 — 서버·API·저장 값은 그대로.
(§10 의 「문서 본문은 한 번에 하나」 는 고칠 수 있는 문서 이야기로 남는다 — 고치는 문서는 여전히 하나, 옆 문서는 보기만.)

- **열**(`#peerCol.peer-col`): 문서 열 바로 오른쪽 — 2열(`#headsDlg`)·3열(패널)보다 앞. **폭은 문서 열과 늘 반반**(아래 「두 면」 — 폭 손잡이 없음: 패널·2열이 넓어지면 두 면이 함께 줄고, 두 면은 저마다 360px 아래로 안 줄어든다) ·
  » 로 오른쪽 28px 띠로 접기 · ✕ 닫기([design.md](../design.md) §5). 머리 = 문서 이름 탭 줄(아래 「두 면」). 좁은 창(≤ 820px)과 「문서 비교」 에서는 안 보인다.
- **두 면**(2026-11-11 사용자 「줄은 위에 한 번, 이름 줄 없이」 · "두번째 면은 여러 문서가 … 문서 이름을 탭으로" · "도구는 하나로 둘다 선택할 수 있게" · "두 면이 같은 크기로 항상 보였으면"): 첫째 면 = 문서 열(고치는 문서), 둘째 면 = 이 열(보기만).
  **좌우 = 이관의 칸 차례**(2026-11-11 사용자 "구지 순서를 바꿀 필요가 있을까?" — 처음엔 첫째 면이 늘 왼쪽): 두 면의 문서가 모두 칸의 문서면 **사업계획서 왼쪽 · 연차보고서 오른쪽** — 어느 쪽을 고치고 있든 자리는 그대로이고
  고치는 문서가 바뀌면 도구 탭 띠(고치는 문서 위)와 문서 이름 탭 줄·「읽기 전용」(보기만 하는 문서 위)이 자리를 바꾼다(`.workspace.peer-left` — 둘째 면이 왼쪽 칸). 칸에 없는 문서를 띄웠거나 둘째 면을 띠로 접었으면 전처럼 둘째 면이 오른쪽.
  - **줄은 두 문서 위에 한 번**: 화면은 세 행 — ① 탭 줄 ② 편집 도구 줄 ③ 문서. ①은 왼쪽(문서 열 위)이 도구 탭 띠, 오른쪽(둘째 면 위)이 **문서 이름 탭 줄**로 같은 행·같은 높이(도구 탭 띠가 두 줄로 꺾이면 함께).
    ② 편집 도구 줄은 **두 문서 폭에 걸쳐 한 번**(둘째 면이 접혔거나 없으면 문서 열 폭만 — 넓어진 만큼 한 줄에 다 들어간다). ③ 두 문서는 늘 같은 줄에서 시작해 같은 줄에서 끝난다 — 창마다 이름 줄은 없다.
    상단 바의 「탭 ▴」·「편집 ▴」·⇅([spec_hwpx_웹편집.md](spec_hwpx_웹편집.md) ② §9 「줄 접기·바꾸기」)는 그 행을 통째로 접는다 — 「탭 ▴」 을 접으면 문서 이름 탭 줄(» · ✕ 포함)도 함께 사라지고, 둘 다 접으면 두 문서가 상단 바 바로 아래에서 시작한다.
    2열·3열과 접힌 28px 띠는 전처럼 상단 바 바로 아래부터 창 끝까지.
  - **문서 이름 탭**: 둘째 면에 띄울 수 있는 문서마다 탭 하나(차례 = 이관의 칸 문서 → 같은 과제의 다른 문서, 지금 문서는 뺌). 고른 탭 = 떠 있는 문서. 다른 탭을 누르면 그 문서로 바뀐다(다시 읽음 — 보던 자리는 잃는다).
    탭 글 = 파일 이름(길면 줄임표 — 전체 이름·칸 종류는 도움말), 탭이 많으면 가로로 굴린다. 줄 오른쪽 끝에 「읽기 전용」 · » · ✕. 탭으로 고른 것은 이 화면에서만(칸 단추를 누르면 그 칸의 문서가 이긴다).
  - **두 면은 늘 같은 크기 — 도구는 하나**: ⓐ **폭**: 문서 열과 둘째 면은 늘 반반(창·패널·2열 폭이 바뀌어도). ⓑ **보기**: 둘째 면은 첫째 면의 보기를 그대로 따른다 — 배율(둘째 면이 제 폭으로 따로 맞추지 않고 **같은 값**) ·
    2쪽 보기 · 쪽 번호 · 휠 쪽 넘김. 그래서 두 문서의 쪽이 같은 크기·같은 자리로 보인다(옆 문서 화면의 여백도 바깥 문서 보기와 같게 — 28·76·80·32px).
    ⓒ **도구 줄은 하나**: 「페이지 보기」 묶음(확대·축소·100% · 폭 맞춤 · 높이 맞춤 · 2쪽 보기 · 쪽 번호 · 휠 쪽 넘김)은 **두 문서에 함께** 듣는다 — 맞춤 배율은 첫째 면 기준으로 재고 둘째 면이 그 값을 받는다.
    글자·문단·표 묶음, 실행 취소, 도구 탭(패널)은 첫째 면(고치는 문서)의 것이다 — 둘째 면은 보기만. 둘째 면만 따로 확대하거나 폭을 달리하는 길은 없다(「항상 같은 크기」).
    둘째 면의 문서를 탭으로 바꿔도, 다시 읽은 문서가 같은 보기를 받는다. 보기 기억(`nfm.view`)은 첫째 면 것 하나뿐.
- **옆 문서 화면** = 같은 앱을 `/?peek=<작업 id>#w=<작업 id>` 로 연 iframe(app.js `PEEK`): 상단 바·도구 탭·도구 줄·2열·패널 없이 문서만. 문단을 고칠 수 없고(contentEditable 끔 — 글 고르기·복사는 됨)
  **GET 밖 요청은 화면이 보내지 않는다**(`api()` 한 곳에서 막음 — 표 메뉴·끌기 같은 다른 길로도 문서가 안 바뀜). Ctrl+S 는 바깥(지금 문서)의 저장. 쪽 번호·쪽 여백 표시는 그 문서의 것이 그대로 보인다.
- **어느 문서**: 처음엔 이관의 첨부 파일 칸(§11) 가운데 지금 문서가 아닌 칸의 문서. 지금 문서가 어느 칸에도 없으면 칸 단추로 고른 칸, 안 골랐으면 앞 칸(사업계획서). 문서 이름 탭으로 같은 과제의 다른 문서(칸에 없는 것 포함)로 바꿀 수 있다(위 「두 면」).
  칸의 문서가 바뀌거나 다른 문서를 열면 따라 바뀐다. 띄울 문서가 없으면 열도 없다.
- **켜고 끄기**: 칸 오른쪽(폴더 단추 다음)의 **같이 보기 단추**(`button.dv-flow-peer[data-task-peer=plan|report]` 28×28 — 눌림 = 그 문서가 옆에 떠 있음 · 지금 문서의 칸·빈 칸은 꺼짐). 열의 ✕ 도 끈다.
  켜고 끈 것은 이 브라우저에 기억(`nfm.peer`), **기본 = 켬** — 이관에서 두 칸이 차 있으면 문서를 열 때 옆 문서도 함께 뜬다.
- **연결 목록에서**(§11 ② · [spec_병합.md](spec_병합.md)): 줄·항목을 눌러 지금 문서가 그 자리로 갈 때 옆 문서도 이어진 자리로 간다(연차보고서 자리 ↔ 사업계획서 자리). 구분 기준 「바꿀 자리」 목록은 지금 문서의 자리뿐이라 옆 문서는 안 움직인다.
- 하지 않는 것: 옆 문서 고치기(그 문서를 열어서) · 이관 밖(칸이 없는 할 일)에서 켜기 · 두 문서의 스크롤 맞물림 · 둘째 면 문서의 패널(검증·헤딩 추출 … — 도구 탭은 첫째 면의 것). · 둘째 면만 따로 확대·폭 조절(두 면은 늘 같은 크기 — 위 「두 면」).

### 13. 할 일 프롬프트 — 할 일마다 저장해 두고 에이전트가 읽는 전제 (2026-11-11 사용자 요청 — ① 같은 날)

할 일(`task.job` — §10)마다 그 일의 **전제·기준**을 사용자가 말한 대로 적은 md 하나를 두고, 그 할 일에서 도는 에이전트가 먼저 읽는다.
에이전트가 일의 전제(무엇이 기준 문서인지)와 어긋난 판단을 하지 않게 하려는 것이다(① 의 당해 차년도 건).

- **파일**: `<저장소>/jobs/<할 일 키>.md`(env `NFM_JOBS` 가 폴더, `off`·`0` = 없음) — 파일 하나가 원본. 지금 있는 것 = [jobs/plan_to_report.md](../jobs/plan_to_report.md)(사업계획서 → 연차보고서 이관). 파일이 없는 할 일은 프롬프트 없음(전과 같다).
  첫 「# 」 줄 = 제목(「— 」 뒤가 표시 이름). 그 줄과 HTML 주석(사용자 원문 기록 등 — 사람·코드 에이전트만 봄)을 뺀 나머지가 LLM 프롬프트에 들어간다. 부를 때마다 읽는다(고친 글이 다음 실행에 바로).
- **적는 것**: 사용자가 말한 전제·기준만 — 무엇이 원본·목적인지 · 값과 내용이 어디서 오는지 · 넣는 것과 안 넣는 것. 사용자가 그 일의 전제를 새로 말하면 이 파일에 적는다(구현 이력·API 는 사양서에).
- **읽는 에이전트**:
  - 코드 에이전트(Claude Code 세션·하위 에이전트): CLAUDE.md 「할 일 프롬프트」 절이 가리킨다 — 그 할 일의 기능을 만들거나 고치거나 설명하기 전에 읽는다.
  - 앱의 LLM 호출: 그 할 일을 고른 작업에서 도는 **자리 연결 LLM 검토**(`POST …/merge-links/llm` — `merge_llm.review(job=)`)가 단위마다 계약 바로 뒤에 「## 할 일 — <이름> (이 작업의 전제 — 먼저 따른다)」 절로 붙인다(`job_prompts.part`).
    함께 보낸 것은 `merge.json` `llm.job {job, name, sha1}` 에 남고, 화면 ② 줄에 「LLM 검토함(N단위 · 할 일 프롬프트 함께 보냄)」 으로 보인다.
  - 앱의 LLM 호출 — **표 채우기**(2026-11-12 newfilemanager-05 — 원본 [spec_헤딩_추출.md](spec_헤딩_추출.md) ② §18): `tables_api.table_fill_propose` 가 계약 바로 뒤에 한 절(`job_prompts.part(p, table_fill.JOB_NOTE)` — 머리 문장은 그 호출의 자료 둘
    (지금 문서 · 사용자가 준 글)이 전제의 어느 문서인지 풀어 주는 판). 보낸 것은 미리보기·제안 응답의 `job` 과 상세 기록 `tables/fill_<ms>.json` 의 `job`, 화면 기준 줄에 할 일 이름.
- **화면에서 보기 — 「지침」**(2026-11-12 사용자 "각 LLM이 검토나 작업할때 '지침' 이나 프롬프트를 확인할 수 있으면 좋겠어" — ① 같은 날): LLM 이 도는 단추 옆에 **「지침」** 단추(보통 단추 — 강조 아님 · `button[data-llm-guide=<step>]`). 누르면 문서 옆 2열(kind `llmGuide` — 모달 아님)에
  그 검토의 프롬프트를 이루는 글을 절마다(`details.lg-part`) 보인다: **계약**(역할·자료 설명·답의 꼴 — 코드에 든 글, 접힘) · **판단 지침**(펴짐 — 파일 경로와 「이 파일을 고치면 다음 실행부터 적용됩니다」) · **할 일 프롬프트**(펴짐 — 같은 안내) · 양식 정보(접힘).
  그 아래 **「마지막으로 보낸 프롬프트」**: 단위마다 한 줄(제목 · 쪽 · 대상 수 · 글자 수 · 오류) — 누르면 그 줄 아래에 프롬프트 전체와 답(JSON)을 편다. 실행 전이면 「아직 실행한 적 없음」. 읽기만 한다(고치기는 파일에서 — 아래 「하지 않는 것」).
  - 붙은 곳: 이관 ② 자리 연결 줄(step `merge-links` — 문서 = 연차보고서, 연결 목록이 나온 뒤면 늘) · 「구분 기준 자리 표시」 줄(step `division-review` 재검토 — 2열 머리 단추로 `division-missing` 빠진 자리 검토와 바꿈). 옆 문서(iframe)에는 없다.
  - 끝점(`app/merge_api.py`): `GET /api/docs/{문서}/llm-guide/{step}` → `{step, name, model(글 | null = 기본 모델), parts[{key: contract|guide|job|form, title, text, source(파일 경로 | ""), note}], last: null | {at, units[{n, title, pages, targets, tables, chars, error, has}]}}` ·
    `GET …/llm-guide/{step}/prompt?unit=N` → `{at, title, prompt, answer}`. 모르는 step · 보낸 것이 없는 단위 = 404(글이 「Not Found」 가 아님 — 끝점이 없는 옛 서버의 404 와 화면이 가른다: 그때는 「서버를 다시 시작한 뒤에 볼 수 있습니다(새 기능)」).
  - 보낸 프롬프트가 있는 곳: 자리 연결 = 작업 폴더 `merge_llm_last.json`(다음 검토가 덮어씀 — [spec_병합.md](spec_병합.md) ② §7) · 구분 기준 = `divisions/review_<시각>.json`(전부터 적던 기록의 마지막 것). 병합의 판단 지침 파일은 [spec_병합.md](spec_병합.md) ② §4 「판단 지침」.
- 하지 않는 것(1차): 화면에서 **고치기**(파일을 편집기에서 고친다 — 보기는 위 「지침」) · 구분 기준 LLM 검토 · 헤딩 추출 LLM(1·2·3단계) · 표 만들기 · LLM 수식 판정에 붙이기(④) · 과제(`task.project`)마다 다른 프롬프트 · 헤딩 추출·표 채우기 단추 옆의 「지침」(헤딩 지침은 제 편집 화면이 있다).

### 14. 1단계 「문서 프레임 작성」 · 2단계 「내용 매핑」 — 단계 묶음 둘 · 묶음마다 한 번에 진행 (2026-11-12 사용자 요청 둘 — ① 같은 날)

이관의 단계 목록(§11)을 **묶음 둘**로 싼다 — **「1단계 문서 프레임 작성」**(구조: 구분 기준 반영까지) · **「2단계 내용 매핑」**(헤딩·표 분석 → 자리 연결 → 넣기 계획 → 내용 반영). 묶음마다 **「한 번에 진행」** 단추, 단계마다 따로 하는 세부 목록은 묶음 안에 접혀 있다.
(처음 꼴 = 단계 전부를 1단계 한 묶음으로 — 에이전트 판단. 같은 날 사용자가 결과를 보고 "지금 문서 프레임 작업인데 왜 내용을 넣지?" → 답 「구조까지만」 · "2단계는 내용 매핑" 으로 가름. 단계 번호·key·판정(§11)은 그대로.)
화면만 — 서버·API·저장 값은 그대로(있는 끝점만 차례로 부른다). 지금은 이관(`plan_to_report`)뿐. 단계 표시·완료 판정은 아래의 2026-11-12 개선을 따른다.

- **묶음에 드는 것**: 1단계 = 준비 · ① 구분 기준 확인(반영 = 절·표 행·열을 사업계획서의 단계·차년도·기관 값에 맞춤 — **내용은 안 넣는다**). 2단계 = ② 자리 연결(앞에 헤딩·표 분석) · ③ 표 안 연결·넣기 계획 · ④ 내용 반영 +
  「⑤ 합계 계산 → 결과 확인」(준비 중 — 세부 목록에 줄로만 보이고 끝난 수에 안 센다). 「프레임」 = 값에 맞춘 연차보고서의 틀(구조), 「내용 매핑」 = 그 틀에 사업계획서 내용을 자리 맞춰 넣기(구분 기준 자리 + 같은 이름 자리 · 서식 맞춤 — [spec_병합.md](spec_병합.md) ② §5·§5-1).
  2단계 「한 번에 진행」 의 ③ 안 차례(2026-11-12 — [spec_병합.md](spec_병합.md) ② §5-3 10 · §5-4 8): 넣기 계획 → 아직 안 물은 빈 자리가 있으면 **빈 자리 검토(LLM)** 한 번 → 다시 계획 → 칸을 못 맞춘 표가 있으면 **표 대응(LLM)** 한 번 → 다시 계획 → ④ 반영.
  둘 다 유료라 누를 때의 확인 글에 적고, 실패해도 멈추지 않는다(찾은 것만 넣는다). 세부 목록의 ③ 줄에는 「표 대응(LLM)」·「빈 자리 검토(LLM)」 단추와 「지침」 이 따로 있다.
- **모양**(`div#taskSteps` 안에 `details#taskStage.dv-phase[data-stage=frame]`(1단계) · `details#taskStage2.dv-phase[data-stage=map]`(2단계) — 첨부 파일 칸 아래 · 테두리 없는 줄. 아래는 묶음마다 같다):
  - **머리 줄**: ▸ · 「1단계」 · 「문서 프레임 작성」 · 「n/1 완료」(2단계 = 「2단계」 · 「내용 매핑」 · 「n/3 완료」) · 단추 「한 번에 진행」(`[data-task-run=frame|map]`) + 진행 막대. 그 묶음의 ①~④만 집계하며 문서 선택(준비)은 별도 상태로, ⑤는 준비 중인 기능으로 표시한다. 왼쪽부터 붙이고, 좁으면 단추가 다음 줄.
  - **상태 줄**(머리 줄 아래 — 접혀 있어도 보임, `.dv-phase-state[data-kind]`): `next` 「다음: ① 구분 기준 확인 — <그 단계의 글>」 · `run` 돌아가는 동그라미 + 「② 자리 연결 — LLM 검토 — 확인 필요 9곳 · 12초」(지금 하는 일 + 지난 시간 — [design.md](../design.md) §7) ·
    `halt` 「멈춤 — ① 구분 기준 확인: <까닭>」 · `done` 「끝남 — 구조를 맞췄습니다 …」(1단계) · 「끝남 — 연결됨 17 · 확인 필요 9(비워 둠) · 같은 이름 자리 66 · 본문 블록 0 · 표 칸 14 · 행 추가 3 …」(2단계). 마지막 실행의 끝(끝남·멈춤)은 그 뒤 단계가 더 나아가거나 다른 문서를 열면 사라진다(화면에만).
    앞 묶음이 덜 끝난 2단계의 상태 줄 = 「1단계(문서 프레임 작성) 뒤에 — 헤딩·표 분석 → 자리 연결(LLM 검토 포함) → 넣기 계획 → 내용 반영(서식 맞춤)」(그 묶음이 하는 일).
  - **세부 목록**: 머리 줄을 누르면 펴지고 접힌다(묶음마다 `ol.dv-flow-steps` — 「`#taskSteps li`」 가 두 묶음의 줄을 문서 차례로 준다). **기본 접힘**, 펴짐은 묶음마다 이 브라우저에 기억(`nfm.taskStageOpen` · `nfm.taskStageOpen2`). 번호는 완료 뒤에도 유지하고, 각 줄의 이름 옆에 「완료 / 다음 작업 / 대기 / 진행 가능 / 진행 중 / 멈춤 / 준비 중」을 글자로 표시한다. 설명·결과와 단추는 이름 아래 별도 줄로 정렬한다. ⑤는 앞 단계 상태에 관계없이 「준비 중」이며 실행 대기와 구별한다. 펼쳤을 때 정상 상태 줄은 다음 단계 이름만 보여 상세 설명의 중복을 줄인다.
  - **단계별 완료**: ③은 넣기 계획이 있으면 완료, ④는 반영 결과가 있어야 완료. 계획 결과 넣을 것이 없으면 ④는 「대상 없음」으로 종료한다. ②를 마쳤으나 이어진 자리가 없는 경우도 ③④에 「대상 없음」을 표시한다. ④에서 「계획 보기」로 들어가 확인·반영하며 ③의 재계획 단추는 유지한다. 실행 중·멈춤 상태는 머리와 해당 줄을 함께 갱신한다(매초 목록을 다시 만들지 않음). 완료 기록의 저장 범위는 그대로이며 ③④ 결과는 현재 화면에서 읽은 상태 기준이다.
  - **1단계 묶음 안의 과제 구성**(2026-11-12 사용자 "1단계에서는 단계, 차년도, 기관구성이 들어가야 하지 … 이걸 저장하고 관리할 수 있어야 하는데 UI가 너무 떨어져 있네" — ① 같은 날): 이관이면 과제 구성 입력(저장한 과제 구성 고르기·저장 · ① 단계·차년도 · ② 기관 구성 · 추가 설정)과
    「문서 반영 상태」 · 「변경 계획 보기」 가 **1단계 묶음(`details#taskStage`) 안, 세부 목록 바로 아래**(`#taskFrameForm.dv-phase-form` — 머리 글 「과제 구성 — 문서 프레임 값」 + 지금 고치는 문서가 어느 칸의 문서인지)에 놓인다. 전에는 패널 아래쪽(자리 표시 줄·양식 줄 뒤)에 따로 있었다 — 이관이 아니면 그 자리 그대로.
    묶음 머리(접혀 있어도 보임), 상태 줄 아래에 **프레임 값 요약 한 줄**(`span.dv-phase-frame` — 「1단계(1–4차년도) · 주관 한국선급 · 공동 3(씨드로닉스 · 유엔젤 · 랩오투원)」: 기준 = 사업계획서 값, 없으면 연차보고서 입력 값 · 출처는 도움말 · 한 줄 줄임표 · 값이 없으면 줄이 없다)과
    그 끝의 **「구성 고치기」**(`button[data-task-frame-edit]` — 1단계를 펴고 첫 입력으로 포커스). 묶음 안에서는 「변경 계획 보기」 가 보통 단추(강조 단추는 카드에 하나)이고 카드는 테두리 대신 윗줄만. 입력 중 단계 목록이 다시 그려져도 폼 노드·포커스는 그대로(폼은 `divRender` 가 한 번 만들고 묶음 그리기는 그 노드를 옮기기만 한다).
    폼이 고치는 것은 **지금(고치는) 문서**의 값이다 — 사업계획서를 고치는 중이면 사업계획서 값(전부터 그랬다 · 이관에서 계획서 반영을 막을지는 [spec_병합.md](spec_병합.md) ④ ㉲).
  - 강조 단추는 카드에 하나: **할 일이 남은 첫 묶음**이 접혀 있으면 그 「한 번에 진행」 이 강조, 펴면 세부 목록의 「다음 할 일」 단추(§11)가 강조. 준비(두 칸에 문서)가 안 끝났거나 남은 단계가 없으면 단추가 꺼진다.
    2단계의 단추는 **1단계가 끝나야** 켜진다(도움말 「1단계 「문서 프레임 작성」 을 먼저 끝내세요」). 한 묶음이 도는 동안 다른 묶음의 단추는 꺼진다.
- **한 번에 진행**(`taskRunAll(묶음)`) — 그 묶음의 안 끝난 단계를 차례로(아래 1·2 는 두 묶음 공통, 3 = 1단계, 4·5 = 2단계):
  1. **누를 때 한 번만 확인**(2026-11-12 사용자 답 「시작할 때 한 번만」 — 「반영 앞에서 멈춤」 은 안 고름): 확인 창에 묶음 이름 · 남은 단계(첫 단계는 지금 상태 글까지) · 「중간 계획 확인 없이 연차보고서가 바뀐다」 · 실행 취소는 편집 한 번(묶음마다 반영 하나).
     1단계 창 = 구조(절·표 행·열)만 바뀌고 **내용은 넣지 않는다**, 2단계 창 = 내용이 들어간다(구분 기준 자리 + 같은 이름 자리 · 그림 · 표 칸 글자 모양) · 분석이 없거나 구조 반영 전 것이면 먼저 분석 · LLM 검토는 유료.
     그 뒤로는 구분 기준 「변경 계획」·「넣기 계획」 을 사람이 확인하지 않고 반영한다(`divApply`·`fillApply` 의 확인 창을 건너뜀). 세부 목록에서 단계마다 누를 때는 전처럼 계획을 보고 「반영」 을 눌러야 바뀐다.
  2. 연차보고서가 고치는 문서가 아니면 먼저 그 문서로 바꾼다(§11 의 단추와 같은 길 — 두 문서의 자리는 그대로).
  3. **(1단계) ① 구분 기준**: 사업계획서 값과 다르면 연차보고서의 입력 값을 사업계획서 값으로(당해 차년도도 — §11) → 변경 계획 → 반영(편집 1). 사업계획서에 저장된 값이 없어 **문서에서 읽은 값**뿐이면 그 값을 사업계획서 작업의 값으로 저장하고 이어 간다(문서는 그대로 — 확인 창에 「문서에서 읽었습니다(…)」 로 보였다).
  4. **(2단계 — ① 이 끝난 문서에서만: 아니면 「1단계가 먼저」 로 멈춤) ② 자리 연결**: 헤딩 그래프·표 구조가 **없는 문서만** 분석한다(스크립트 — `POST …/headings {first: true}`, 끝날 때까지 기다림 · 이미 있는 분석은 다시 돌리지 않는다 — spec_헤딩_추출 ② §17 뼈대 유지).
     **단, 연차보고서의 분석이 구조 반영 전 문서의 것**(**있는** 2·3단계 결과 가운데 하나라도 `meta.rev` < 구분 기준 반영 `applied.rev` — 2단계만 있고 3단계가 없는 문서도: 첫 분석은 있는 단계를 건너뛴다)**이고 스크립트만 돈 것**(`llm.requested` 아님)**이면 다시 분석한다**(`POST …/headings {stage: 2}` → `{stage: 3}`, 스크립트) — 반영으로 늘어난 절·표가 분석에 없으면 그 자리를 못 잇는다(④ ⓑ 가 이렇게 풀림 · LLM 을 돌린 분석은 안 덮는다).
     LLM 을 돌린 분석이라 안 덮은 때는 끝 글에 「헤딩·표 분석은 구조 반영 전 것(LLM 결과라 다시 안 돌림 — 늘어난 절·표는 못 이었을 수 있음)」. 분석 요청이 409(다른 헤딩 작업이 도는 중)면 그 작업이 끝난 뒤 한 번 더 건다.
     단계마다 누를 때는 다시 돌리지 않고 ② 줄 끝에 「구조 반영으로 늘어난 절·표는 헤딩·표 분석에 아직 없습니다(2단계 「한 번에 진행」 이 다시 분석)」 만 보인다(알림 — 다그치지 않음). → 연결 목록 →
     **확인 필요(묶음)나 못 정한 표(같은 표인지 — `fixed.counts.tablesOpen`: [spec_병합.md](spec_병합.md) ② §5-1 「표 짝 검토」 · 같은 날 사용자 「이 내용도 LLM 검토 단계에서」)가 있고 아직 LLM 검토 전일 때만 LLM 검토 한 번**(2026-11-12 사용자 답 「넣음」 — 유료 · 수십 초. 이미 검토했으면 안 돈다). 검토 뒤에도 남은 확인 필요는 넣지 않고 비워 둔다(§11 — 「다 매칭될 필요는 없다」). LLM 이 실패해도 멈추지 않는다(이어진 자리만 넣음 — 끝 글에 「LLM 검토는 못 함」).
  5. **(2단계) ③ 넣기 계획 → ④ 내용 반영**: 계획을 세우고 곧바로 반영(편집 1). 넣을 것이 없으면(이미 넣었거나 넣을 자리가 없음) **실패가 아니라 끝난 것**. 계획 뒤 문서가 바뀌어 409 가 나면 계획을 한 번만 다시 세운다.
     넣을 자리 = 이어진 묶음 + 같은 이름 자리(연결 목록의 `fixed.todo` — 묶음이 하나도 안 이어져도 같은 이름 자리가 있으면 넣기 계획을 세울 수 있다). 서버가 같은 이름 자리를 못 세면(`fixed.error`) ② 줄에 「같은 이름 자리 못 셈」 — 0 으로 보고 「대상 없음」 으로 끝내지 않는다(넣기 계획은 세울 수 있다).
  - **멈추는 곳**(상태 줄 `halt` · 세부 목록이 펴짐 · 끝난 단계는 그대로 남음): 사업계획서에 값이 없음 · 다른 문서를 못 읽음 · 변경 계획/반영 실패(표준 검사 422 등 — 알림 글) · 분석 실패 · 연결 목록을 낼 수 없음(문서별 까닭) · 넣기 계획/반영 실패 ·
    도는 중 단추 「멈춤」(지금 하는 일이 끝나면 멈춤) · 도는 중 다른 문서를 엶 · **도는 중 사업계획서·연차보고서 칸의 문서를 바꿈**(누를 때 확인한 쌍이 아니면 다른 계획서의 내용이 들어갈 수 있다 — astra P1) · 2단계인데 ① 이 안 끝남.
  - 끝나면 알림 「문서 프레임 작성 — 구조를 맞췄습니다 …」 · 「내용 매핑 — 연결됨 n · …」. 실행 취소는 묶음마다 한 번(1단계 = 구분 기준 반영 1 · 2단계 = 내용 반영 1 — 두 묶음을 한 번에 되돌리는 것은 없다 → 확정(§8)을 미리 해 두면 「버리기」 로).
- **할 일 프롬프트와의 관계**(§13): 「연차보고서는 사람이 확인한 뒤에만 바뀐다」 는 남는다 — 확인이 「단계마다 계획을 보고」 또는 「한 번에 진행을 누를 때 한 번」 둘 중 하나가 됐다(`jobs/plan_to_report.md` · [spec_병합.md](spec_병합.md) ② §1 에 같은 날 반영).
- 하지 않는 것: 3단계 이후(이름·내용 모두 사용자 설명 전) · 두 묶음을 한 번에 도는 단추 · 양식 맞추기의 별도 묶음 · 한 번에 진행 전체를 한 번에 되돌리기 · 도는 중인 서버 호출을 끊기(멈춤은 그 호출이 끝난 뒤) · 이미 있는 분석을 반영 뒤에 다시 돌리기(④). 취합의 두 묶음은 [spec_취합.md](spec_취합.md) ② §5에서 별도로 정의한다.

### 15. 시작 화면의 TASK 카드 (2026-11-12 사용자 요청 — ① 같은 날)

**TASK = 할 일**(`task.job` — §10)을 부르는 이름. 시작 화면(문서를 열기 전 — `#empty`)에 TASK 마다 **카드 한 장 + 로고**를 두고, 카드로 그 TASK 를 시작한다.
화면만 — 서버·API·저장 값은 그대로(있는 끝점 `POST /api/docs` · `PUT /api/works/{id}/task` 만 부른다).

- **자리**: 올리기 묶음(`.home-intro` — 제목 글 + 파일 놓는 곳) 바로 아래 `section#homeTasks` — 제목 「TASK」 + 시작 안내 노트 아이콘 + 카드 줄(`ul#taskCards`). 그 아래로 기능 소개 줄(`.home-capabilities`) → 최근 작업.
- **카드**(`button.task-card[data-task=<할 일 키>]`): `task_catalog.js`의 `TASK_CATALOG` 차례 그대로(= 일의 흐름). 할 일 목록(`WORK_TASK.job`)과 카드가 **같은 카탈로그의 이름**을 읽는다 — 카드는 이름을 「문서 / 동작」 두 줄로 갈라 보인다(이름이 그 꼴이 아니면 한 줄).
  한 장 = 로고 · 문서(작게) · 동작(크게) · 설명을 읽는 노트 아이콘 · 맨 아래 「<처음 올릴 문서> 올려 시작 →」. 노트 단추는 파일을 고르는 카드 단추와 나란한 요소로 두어 설명을 읽다가 업로드가 시작되지 않게 한다. 카드 데이터는 §16의 카탈로그에서 읽는다.

  | TASK(할 일 키) | 문서 / 동작 | 설명 | 처음 올릴 문서 | 양식 판정이 종류를 못 정했을 때 |
  |---|---|---|---|---|
  | `plan_fit` | 사업계획서 / 양식 맞추기 | 단계·차년도·기관에 맞춰 양식의 절·표를 늘리고 줄입니다. | 사업계획서 | `file = plan` |
  | `plan_merge` | 사업계획서 / 취합 | 기관이 나눠 쓴 문서의 내용을 사업계획서 하나로 모읍니다. | 취합본(내용을 모을 원래 사업계획서) | `plan` |
  | `plan_to_report` | 사업계획서 → 연차보고서 / 이관 | 사업계획서에서 필요한 내용을 뽑아 연차보고서로 옮깁니다. | 문서(둘 가운데 하나) | 안 정함(칸에서 고른다 — §11) |
  | `report_fit` | 연차보고서 / 양식 맞추기 | 단계·차년도·기관에 맞춰 양식의 절·표를 늘리고 줄입니다. | 연차보고서 | `report` |
  | `report_merge` | 연차보고서 / 취합 | 기관이 나눠 쓴 문서의 내용을 연차보고서 하나로 모읍니다. | — (준비 중) | — |

- **로고**: TASK 마다 하나 — 둥근 네모 바탕(색 = 문서) + 흰 선 그림(문서 표시 + 동작 표시). 규칙의 원본은 [design.md](../design.md) §12. 그림 = `index.html` `<symbol id="taskIcon-<할 일 키>">`, 바탕색 = `landing.css` `.task-logo[data-doc=plan|report|plan-report]`.
- **시작**: 카드를 누르면 파일 고르기(hwp·hwpx — hwp 는 서버가 hwpx 로 바꿔 받는다), **카드에 파일을 놓아도 같다**(창의 다른 곳에 놓으면 전처럼 그냥 열기 — 놓는 동안 그 카드만 파란 테).
  ① 올림(`POST /api/docs` — 같은 파일로 하던 작업이 있으면 이어 엶: §1) → ② 그 작업의 `task` 를 `{kind: rnd, job: 그 TASK, file: 양식 판정이 정한 종류(§10 「안 고른 문서는 짐작」) — 없으면 위 표의 값}` 로 저장(`project` 는 그대로)
  → ③ 새 작업이면 첫 분석(§9) → ④ **작업 내용(연구개발과제 패널 — §10)** 을 연다: 「할 일」 칸이 그 TASK 이고, 이관이면 첨부 파일 칸·단계(§11·§14), 취합이면 취합본·기관 문서 줄([spec_취합.md](spec_취합.md) ② §5). 과제 이름과 나머지 문서는 거기서 넣는다(전과 같다).
  - 이어 연 작업에 **다른 TASK 가 이미 있으면 바꾸지 않는다**(과제에 묶인 문서면 묶인 문서 모두의 할 일이 따라 바뀐다 — §10 「할 일은 과제에 하나」): 그대로 열고 알림 「이 문서는 하던 작업입니다(TASK 「…」) — TASK 를 바꾸지 않고 이어서 엽니다」 + 단추 「새 작업으로 열기」(같은 파일을 그 TASK 의 새 작업으로).
    TASK 가 비어 있던 작업이면 그 TASK 를 적고 알림 「같은 파일로 하던 작업을 이어서 엽니다 — TASK 「…」」(같은 단추).
  - docx 는 받지 않는다(알림 「TASK 는 hwp·hwpx 문서로 시작합니다」 — TASK 의 도구(구분 기준 · 헤딩·표 분석 · 첨부 파일 칸의 올리기)가 hwpx 것이다).
  - 올리는 동안 다른 카드는 받지 않는다. 작업 저장이 꺼져 있으면(`NFM_WORKS=off`) 값은 그 화면에서만(§10).
- **준비 중**: 기능이 아직 없는 TASK(지금 「연차보고서 취합」 — `TASK_CATALOG[…].soon`)는 카드가 보이되 흐리고 맨 아래 글이 「준비 중」(`aria-disabled`) — 누르거나 파일을 놓아도 시작하지 않는다(알림만). 패널의 「할 일」 목록에서는 전처럼 고를 수 있다(값만 저장 — §10).
- **좁은 창**(창이 아니라 시작 화면 폭 — `@container home`): 한 줄에 다섯 장 → 900px 아래 세 장 → 560px 아래 두 장 → 430px 아래 한 장(로고 왼쪽 · 글 오른쪽). 가로 넘침 없음.
- 하지 않는 것: 카드에서 하던 작업 고르기(그것은 최근 작업 · 작업 목록) · TASK 별 진행 중 작업 수 · 예제로 TASK 시작 · 패널 「할 일」 칸의 이름을 「TASK」 로 바꾸기(④).

### 16. TASK는 모듈의 조합 — 개발 시 함께 갱신할 계약 (2026-11-12)

**작업(work)**은 파일 하나의 저장 공간(§1), **TASK(`task.job`)**는 목적을 이루기 위해 모듈들을 정해진 순서로 사용하는 일(§10·§15)이다. 하나의 모듈을 고칠 때 그것을 쓰는 TASK도 확인한다. TASK마다 문서 처리 코드를 복제하지 않고 공통 모듈의 입력·산출물·선행조건을 연결한다.

| TASK | 입력 → 산출물 | 사용하는 모듈과 순서 | 다음 단계로 가는 조건 |
|---|---|---|---|
| `plan_fit` 사업계획서 양식 맞추기 | 사업계획서 + 과제 구성 → 구조를 맞춘 사업계획서 | 구분 기준(`division_model`·`division_plan`·`division_profiles/rnd`)의 값 확인 → 변경 계획 → 반영 | 지원 양식과 유효한 과제 구성. 계획은 읽기이며 반영 시에 문서가 바뀜 |
| `report_fit` 연차보고서 양식 맞추기 | 연차보고서 + 과제 구성 → 구조를 맞춘 연차보고서 | 같은 구분 기준 모듈, 양식별 처리만 다름 | 위와 같음. 이관의 원본 문서나 내용 매핑이 필요하지 않음 |
| `plan_to_report` 사업계획서 → 연차보고서 이관 | 내용이 있는 계획서 + 보고서 서식 → 필요한 내용이 들어간 보고서 초안 | 1단계: 계획서 값에 맞춰 보고서 구조 반영. 2단계: 헤딩·표 분석(`heading_runs`·`heading_graph`·`heading_tables`) → 자리 연결(`merge_pairs`·`merge_fixed`·`merge_llm`) → 빈 자리 검토(`merge_gaps`)·표 대응(`merge_table_map`) → 넣기 계획·반영(`merge_fill`·`merge_tables`·`merge_convert`, API `merge_api`) | 두 문서와 기준 값 확보 → 1단계 완료 → 사용할 분석 확보 → 연결 결과 → 유효한 넣기 계획. 원본은 유지, 모든 자리를 채우는 것이 목표는 아님 |
| `plan_merge` 사업계획서 취합 | 취합본 + 배포 기준본에서 나온 기관 문서들 → 취합본 하나 + 자리·반영 기록 | 1단계: 구조 반영 → 분석·배포 기준본(`merge_gather_frame`). 2단계: 기관마다 자리 연결·작성 내용 판정(`merge_gather`) → LLM 검토(`merge_gather_llm`) → 계획·반영·틀 맞춤(`merge_gather`·`merge_gather_fit`, API `merge_gather_api`) | 현재 과제 구성에 맞는 배포 기준본 → 기관 문서의 반영할 기관 지정 → 기관별 연결·계획. 겹친 내용을 자동으로 덮지 않음 |
| `report_merge` 연차보고서 취합 | 준비 중 | 실행 모듈 없음 | 카드의 준비 중 표시만으로 실행 가능하다고 판단하지 않음 |

업무 전제의 원본은 [이관 프롬프트](../jobs/plan_to_report.md)와 [취합 프롬프트](../jobs/plan_merge.md), 개별 알고리즘·저장·API의 상세는 각 기능 사양서다. 위 표는 **변경 영향을 찾는 지도**이며 그 상세를 다시 정의하지 않는다. 취합은 기관 문서마다 진행하므로 한 문서의 기관 미지정·겹침이 다른 준비된 문서까지 막는 것으로 해석하지 않는다.

- **TASK 정의**: `app/static/task_catalog.js`의 `TASK_CATALOG`가 화면의 이름·순서·처음 올릴 문서·준비 중 여부·필요한 문서 역할의 원본이다. `app.js`의 시작 카드(`HOME_TASKS`)·선택 목록(`WORK_TASK.job`)·이관 문서 칸(`TASK_FILES`)·취합 입력(`TASK_GATHER`)은 그 정의에서 파생한다. 서버 `TASK["job"]`의 허용 키와 일치해야 한다. `task.job` 키와 문서 역할(`plan`·`report`·`part`)은 저장 계약이므로 화면 이름을 바꾼다고 바꾸지 않는다.
  같은 파일의 `TASK_STAGE_META`는 이관·취합이 공유하는 1·2단계 이름의 원본이다. 실제로 쓰는 세부 모듈·완료 조건·실행은 이관의 `taskSteps`·`taskRunSteps`와 취합의 `gatherSteps`·`gatherRunAll`이 각각 맡는다. 사용자에게 보이는 같은 단계 이름과 서로 다른 문서 처리 규칙을 혼동하지 않는다.
- **진행 상태**: 완료는 API가 돌려준 현재 결과와 선행조건으로 계산한다. 클릭한 사실이나 진행 안내를 눌렀다는 이유로 완료를 기록하지 않는다. 단계 안내는 해당 묶음을 펼쳐 이동하는 탐색이며 실행은 기존 「한 번에 진행」·세부 단추가 맡는다. 문서 선택/준비·처리 단계·준비 중 기능을 구별하고, 오류·대기 이유·다음 행동은 항상 읽을 수 있게 둔다.
  과제 구성을 바꾸거나 문서 선택을 풀어 앞 조건이 다시 필요해지면, 이전 내용 매핑 완료 기록보다 **지금 선행조건**을 우선한다. 순서 안내·묶음 상태는 앞 단계를 현재로, 뒤 단계를 대기로 표시한다. 취합의 「준비」는 취합본이 없으면 문서 선택으로, 취합본은 있고 과제 구성 값이 없으면 1단계를 펼쳐 과제 구성을 확인할 수 있는 곳으로 이동한다.
- **모듈 변경 시**: 위 표로 영향받는 TASK를 고른 뒤, 입력/출력·완료 조건·결과가 낡았을 때 다시 읽는 경로(문서 전환·구조 반영·재계획·실행 취소)를 함께 확인한다. 화면의 완료 판정과 자동 순차 실행이 서로 다른 선행조건을 만들지 않게 한다. 새 TASK는 실제 처리 모듈·입력 역할·미제공 상태를 함께 등록하고 해당 `jobs/` 전제 및 로고를 확인한다.
- **검증 선택**: 카탈로그를 바꾸면 `tests/test_task_catalog.py`(서버 허용 키·실제 저장 API·입력 역할·카드 이름/로고 계약, Node.js 필요) + 시작 화면(`home`)·작업 선택(`task`). 이관 흐름은 `task`·`task_run`, 취합 흐름은 `gather`, 공통 머리/도움말은 `panel_head`·`note_help`. 구분 기준·분석·병합 모듈을 바꾸면 영향받는 모듈의 pytest도 함께 고른다. UI 검사는 `tools/run_ui_gates.py`로 격리된 임시 서버에서 병렬 실행하며 pytest와 동시에 돌리지 않는다(CLAUDE.md).
