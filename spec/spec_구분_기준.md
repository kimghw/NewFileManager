### 3. 자리 찾기 — 두 소스 → 공통 후보

```text
프로파일 탐지(FMM find 이식) ─┐
                              ├→ 공통 후보 → 값·물리 범위 검증 → 변경계획 → 반영
헤딩 분석(고정한 실행 n) ─────┘   (division_sources/heading.py)
```

- **1차 소스 = 프로파일 탐지**(결정적). 헤딩 추출 결과(division 라벨·인스턴스·repeats·3단계 행헤더/열헤더 경로)는 **후보**일 뿐 실행 명령이 아니다 — 인스턴스 `members` 는 헤딩 후보 소속이지 본문·표·그림을 포함한 복제 범위가 아니고, 3단계 `repeats` 는 헤더 서명 유사성이지 복제할 행·열 단위가 아니다.
- 두 소스가 **같은 문서 버전·같은 물리 범위·같은 구분 기준**을 가리킬 때만 근거를 합치고, 경계나 값이 다르면 보류(일치만으로 자동 승인하지 않음).
- 분석 실행이 없으면 그 소스는 「근거 없음」 — 초기화 때문에 LLM 실행을 필수로 만들지 않는다. **반영 중 LLM 호출 없음**.
- 오래된 결과 방어: 계획에 고정한 `baseRev`·스냅샷 해시·프로파일 버전·설정 해시·분석 실행 번호를 반영 직전 잠금 안에서 다시 확인, 달라졌으면 **409 재계획**. 헤딩 실행의 `sha256` 은 원본 파일 해시고 오래됨 판정은 `rev` 비교라 쓰기 안전장치로 쓰려면 보강 필요(④ — heading_runs 소관).
- **구현(2026-11-09, `app/division_plan.py`)**: 1차는 프로파일 탐지만(헤딩 후보 소스는 ④). 계획 = 세션 잠금 안에서 `struct.snapshot/restore` 로 독립 사본을 뜨고(같은 블록 id·원본 기준) **잠금 밖**에서 사본에 `profile.apply` 를 끝까지 돌린 뒤,
  반영 전 후보(`candidates`)와 반영 뒤 후보·남은 블록·오류로 자리마다 상태를 매김(`division_model.status_of`) + 지워진 글 문단 목록(`deleted`) + 글 바꿈(`changes`) + `baseRev`·`sha256`·프로파일 버전·설정 해시.
  같은 값을 이미 전체 반영한 문서면 `rebuild=False`(FMM `divisionsDone`). 사본 문서는 계획에 붙여 두었다가(세션마다 마지막 계획 하나, 메모리) **반영 때 그대로 세션 문서가 된다** — 엔진을 두 번 돌리지 않는다.

### 4. 반영 = 공통 편집 트랜잭션 (`server.py` `_edit` 의 공통부를 추출·강화)

- 한 번의 반영 단위: **문서 버전 확인 → 스냅샷 1개 → 선택한 변경 전체 실행 → 의미상 완료 조건 확인(미처리 잔여 없음) → 전체 문서 구조 검사 1회(hwpx OWPML · docx OOXML 참조 규칙 — 원본 대비 판정) → 성공이면 undo 1개·rev +1·로그 1줄**.
- 실행 중 예외·예상 밖 미처리·검사 실패 = **전체 복원**(FMM 은 묶음 실패를 `errors` 에 넣고 계속해 삭제 뒤 복사 실패가 앞선 변경을 남길 수 있었고, 6차례 뒤 잔여를 확인하지 않아 `errors=[]` 가 완료를 뜻하지 않았음). 사전에 명시적으로 제외한 자리는 실패와 구분.
- 자리별 상태 5종(§2) — `unresolved` 를 「완료」로 보이지 않는다. 아무 변화가 없으면 undo·rev 를 늘리지 않는다. 별도 무검사 경로는 만들지 않는다.
- **입력 중인 값**과 **현재 문서에 마지막으로 적용한 값**을 분리 저장. 적용 상태·문서 안 값 대응 정보는 문서와 함께 작업에 저장하고 undo 로 복원(`_snap` 에 구분 설정·적용 상태 포함 — 지금은 없음). 대량 삭제 전 **반영 직전 체크포인트를 디스크**에.
- 로그 한 줄(`log.jsonl` kind `divisions`) = 작업 id · planId · 계획 해시 · 전후 rev · 변경 수 · 검사 요약; 상세 변경 목록은 결과 파일(`works/<id>/divisions/<n>.json`).
- 출력파일 검증(한글 PDF 비교)은 반영 뒤 재개방·다시 저장·PDF 확인이지 구분 값의 의미상 정확성·내용 귀속을 검증하지 않는다.
- **화면**: 떨어진 여러 자리를 한 번에 바꾸므로 `applyTops`(바뀐 첫 블록~마지막 블록 범위 교체, `app.js` 1051)에 그대로 연결하면 사이의 안 고친 블록이 화면에서 빠질 수 있다 → 1차는 반영 결과 요약을 받은 뒤 **문서 뷰를 한 번 다시 읽고 스크롤·선택 복원**(`reloadDoc`). 여러 연속 구간을 각각 교체하는 응답 계약은 후속.
- **구현(2026-11-09, `server.py`)**: `_edit` 의 공통부를 `_transact(s, run, op, req, check)` 로 뽑았다(스냅샷 `_snap` → `run()` → `check`(기본 `_hosts_check` = 닿은 문단만, 구분 기준은 `_full_check` = `check_doc` 문서 전체 · 원본 대비 개수 비교) →
  실패면 `_rollback`·`rejected` 기록·422 → undo 1·글/집합 갱신·`_bump`(rev +1·기록 1줄 + `run()` 의 `log` 칸)). `_edit` 의 호출 계약은 그대로. 구분 기준 반영의 `run()` = `s.doc = 계획의 사본`.
  `_snap`/`_rollback` 이 `s.division["applied"]` 를 함께 묶고 되돌린다(실행 취소 = 반영 취소), `_persist` 상태에 `division {settings, applied}`(다시 열면 복원), 계획은 저장하지 않음(메모리 — 서버를 다시 켜면 409 재계획).
  할 일 없는 계획(`groups`·`changes` 없음)은 반영해도 undo·rev 를 안 올린다(`nothing: true`). 기록: `divisionPlan`(rev·planId·설정 해시·요약) · `divisions`(= 반영, planId·요약·OWPML) · 상세는 `works/<id>/divisions/<planId>.json`(`works.add_detail`).

### 5. 내용 보호 (astra P1)

- 1차 = **지원하는 빈 양식의 초기화**로 한정. 작성본 재구성은 `기존 항목 ↔ 값 id` 대응을 먼저 확정한 뒤(개수와 이름 차례만으로 처리하지 않음).

- 본뜨기 정책 3종(§2 변경계획)을 자리마다 고른다.
- **항목 꼴 맞춤**(2026-11-10 — 사용자 "중간 줄이 맞지 않네"): 문단 묶음의 마지막(자리표시) 항목이 **라벨 바로 뒤에만** 빈 문단을 갖고 앞 항목들은 모두 라벨 다음이 글 있는 문단이며
  그 빈 문단 뒤 글이 앞 항목들의 라벨 다음 글과 같은 꼴(`_content`)이면, 그 빈 문단은 양식의 군더더기로 본다(KEIT 연구개발계획서 2-2 「[공동연구개발기관N(기관명 기입)]」 아래 7pt 빈 줄 —
  주관·공동1 엔 없음). 항목 길이(`_last_end` 의 cap)에 안 세어 항목이 앞 항목과 같은 길이(「라벨 → o → 빈 줄」)가 되게 하고, 반영 때 남길 항목(이름을 넣을 것·본뜰 것)에서 **지운 뒤**
  본뜬다(`core._stray_blanks`·`_unstray`) — 빈 문단만 지우므로 지워지는 글은 없다. 모든 항목이 같은 꼴(「(2) 일자리 창출 계획」처럼 셋 다 「라벨 → 빈 줄 → o」)이면 손대지 않는다.

- 한계 = 「임의 문서의 무손실 복제」 계약이 아님: hwpx 사본에서 `DROP_ON_COPY`(구역·단·머리말·꼬리말·쪽 번호·`ole`·`chart`·`video`)와 줄 배치 캐시 제거, docx 사본에서 북마크·`w:sectPr` 제거 → **복제 범위 안 미지원 객체·교차 참조를 사전 검출해 그 자리를 `unsupported` 로 보류**.
  블록 id 매핑·병합 셀 경계·새 문단의 원본 출처를 계약에 넣는다. 재이식·믹스인 이동은 우선순위 낮음.

### 8. 화면

- **기관 입력 줄(2026-11-10)**: 역할은 「주관」「공동」으로 줄여 이름 입력칸 앞에 두고, 비영리·삭제와 한 줄로 정렬한다. 좁은 패널에서도 역할을 입력칸 위로 올리지 않는다. 보조기기용 이름과 삭제 도움말에는 기관 순번을 유지한다.
- **설정 화면 개편(2026-11-10)**: 지원 양식은 작은 요약으로 표시한다. 기본 설정은 「1. 단계·차년도」「2. 기관 구성」으로 나누고, 단계별 전체 차년도 범위와 기관 합계를 보여 준다. 사업기간·기타 기관은 「추가 설정」에, 저장한 기준 불러오기·저장·삭제는 별도 접이식 영역에 둔다. 문서에서 읽기는 입력 보조 행동, 「변경 계획 보기」는 주요 행동으로 구분한다.
- 「문서 반영 상태」는 입력값과 마지막 반영값을 구분하며 입력을 바꾸면 바로 갱신한다. 접은 영역·선택한 저장 항목은 행 추가/삭제 후에도 유지하고, 계획 계산 중에는 설정 입력을 잠근다. 값이 바뀐 이전 계획은 반영할 수 없게 안내한다. 실제 반영은 기존 2열 계획 검토·확인 흐름을 유지한다.

- **3열 패널 탭 「구분 기준」**: 프로파일·지원 양식 판정 결과 · 값 입력(단계별 차년도, 기관 목록 + 역할·비영리) · 저장한 기준(프리셋, FMM 가져오기) · 현재 문서 적용 상태(마지막 적용 값·rev·「입력 중 값과 다름」) · 「계획 보기」.
- **2열 「바꿀 자리」**(헤딩 추출 열과 같은 자리 — 모드 이름과 돌아갈 위치를 분명히): 자리마다 상태(적용/이미 맞음/제외/지원 안 됨/미해결) · 탐지 근거 · 추가·삭제될 내용 · 자리별 선택 · 「반영」·「이번 반영 취소」. 항목을 누르면 1열 문서가 그 자리로 가고 열은 유지(사용자 선호 — 모달 금지).
- 「가져오기 → 초기화 → 편집 → 검증」 흐름은 **선택 가능한 안내**로만(초기화가 필요 없는 문서에 강제 단계로 두지 않음).
- **구현(2026-11-09, `app.js` 끝 「구분 기준」 절 · `index.html` `#tabDiv`/`#paneDiv` · `style.css` `.dv-*`)**: 3열 탭 = 「양식」(판정·지원 여부) · 「구분 값」(단계 칩마다 차년도 수 + 「+ 단계」, 주관·공동 줄마다 이름·비영리·×, 접는 「선택」 = 사업기간·당해 차년도·외 기관·국외기관·위탁·세부과제(쉼표 목록),
  저장한 기준 select + 불러오기·저장…·지우기, 「문서에서 읽기」, 「계획 보기」(10~20초, 값·뺀 자리를 보내 계획) · 「바꿀 자리 열기」) · 「이 문서에 적용한 값」(반영됨 rev·때·값 요약·상태 배지, 입력 중 값과 같음/다름, 계획 있음/오래됨, 「이번 반영 취소」).

### 11. 문서 표시 · 추가한 자리 · LLM 재검토 (2026-11-10 사용자 요청 — ① 같은 날)

- 「문서 표시」 카드는 제목·표시 전환·색상 범례·행동 버튼만 기본 표시한다. 긴 사용 설명과 묶음/전체 문단 수·편집 차례·우클릭 안내는 생략하고, 문서 변경으로 다시 읽기가 필요한 상태·로딩·오류·빈 결과는 필요한 때만 표시한다.
- **문서 표시**(「구분 기준」 탭 맨 위 「문서 표시 보기/감추기」, 이 브라우저에 기억 · 기본 감춤): 문서의 문단마다 **어느 구분 기준 자리에 드는지** 색으로 보인다. 자료 = `GET …/divisions/members`
  (계획 없이 `find` 만 — 양식 0.3초): 묶음마다 key·구분·종류·항목(라벨 id·값 글·항목 안 문단 id 전부)·출처. 문단이 여러 묶음에 들면(단계 > 차년도 > 세부과제 > 기관) **가장 안쪽** 구분의 색,
  라벨 문단은 왼쪽 띠 + 진한 색, 도움말(title)에 겉→안 소속 전부. 어느 묶음에도 안 드는 문단은 그대로 = 「구분 기준에 속하지 않음」. 범례(구분별 색·묶음/문단 수)·「다시 읽기」(편집 차례 기준)·
  「추가한 자리 N」·「LLM 재검토」 단추가 같은 줄. 쪽을 다시 나누거나 문서를 다시 읽으면 표시를 다시 입힌다(`paginate` 끝).
- **추가한 자리(hint)** = 사용자가 문서에서 **오른쪽 단추 → 「구분 기준 자리로 추가…」** 로 표시한 **라벨 문단 하나**: `{id, para, dim, value, note, by: user|llm, at, reason}`. dim = 단계·차년도·단계-차년도·
  세부과제·기관 또는 **기타(이름 직접 입력 — 표시만)**. 값은 비우면 서버가 글에서 읽는다(`core._key`). 세션 `division.hints` 에 두고 작업 폴더에 저장·복원(settings·applied 와 같은 길), 바뀌면 계획은 버린다.
  API `POST …/divisions/hints`(추가·고침) · `DELETE …/divisions/hints/{id}` · members 응답의 `hints`. 2열 「구분 기준 — 추가한 자리」(headsDlg kind `divisions-hints`): 출처·구분·값·문단 글·엔진 반영 가능 여부·까닭·지우기, 줄을 누르면 문서의 그 문단.
- **엔진 연결(꼴 규칙)**: 라벨 판정은 글 꼴 기반이라 id 하나를 억지로 넣으면 사본(새 id)을 다음 차례에 못 알아본다. 그래서 hint 는 **그 문단의 꼴(`_shape`)·구분(`_key`)을 「라벨 꼴」로 등록**하고(`find(..., hints=)`),
  같은 꼴·같은 구분의 문단은 어디서나 라벨로 본다(`PARA_LABEL`·`LABEL_MAX` 관문 해제, `NOT_LABEL` 은 유지). 값 차례(1,2,… / 주관,공동1,…)·2개 이상 등 묶음 규칙은 그대로 — 혼자면 묶음이 안 되고(표시만),
  LLM 재검토가 형제를 찾아 채우는 것이 그 길. 글에 값 낱말이 없거나(`_key` None) 기타 구분이면 **표시만**(반영 계획에 안 듦 — 2열에 까닭). 묶음에 `hinted` 표시 → 계획 2열에 「추가」 배지.
- **LLM 재검토**(`POST …/divisions/llm_review`, 동기 — 수십 초, `app/division_llm.py`): 보내는 자료 = 구분 값·묶음 요약(라벨 글·id)·추가한 자리(앞뒤 문단 글 포함)·헤딩 개요(levels)·**라벨이 아닌데 값 낱말이 있는 문단**
  (후보 — id·글·그릇). 답 = `revisions[{action add|change|remove, hintId, para, dim, value, reason}]` + summary(JSON schema, 입력에 있는 id 만). 서버가 검증해 **hint 층에만** 반영(자동 묶음은 안 건드림):
  add → by llm 새 hint, change → dim·value·reason 고침(출처 유지), remove → llm 것만 지움(사용자 것은 `llmNote` 로 제안만). 호출 기록 `divisions/llm_<n>.json`·로그 `divisionLlm`. 결과는 2열 목록·문서 표시에 바로.
- 1차 제외: 표 칸 라벨 hint 의 엔진 연결(표시만), 자동 묶음의 삭제·범위 고침(LLM 은 hint 층만), hint 값의 수동 지정이 글과 다를 때의 엔진 반영(엔진은 글을 따름 — 2열에 「글에서 읽은 값」 병기).

### 12. 역할 칸 행 묶음 — 「이름 (주관)」·「이름 (공동)」 칸 (2026-11-10 사용자 보고 「이 테이블만 빠진듯」 — ① 같은 날)

- **대상**: 머리 칸에 「기관」과 「역할」(또는 「주관」)이 함께 있는 열 — 양식 7-1 (3) 가. 참여연구자 현황의 「소속 기관 (역할)」, 신규채용 실적 및 계획 표의 「기관명 (주관/공동)」 — 에서
  「이름 (주관)」·「이름 (공동)」 칸이 위아래로 맞닿아 이어지는 표. 그 칸들이 **기관 행 묶음**(표 행 · 기관)이 된다.
- **항목 = 기관 하나** = 그 칸이 걸친 행 전부(사람 행 포함). 같은 이름·역할 칸이 이어지면 한 기관(양식 예시 「KETEP (공동)」 두 칸 — 사람마다 칸을 나눈 것). 값 = 「(주관)」 → 주관, 「(공동)」 → 나온 차례로 공동 1, 2, ….
- **칸 라벨 묶음과의 경계**: 라벨 낱말이 든 칸(빈 양식 신규채용 표의 「주관연구개발기관명 (주관)」)은 지금까지처럼 칸 라벨 규칙 몫이고, 그 열에 라벨 칸이 하나라도 있으면 이 규칙은 물러난다.
  반영이 이름을 넣은 뒤(「인텍 (주관)」)에는 이 규칙이 다시 찾는다 — 신규채용 표가 반영 뒤에도 기관 자리로 남는다(전에는 사라졌음).
- **반영**: 항목 수를 기관 수에 맞춤(공통 계획 — 본뜰 항목 = 가장 큰 공동 항목 중 뒤, 남으면 끝에서부터 지움) · 이름 = 그 자리 기관 이름(이름이 없으면 기본 이름 「주관기관(미입력)」·「참여기관k」 —
  8-3 기관-연도 표와 같게), 역할 괄호는 그대로(주관 항목을 본떠 공동이 된 사본만 「(공동)」) · 행을 늘리거나 줄였으면 「번호」 열을 1부터 다시(그 열 칸이 모두 숫자일 때만).
  사람 행의 예시 글(성명·직위·계상률)은 손대지 않는다 — 사본은 본뜬 항목의 예시를 따라간다(② §5 「양식 안내·예시 유지」).
- **그대로 두는 경우**(지원 안 됨): 「(주관)」이 처음이 아니거나 둘 이상 · 같은 이름이 떨어져 두 번 · 이름 칸에 **구분 값에 없는 이름**(빈 칸·양식 예시 「KEIT·KIAT·KETEP·OO대학교」·기본 이름 말고)이 있음 —
  작성한 표로 보고 건드리지 않는다(8-3 기관-연도 표의 「구분 값과 어긋난 표」와 같은 뜻). 그래서 반영 뒤 기관을 빼거나 이름을 바꾼 값으로는
  이 표가 다시 맞춰지지 않는다 — 「이번 반영 취소」 뒤 다시 반영(④).
- **이 보호의 범위**: 「값에 없는 이름이 표에 있을 때」뿐이다. 표의 이름이 모두 값에 있으면 다른 묶음과 같이 **자리 차례**로 맞춘다 — 값에서 기관 차례를 바꾸거나 중간에 기관을 끼우면 이름이 자리 차례대로
  다시 쓰여 사람 행이 다른 기관 이름 아래 놓이고, 늘릴 때 사본은 본뜬 항목 바로 뒤에 들어가 그 뒤 항목이 다음 기관 이름을 받는다. 빈 양식(예시 행)에서는 문제가 아니지만 작성한 표의 내용 귀속은 지키지 못한다(② §5 — 1차는 빈 양식, ④).

### 13. 빠진 자리 검토 — LLM 이 묶음 밖 표·문단을 본다 (2026-11-10 사용자 「LLM 이 리뷰/검증하는 과정이 없나?」 → 「추가한다」 — ① 같은 날)

- **목적**: 스크립트(글 꼴 규칙)가 놓친 구분 기준 자리를 LLM 이 찾아 **후보로 보인다**. 판정만 — 문서·자동 묶음·추가한 자리·계획을 건드리지 않는다(② §3 「반영 중 LLM 호출 없음」 그대로).
  §11 「LLM 재검토」(표시한 자리의 형제 찾기)와 다른 동작이고, 표시한 자리가 하나도 없어도 돈다. 이 끝점은 사용자가 누를 때만 돈다(한 번에 수십 초·호출 비용) —
  새 작업의 첫 분석만 §14 의 취합 검토로 이 검토를 한 번 저절로 돌린다([spec_작업.md](spec_작업.md) ② §9, 2026-11-10 사용자).
- **보내는 자료**(`division_llm.missing_data` — 잠금 안에서 만들고 호출은 잠금 밖): 구분 값 · 지금 묶음 요약(구분·종류·라벨 처음 2개) ·
  **어느 묶음 항목에도 안 든 본문 바로 아래 표** 중 제목·머리 두 행·첫 열·칸 글에 구분 낱말(기관·주관·공동·위탁·단계·차년도·년차·연차·세부)이 있는 것(「작성요령」 상자와 칸 2개 이하 표는 뺌, ≤ 80개 —
  id·크기·제목·둘러싼 헤딩 2개·머리 칸·첫 열 칸·낱말이 든 칸 표본) · **묶음 밖 본문 문단** 중 구분 낱말이 있는 짧은 줄(빈칸 빼고 ≤ 60자, ≤ 120개 — id·글·헤딩·바로 다음 블록).
  묶음 **안**에 든 표·문단, 묶음을 품은 표, 칸 안 중첩 표는 보내지 않는다(이미 어느 구분의 자리 — 그 안에서 빠진 다른 구분 기준은 1차 제외). 문단 길이는 「※」 주석을 뗀 글로 센다.
  빈 양식 실측: 표 27 · 문단 31 · 프롬프트 1.6만 자.
- **판정 기준**(계약 `MISSING_CONTRACT`): 내는 것 = 행·열·절이 기관·단계·차년도 값마다 되풀이되어야 하는 곳. 내지 않는 것 = 작성 안내·예시 상자, 기관·단계로 나뉘지 않는 건·실적 목록, 값 하나만 적는 칸,
  문장 속 낱말, 합계 줄. 덧붙인 세 규칙(실제 호출로 고침 — ③): ⓐ **사람·건 목록이라도 기관(단계·차년도) 칸이 행을 묶으면 자리**(역할이 붙은 기관 값·값마다 다른 기관 이름이 위아래로 이어짐 —
  사용자가 보고한 참여연구자 현황이 이 꼴, ① 2026-11-10) ⓑ 제목 줄과 그 아래 표가 한 벌이면 **제목 줄만** 낸다(표는 딸린 것) ⓒ ⓐ 에 걸려도 **내지 않는 것**(사용자 결정 ① 같은 날 「편성도·수행실적 표는 필요 없음」):
  지난 실적·이력 목록(수행실적·기술이전·사업화 실적·지식재산권) · 편성도·조직도 꼴 표 · 작성 예시 표(기관명 칸이 「AAAAA」 같은 예시 글자뿐).
- **답**(JSON schema): `missing[{id, dim, pattern(무엇마다 무엇이 되풀이되는지 한 줄), reason(한 문장), confidence high|medium|low}]` + `summary`. 서버가 **보낸 id 만** 받고(모르는 id·중복은 건너뜀)
  종류·제목·글을 붙여 확신 순 → 문서 순으로 돌려준다.
- **API**: `POST /api/docs/{id}/divisions/llm_missing` `{effort?}` → `{missing[{id, kind: table|paragraph, dim, dimName, title, text, size(표 크기), path(둘러싼 헤딩), pattern, reason, confidence}], skipped[{…, why}], summary, sent{tables, paragraphs}, call, detail, rev}`.
  보낼 표·문단이 없으면 호출 없이 빈 결과 · 답이 없으면 502(기록은 남김) · 기록 `divisions/missing_<t>.json` · 로그 `divisionMissing`. 세션 상태(rev·계획·추가한 자리)를 바꾸지 않는다.
- **화면**: 「문서 표시」 줄의 「빠진 자리 검토」 → 2열 「구분 기준 — 빠진 자리 후보」(headsDlg kind `divisions-missing` — 모달 아님): 「LLM 검토 실행」 · 결과 표(확신·구분·종류·자리·되풀이 꼴과 까닭) ·
  줄을 누르면 문서의 그 표·문단으로 · **문단 후보는 「자리로 추가」**(§11 추가한 자리로 — 엔진 꼴 규칙에 연결) · **표 후보는 표시만**(표 규칙은 엔진에 사람이 넣는다 — §12 가 그 예).
  결과는 검토한 편집 차례 기준(문서가 바뀌면 「문서가 바뀜 — 다시 검토」), 문서를 닫으면 화면에서 사라진다(기록 파일은 남음).
- 「자리로 추가」 단추는 구분이 단계·차년도·단계-차년도·세부과제·기관인 문단 후보에만 난다(LLM 이 기타로 낸 문단은 단추 없음).
- 1차 제외: 묶음 안에서 빠진 다른 구분 기준(차년도 묶음 항목 안의 기관 되풀이 등) · 표 후보의 엔진 자동 연결 · 이 끝점 결과의 세션 저장·복원(§14 의 취합 검토는 남긴다) · 반영 계획과의 연동(계획 2열에 후보 병기).

### 14. LLM 검토 — 두 검토를 함께 돌려 한 목록으로 (2026-11-10 사용자 「검토만 2가지는 일단 병렬로 해서 최종 취합」 — ① 같은 날)

- **무엇**: §11 재검토와 §13 빠진 자리 검토를 **한 번에, 동시에** 돌리고 결과를 한 목록으로 합친다. 두 검토의 계약·자료·검증(`division_llm.ask`·`apply_revisions` · `ask_missing`·`check_missing`)은 그대로 쓴다.
  재검토는 표시한 자리가 하나 이상일 때만, 빠진 자리 검토는 보낼 표·문단이 있을 때만 돈다(안 돈 쪽은 까닭을 `why` 에).
- **API**: `POST /api/docs/{id}/divisions/review` `{auto?: bool, effort?}`.
  자료는 잠금 안에서 한 번에 만들고(같은 `rev` · 같은 묶음), 호출은 잠금 밖 **스레드 둘**, 재검토의 반영(추가한 자리 층 — §11)은 잠금 안에서 `rev` 가 그대로일 때만 — 그 사이 문서가 바뀌었으면 재검토는 반영하지 않고
  `errors.review`, 빠진 자리 후보는 판정이라 그대로 돌려준다(화면이 「문서가 바뀜」). 부른 검토가 모두 답이 없으면 502(기록은 남김), 한쪽만 답이 없으면 `errors` 에 적고 다른 쪽 결과로 200. 이미 돌고 있으면 409.
  응답 `{at, rev, ran{review, missing}, why{review?, missing?}, errors{review?, missing?}, review{applied, skipped, summary, call} | null, missing{missing, skipped, summary, sent, call} | null, items, costUsd, ms, hints, detail}`.
  - **취합 `items`**(`division_llm.merge_review`): `[{id(문단·표 id), kind paragraph|table, sources[review|missing], dim, dimName, text, title, size, path, pattern, reason, confidence, action(add|change|remove — 재검토), value, hintId, note}]` —
    재검토가 반영한 것 먼저(응답 차례, 같은 문단의 여러 고침은 한 줄), 이어서 빠진 자리 후보(확신 순). **같은 문단이 둘 다에 있으면 한 줄**(`sources` 둘 — 재검토의 구분·값에 빠진 자리 검토의 꼴·확신을 붙임).
  - `auto: true`(새 작업의 첫 분석 — [spec_작업.md](spec_작업.md) ② §9): 이미 검토 결과가 있거나(`done`) 지원 양식이 아니거나(`unsupported`) LLM 연결이 없으면(`llm`) 호출 없이 `{skipped, review}`.
  - **결과를 남긴다**: 마지막 결과(위 응답에서 `hints`·`detail` 뺀 것)를 세션 `s.division["review"]` → `state.json` `division.review` · `GET …/divisions` 의 `review`(도는 중이면 `reviewing: true`).
    화면을 새로 고치거나 작업을 다시 열어도 남는다. 실행 취소 묶음(`_snap`)에는 넣지 않는다 — 결과에 검토한 `rev` 가 있어 문서가 바뀌면 화면이 「문서가 바뀜 — 다시 검토」. 확정·복원에서도 그대로 둔다.
    상세(자료·프롬프트·응답)는 `divisions/review_<t>.json`, 기록 `divisionReview`{auto, ran, applied, found, items, ms, costUsd, errors?}.
  - 낱개 끝점 `llm_review`·`llm_missing` 은 그대로(하나만 다시 돌릴 때 — 그 결과는 세션에 남기지 않는다, §13).
- **화면**: 「문서 표시」 줄의 「LLM 재검토」 단추 자리에 **「LLM 검토」**(결과가 있으면 「검토 결과 N」, 도는 중 「LLM 검토 중…」) → 2열 「구분 기준 — LLM 검토 결과」(headsDlg kind `divisions-review`):
  위에 두 검토의 요약(반영·건너뜀·후보 수·안 돈 까닭·시간·비용)과 LLM 판단 글, 한 표(출처 · 확신 · 구분 · 종류 · 자리 · 꼴과 까닭 · 동작 — 빠진 자리의 문단 후보는 「자리로 추가」, 재검토 줄은 「반영됨」),
  아래 「LLM 검토 실행」/「다시 검토」. 줄을 누르면 문서의 그 자리로. 「추가한 자리」·「빠진 자리 후보」 목록과 그 안의 낱개 실행 단추는 그대로이고, 취합 실행의 결과는 그 두 목록에도 들어간다.
  다른 화면(새로 고치기 전)이 시작한 검토가 도는 중이면 5초마다 상태만 읽어 단추 글을 고친다(입력 폼은 다시 그리지 않음).

### 15. 이름 든 기관 제목 줄 · 사업화 절 · 외 기관 절 (2026-11-10 사용자 「판단되는 곳은 다 넣어줘」 — ① 같은 날)

빠진 자리 검토(§13)가 낸 후보 가운데 사용자가 자리로 넣기로 한 세 가지. 모두 `rnd/core.py` 의 자리 찾기 규칙이다(프로파일 VERSION 3).

- **이름 자리는 라벨 꼴에서 뺀다**: 「…기관(이름)」의 괄호 안과 「…기관 : 이름」의 쌍점 뒤는 꼴(`_shape`)을 견줄 때 지운다. 그래서
  ⓐ 반영이 이름을 넣은 뒤에도 「[주관연구개발기관(김거화)]」·「[공동연구개발기관1(이현미)]」·「주관연구개발기관(김거화)의 장」 들이 같은 꼴로 묶인다 — **반영 뒤에도 기관 절이 문서 표시에 보이고**,
  기관을 더한 값으로 다시 계획하면 그 절들이 늘어난다(전에는 이름 때문에 꼴이 갈려 묶음에서 사라졌다 — FMM ④ 「이름만 남은 라벨」).
  ⓑ 자리표시가 서로 달라도 묶인다 — 사업화 추진전략의 「[주관연구개발기관 : 기업명1]」·「[공동연구개발기관 : 기업명2]」(제목 줄 + 5x2 표 한 벌)가 기관 문단 묶음이 된다. 빈 양식에서 새로 생기는 묶음은 이것 하나.
- **값에 없는 이름이 라벨에 있으면 그대로**(`_label_fit` — §12 「그대로 두는 경우」·8-3 기관-연도 표와 같은 뜻): 이름 든 라벨이 묶음이 되면서 작성한 문서의 기관 절도 잡히게 되므로, 라벨의 이름(자리표시 「기관명 기입」·「기업명n」,
  기본 이름 「참여기관k」·「주관기관(미입력)」은 이름이 아님)이 구분 값의 기관 이름에 없으면 그 묶음은 지원 안 됨으로 둔다. 따라서 **반영 뒤 기관 이름을 바꾸거나 기관을 뺀 값**으로는 이 절들이 다시 맞춰지지 않는다 —
  「이번 반영 취소」 뒤 다시 반영. 이름이 모두 값에 있으면 다른 묶음처럼 자리 차례로 맞춘다(§12 「이 보호의 범위」와 같음).
- **외 기관 절**(`_outside_groups`): 「연구개발기관 외 기관」·「연구개발기관이 아닌 …」 머리 문단(앞 4블록 안) 아래 「가. 기관명: (역할: )」·「나. 기관명: (역할: )」 제목 줄 — 사이가 표·빈 줄뿐이면 이어진 항목.
  항목 = 제목 줄부터 다음 제목 줄 앞까지(양식: 제목 줄 + 11x6 표 + 빈 줄), 마지막 항목은 앞 항목 길이만큼. 값 = 외 기관 1, 2, … · 목표 = 추가 설정의 「연구개발기관 외 기관」 수 —
  **0곳이면 항목을 다 지우고**(표지 외 기관 행·국외기관 묶음과 같은 정책), 여럿이면 본뜬다. 제목 줄은 차례 글자(가·나·다…)를 자리대로, 이름이 있으면 「기관명:」 뒤에 쓰고 「(역할: )」 은 그대로 둔다.
- 사업화 절의 한계: 양식은 「※ 주관/공동연구개발기관 중 기업만 작성」이지만 묶음의 목표는 주관 + 공동 **전부**다(비영리로 고른 기관 몫도 생김 — ④).
